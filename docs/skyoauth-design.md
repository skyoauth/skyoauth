# SkyOAuth — Architecture, security model, and roadmap

> **Status:** proposed design for review. This document specifies project requirements, not implemented authentication. The bootstrap supplies a Rust service and a TypeScript health client. See [skyoauth-tasks.md](skyoauth-tasks.md) for interfaces, schema, milestones and release tests.

## 1. Executive summary

SkyOAuth is a small, self-hostable **identity bridge** for public-facing applications and private APIs. It accepts existing human and workload identities, applies administrator-owned trust and authorization policies, and presents stable SkyOAuth credentials to protected services without application-managed static API secrets.

SkyOAuth is not an upstream human identity provider, service mesh or application traffic proxy:

- **Browser:** upstream OIDC establishes an opaque, Secure/HttpOnly server-side session. A required **TypeScript SPA library** manages browser-safe session state and CSRF; JavaScript never receives OAuth access or refresh tokens.
- **CLI:** a required, reusable **Rust client crate** uses SkyOAuth's stable public-client Authorization Code + PKCE interface and transaction-specific confirmation. It receives short-lived SkyOAuth API credentials, not upstream-provider tokens. A reference CLI consumes this library rather than implementing a second protocol stack.
- **Workloads:** GitHub Actions OIDC, projected Kubernetes service-account tokens and registered external JWTs become scoped SkyOAuth access tokens. Direct exchange uses RFC 8693; single-proof service delegation is an explicitly separate extension (§5.7). **GitHub Actions → our k3s APIs is mandatory.**
- **Gateway:** Envoy Gateway calls a private, out-of-band gRPC `ext_authz` service. Minimal bearer support ships in M2; cookie/session support in M3. ConnectRPC calls, streams and downloads flow **directly from Envoy to the application**, never through SkyOAuth.
- **Backend:** the application remains authoritative for resource RBAC. It validates the signed credential profile, its own registered audience, canonical tenant/resource ownership and operation permissions. Audience registration and service identity are different objects.

**Non-negotiable migration goal:** replacing the upstream human IdP requires **zero changes, rebuilds, reconfiguration or redeployments of browser/CLI/agent clients or protected services**. Human reauthentication is acceptable. WIF registrations, discovery URLs, uploaded JWKS, per-cluster TokenReview configuration, subject bindings, supported service grants, audiences/scopes, resource constraints and effective policy decisions survive without administrative reset. Unsupported impersonation policy remains disabled, including after a capability upgrade.

SkyOAuth owns its public issuer/signing keys, tenants, audience authority, clients/application origins, principals, trust/policy database and independent operator authority. These are not owned by the replaceable human IdP.

### 1.1 Goals

1. Remove static application API keys/PATs/bootstrap secrets from SPAs, CLI applications, CI jobs and workload agents.
2. Provide **both** a TypeScript SPA library and a reusable Rust CLI library with stable, versioned contracts across human IdP migration. Their credential APIs are intentionally different.
3. Support GitHub Actions → protected cluster APIs without cloud STS, SPIRE, sidecars or an auth-service data-plane hop.
4. Preserve independently administered WIF sources, keysets, bindings, service policies, audience assignments and client registrations across migrations/upgrades.
5. Work with k3s/Kubernetes, Envoy Gateway, ConnectRPC and optional Cloudflare Tunnel/alternate gateways.
6. Keep the Rust service narrow and auditable; separate authentication, issuance, independent operator authority and application resource authorization.

### 1.2 Non-goals

- Passwords, end-user MFA, directory provisioning, upstream consent management and organizational identity governance. **SkyOAuth's native-client confirmation and independent operator credentials are in scope.** Device verification/confirmation is required if that optional flow ships.
- A mandatory service mesh, SPIRE/SPIFFE, cluster sidecar or node agent.
- Proxying application bodies, streaming payloads, downloads or SSE through SkyOAuth.
- General cloud credential brokerage in v0.1; this does not make WIF for SkyOAuth-protected APIs optional.
- Replacing backend resource RBAC with a universal application ABAC engine.
- Public access to upstream administrator tokens, arbitrary impersonation, or token-controlled URL/JWKS discovery.
- Identical secret-handling APIs across browsers and native apps; a Node-only client or reference executable alone does not satisfy the two library requirements.

### 1.3 Bounded release scope and workload-first delivery

v0.1 still requires direct/delegated WIF, opaque SPA sessions, both client libraries, usable native login/renewal and zero-reset human-provider migration. It does **not** require active true impersonation, device flow, an admin UI, cloud STS, alternate gateways, provider-token exchange or a general enrollment/invitation product. Dormant impersonation storage is a preservation rule, not an activation subsystem (§5.6).

The logical schema is specified together, but implementation is split: **M1a** delivers workload principals/trust/grants, tenant/audience/checker authority, independent operator/bootstrap/recovery and durable replay; **M2 can ship its usable WIF slice after M1a**. **M1b**, completed before M3, adds human providers/enrollment, origin/routes/client policy, browser/native/refresh state and the sole provider-transition primitive. M1b can run alongside M2; human tables, native approval UX and optional features do not block the first workload token. Tasks §9 assigns the boundary explicitly.

A small installation provisions one explicit tenant and may assign several scoped roles to one operator. Tenant IDs, audience ownership and isolation checks apply even to a single-tenant installation. Tenant-management UI and self-service tenant creation are not required. Any future single-tenant-only distribution is a separate reviewed scope choice, not a reason to omit tenant checks from credentials that already carry them. Full v0.1 acceptance remains stronger than the earlier usable M2 milestone.

A human migration is not an external issuer's compromise/rotation/outage or a requested WIF-policy change. Those can require independent operator action. Equal emails do not prove identity continuity. The replacement provider must meet the configured human-authentication requirements. TokenReview reviewer rotation, audience administration and signer rotation remain independent operations, never implicit migration side effects.

Browser auth routes are served on the registered application origin. Native authorization and its upstream callback are on the canonical issuer origin. External clients cannot reach private authorization, live-policy or operator listeners.

### 3.1 Four boundaries

1. **External proof is untrusted until verified by the selected registered source.** An `iss`, `kid`, source ID or grant ID is not authority to choose a verifier URL, tenant or subject.
2. **SkyOAuth owns issuance and administrative trust.** Stable local human/workload/service principals are distinct from upstream subjects. Independent `adm_*` identities cannot be acquired through OIDC claims or WIF. Instance-owned audience assignments bound tenant issuance.
3. **Envoy authenticates transport, not application permissions.** Protected routes fail closed; client identity headers are stripped; the backend is not directly accessible to untrusted callers.
4. **The API checks the exact credential profile and canonical resource tenant, then RBAC.** An explicit human `backend_rbac` constraint mode is not a WIF exemption or an automatic allow.

Isolate **public access-token** signer keys/permissions from public handlers and operator/reviewer credentials; no process that serves Check or holds internal assertion keys has public-signing permission (OQ-TM-10). That signer can be separately deployed or use KMS/HSM; it enforces structural limits and logs every signature rather than re-checking issuance policy (§6, OQ-TM-16). The gateway's internal assertions instead use a distinct local signing key and private verifier set (§6.2), never the public issuer key. No client library replaces server-side enforcement.

## 4. Deployment, origins and traffic paths

Baseline: Rust/Axum + Tokio, PostgreSQL, two or more stateless replicas, public HTTP via Envoy, separate authenticated private gateway/policy/operator listeners. Valkey is an optional bounded cache, not a required security dependency. Gateway API HTTPRoutes and SecurityPolicy protect every sensitive route.

| Entry point | Example | Boundary |
| --- | --- | --- |
| Issuer/token/JWKS | `https://identity.example.com/oauth/token`, `/.well-known/jwks.json` | Public, TLS, rate limited |
| App auth | `https://app.example.com/_skyoauth/login`, `/callback`, `/session`, `/logout` | Registered ApplicationOrigin; app-local cookie |
| Native flow | Issuer `/oauth/authorize`, `/oauth/callback`, `/oauth/confirm` | Issuer-local transaction cookie; no app-cookie sharing |
| App RPC/streams/downloads | App `/rpc/...`, `/events/...`, `/downloads/...` | Envoy -> backend, no SkyOAuth payload hop |
| Auth checks | `envoy.service.auth.v3.Authorization/Check` | Authenticated private Envoy caller |
| Live policy check | `POST /internal/v1/policy/check`; `/internal/v1/policy/recheck-session`; `/internal/v1/policy/close-session` | Registered checker; admission, renewal and idempotent release of its own stream context |
| Internal assertion keys | `GET /internal/v1/assertion-jwks` | Private authenticated checker/gateway trust distribution, never public issuer JWKS |
| Operator API | `/admin/v1/...` | Separate private mTLS authority and local roles |

`ApplicationOrigin` binds one canonical HTTPS origin to one tenant, callback URI, allowed relative return paths and approved API audience IDs. Its global origin ownership is enrolled by instance `security_admin`; a tenant cannot claim another tenant's host. A scoped `client_admin` can narrow permitted routes/audiences but cannot reassign the host/tenant. v0.1 does not implicitly multiplex tenants on the same origin. Multi-tenant applications may serve multiple application organizations inside their one explicitly mapped SkyOAuth tenant; any different mapping needs a separate reviewed protocol.

Resolve browser tenant/provider from the registered origin and `TenantLoginState`, **not** a free `tenant` query or an untrusted forwarded header. At the public ingress, require an allowlisted authority/SNI/route match; SkyOAuth accepts canonical authority only from its authenticated trusted gateway chain. Unknown/ambiguous origin, spoofed Host/Forwarded values or disabled origin denies before redirect. Return locations are normalized same-origin relative paths validated against the stored allowlist; reject protocol-relative URLs, backslashes, traversal and prefix-confusion tricks.

Use host-only `__Host-` cookies with Secure, HttpOnly and Path=/; do not broaden Domain for convenience. An issuer host distinct from the app host does not imply sharing their cookies. The active-provider switch preserves origin and callback registrations.

**Backend identity transport:** bearer calls carry their original SkyOAuth access JWT; cookie calls cause SkyOAuth to return a short-lived signed internal human-session assertion to Envoy for the private, overwritten backend header `X-SkyOAuth-Assertion` (§6; OQ-API-10). Both internal links are authenticated and the backend rejects mixed credentials. RPC failures return typed errors, never an IdP HTML redirect: 401 for missing/invalid authentication, 403 for definitive authorization denial, the distinct capacity results in §6.1.1, and 503 for unavailable route/auth infrastructure (§4.2). The SPA explicitly navigates to login only for an authentication result. An alternative header adapter must preserve the same typed identity semantics and authenticated transport, not infer profiles from a subject prefix.

**Consume browser credentials on every route except the exempt SkyOAuth cookie endpoints.** On an enrolled host, including the issuer host, every route except the exempt cookie endpoints below (seven fixed endpoints plus each exact registered per-provider issuer callback path) removes **all Cookie fields** and `X-SkyOAuth-CSRF` before forwarding, regardless of authentication class or whether ext_authz runs (OQ-GW-3, OQ-GW-12). This includes the SPA shell, assets, public/health endpoints, bearer routes and every non-exempt SkyOAuth endpoint. Configure HTTPRoute `RequestHeaderModifier.remove: [cookie, x-skyoauth-csrf]`, producing Envoy route-level `request_headers_to_remove`; the rule is not conditional on an auth-service response. On protected routes, SkyOAuth must first receive the original bounded metadata for session/Origin/CSRF validation and mixed-credential rejection. Use ordinary upstream-stage removal, not early removal before ext_authz. The gRPC `OkHttpResponse.headers_to_remove` remains defense in depth, with non-appending assertion replacement. Authentication rejects duplicate/ambiguous SkyOAuth cookies rather than choosing a copy. Never copy cookies/CSRF into alternative forwarded metadata; redact them in gateway logs/traces as well as application logs. Test actual filter ordering and upstream bytes, including retries and mirrors; prohibit configurations that restore or expose the credentials.

**Application responses cannot set cookies in v0.1.** Every such route also configures HTTPRoute `ResponseHeaderModifier.remove: [set-cookie]` / Envoy `response_headers_to_remove: [set-cookie]`, removing every Set-Cookie field, not selectively parsing reserved names. No Lua/Wasm/ext_proc cookie-name filter is required by this baseline. Seven fixed SkyOAuth cookie endpoints routed to the independently verified SkyOAuth backend identity are exempt consumers/issuers of their required cookies: app-origin `/_skyoauth/login`, `/_skyoauth/callback`, `/_skyoauth/session` and `/_skyoauth/logout`, and issuer `/oauth/authorize`, `/oauth/callback` and `/oauth/confirm`. Each exact per-provider issuer callback path (server-generated `/oauth/callback/{provider_id}`) registered for a provider without RFC 9207 `iss` (§5.2, OQ-TM-4) is exempt in the same way as `/oauth/callback`: it consumes and rotates `__Host-skyoauth_native`, is listed by exact path in the approved issuer projection and routes to the verified SkyOAuth backend; no prefix or pattern exemption covers such paths. Every other SkyOAuth endpoint, including `/oauth/token`, `/oauth/revoke`, `/.well-known/*` and `/_skyoauth/oidc/backchannel-logout`, keeps both removals (OQ-GW-3). A path prefix, caller header or tenant-supplied flag alone cannot grant an exemption. Include both removals, their stage/order and the exact exemptions in the approved semantic projection. Missing removal or an unauthorized exemption rejects preparation/activation. Public-route tests run with no ext_authz call and still prove that static servers receive no session/flow cookies and cannot set them. Genuine SkyOAuth login/callback/session/logout/native flows must continue to work. A billing or static-file backend receives no reusable session credential usable against another audience. This is credential containment, not isolation from malicious JavaScript served on the same trusted application origin.

Cloudflare Tunnel supplies connectivity, not per-route authorization. WAF, rate limits and Cloudflare Access remain separately configured. Do not trust arbitrary `CF-*` or `X-Forwarded-*` outside the configured proxy chain.

### 4.1 Cookie route selection and request binding v1

`ApplicationRoute` is a tenant-owned child of `ApplicationOrigin`, administered by `client_admin` within that origin's audience assignments. Its immutable configuration version records an exact or segment-prefix path, nonempty method allowlist, exactly one resource-server ID, accepted credential profiles, session lease duration and maximum stream duration. For cookie requests, SkyOAuth resolves **only the origin/route versions pinned by the active RouteBundleVersion** (§4.2), then selects that origin's `HumanAccessPolicy` for the route's audience. `/rpc/billing` and `/rpc/deploy` can therefore issue different audiences/scopes on the same host. Request headers, cookies, query parameters and JSON bodies cannot select an audience or policy. A staged PATCH is not a live authorization change.

For a method, exact path beats prefix; otherwise choose the longest matching **segment** prefix (`/rpc/billing` matches itself or `/rpc/billing/...`, never `/rpc/billing-admin`). Reject equal-precedence conflicts on writes. Select before checking status: a disabled winning route denies rather than falling back to a broader route. Unknown routes/methods, missing policy/assignment or unsupported profiles deny. Gateway routing and this registry must select the same receiver; the mandatory admission procedure below applies to every change, not just initial deployment. M2 bearer routes already pin an expected audience in gateway/backend configuration; this additional cookie mapping ships in M3. Bearer validation never chooses the expected audience from the token itself.

**Routing-agreement admission is mandatory on every change** to either ApplicationRoute or gateway routes, precedence, receiver destinations, authentication policy, rewrites or route-cache behavior. A revision-checked deployment plan validates the prospective pair for method/path/host selection, exact audience/receiver, supported profiles and no-rewrite rules. Generate both representations from one reviewed route bundle where practical; direct registry PATCH/import or an out-of-band gateway edit cannot activate an unchecked mapping. Restrict gateway mutation to the admission-controlled deployment path; a CI smoke test alone is not enforcement. Registry and gateway administrators retain their respective authority; neither role silently acquires the other's rights. Section 4.2 defines the enforcers and persisted evidence.

There is no distributed atomic-write claim: staging leaves the old pinned pair live. A real gateway change closes the entire affected origin bundle to new cookie-authenticated application requests for its apply-and-observe cycle, not merely the edited path. Unchanged contexts may retain only their existing leases during that window (§4.2); operators must account for possible stream interruption. Independently classified public routes and fixed SkyOAuth cleanup endpoints are not implicitly cookie-gated. A strictly registry-only activation may instead switch pins atomically under the unchanged deployment evidence without closing the gate, subject to §4.2's exact equivalence and freshness checks. Known mismatch stays closed; transient observation loss uses only the bounded last-verified-state rule. A deliberate rollback after successful activation is another validated activation; compensating an unfinished apply uses only the separately bounded abort authority in §4.2. Neither restores historical security state. Unaffected bundles need not stop. The coordination cost and possible denial are explicit; trusted per-route audience metadata remains a future alternative under ADR-007/ADR-020, not a caller-header fallback.

The internal assertion carries `skyoauth_route` (the ApplicationRoute ID) and `skyoauth_route_version` (the pinned ApplicationRouteVersion ID; OQ-TP-1), plus `skyoauth_request={version:1,method,scheme,authority,target_sha256}`. The v1 tuple is the request **after ingress validation/normalization and before ext_authz**, and must be identical at the backend before framework URL decoding. `scheme` is `https`; `method` is the exact uppercase registered method. `authority` is the registered lowercase ASCII/IDNA host with a non-default port if present (443 omitted); userinfo, trailing-dot aliases and conflicting Host/:authority are rejected. The internal TLS hop does not redefine the external scheme/origin.

`target` is the exact ASCII origin-form path plus optional `?query`. Query ordering, duplicate parameters, percent-escape spelling, `+` versus `%20`, and absent versus empty query are preserved; neither signer nor verifier parses/reorders the query or decodes the bound target. Ingress rejects fragments, controls, literal backslashes, malformed escapes, encoded path separators, dot/traversal segments (including percent-encoded dots) and repeated path slashes; non-ASCII path data must be percent-encoded. Canonical authority validation occurs once before route selection. These are required deployment/parser rules, not assumed Envoy defaults. The backend compares method/scheme/authority and the raw-target digest before applying its documented single URL-decoding pass for resource routing; configurations needing double-decoding are unsupported.

`target_sha256` is the unpadded base64url encoding of the full 32-byte SHA-256 digest of the exact ASCII `target` bytes defined above (43 characters). Do not include the raw path/query in the assertion or its stored continuation binding. The backend recomputes that digest from its received raw target; it does not hash a parsed/reconstructed URL. This keeps the binding fixed-size without changing exact-match semantics. Hashes are not encryption or anonymization: low-entropy targets can be guessed, so redact assertions/digests and sensitive request queries from logs. Input target/header size limits still apply.

Request-binding fixture: target `/rpc/billing?item=1&item=2&q=a%20b` has `target_sha256=EqNKWsbu3kU-OFps9t2Cn28dZrhJcWZ1ApnVNevplu8`. Test that query order, duplicate values, escape spelling and absent versus empty query produce different bindings; a 4 KiB query must not enlarge the assertion's target claim.

**v0.1 routes accepting `human_session` forbid path/host/query rewrites, post-auth routing-input mutations and route-cache rematching.** No URLRewrite prefix replacement, automatic host rewrite or trust in client-supplied `X-Original-*` is a workaround. Configuration admission/smoke tests reject such routes; unexpected mismatch fails closed at runtime. Backends without access to the raw target cannot use this assertion adapter. Supporting rewrites later requires a separately specified authenticated original/effective-target profile, not relaxed equality. The assertion binds request metadata, not the body; backend resource/RBAC checks remain necessary.

### 4.2 Route admission enforcer and runtime observations

**Protected scope, not opt-in labels.** Instance `security_admin` enrolls the protected set by cluster, Gateway UID, listener and hostname intersection in the approved bundle. A ValidatingAdmissionPolicy/binding (`failurePolicy: Fail`, `validationActions: [Deny]`) plus RBAC restrict configuration writes affecting that set to the dedicated route-controller service account. Guard create/update/delete of every route that could attach to a protected listener/host, including new or unlabeled routes, omitted/wildcard hostnames, more-specific shadow routes, old and new parentRefs, cross-namespace attachments and changes to allowedRoutes/namespace selectors. Non-cookie bearer, public auth and health paths on a protected host are managed resources in the same bundle with their own explicit authentication class; they do not acquire cookie authorization. M2-only routes on a distinct unenrolled host/listener stay outside this mechanism until that scope is enrolled. Shared Gateway-wide policy or listener changes require approval of all affected bundles or are rejected, not declared unrelated because the edited object lacks a bundle label. v0.1 allows exactly one RouteBundle per ApplicationOrigin, so the traffic gate is origin-wide (OQ-GW-8). The issuer host is not an ApplicationOrigin but its routes are enrolled for containment; it is the single exception, carried by one instance-level system bundle (OQ-GW-12). Instance `security_admin` owns and prepares the system bundle; a distinct second `security_admin` approves it, or one actor does both under an explicit audited instance policy. An origin cannot be security-enabled without an enrolled protected scope (OQ-GW-12). A new ApplicationOrigin starts with security_status `disabled` and security_reason `not_enrolled`. The first approved gateway_apply activation covering its verified protected scope enables it only while security_reason is still `not_enrolled`, checked by compare-and-set on security_revision, and advances security_revision in the same transaction; that initial enablement needs no recovery reason or `reenable_targets` entry. An incident security-disable sets security_reason `incident`, so a disabled origin never re-enables this way. security_reason is `not_enrolled` or `incident` while disabled and empty while enabled. Before the M3 route controller exists every application origin therefore stays `disabled` (`not_enrolled`): its `/_skyoauth/login` and `/_skyoauth/callback` deny (OQ-API-1) and SkyOAuth issues no session or assertion for it. Containment applies to the issuer host once the controller is installed.

The adapter's guarded inventory includes Gateway/HTTPRoute/SecurityPolicy, reference permissions, supported security/traffic extensions and backend identity/routing configuration that can affect the protected set. Where an indirect dependency cannot be safely narrowed by the supported admission predicates, guard that entire dependency scope or reject the attachment/extension; do not assume CEL can dynamically traverse arbitrary Kubernetes objects. Pin this inventory and parameterized host/listener rules with tests in T00.5/T50.4. Exactly four admission exceptions exist (OQ-GW-14): narrow status-only updates by the existing gateway controller, the explicitly scoped TLS-renewer update, the non-referenceable cert-manager temporary-key CREATE/DELETE class and the sealed/acknowledged credential-retirement DELETE, as listed under **Guard coverage** below. Infrastructure administration owns the installed policy/bindings, dedicated namespace boundary, parameter schema/mutation guard and maximum writer envelope. Instance security_admin registers that deployed tuple in the service; only service-authorized live renewal/retirement entries within the installed envelope are delegated to the reconciler below. Verify installation before enabling traffic. Ordinary direct edits and new shadow routes are rejected at admission, not merely discovered later. Cluster administrators who can remove these guards remain trusted infrastructure principals.

**Explicit authority and preparation.** The separately deployed **SkyOAuth route controller** (`service/src/route_control`, `skyoauth-service route-control`, M3) is the sole writer for the protected gateway configuration, not for all gateways in the cluster; the explicit TLS-renewer exception below grants only bounded Secret-material updates. A tenant `client_admin` creates a bundle parent, then requests preparation at `POST /admin/v1/tenants/{tenant}/route-bundles/{id}/preparations`. This stores an immutable `AdministrativeOperation(kind=route_bundle_prepare)` input snapshot, expected active generation, origin/route versions, security preconditions, required `activation_mode` (`registry_only` or `gateway_apply`), gateway-apply timeout, and any explicit recovery intent including failed-attempt supersession; it is not an approved deployment or a RouteBundleVersion with a caller-chosen expected digest. The M3 controller's preparation worker runs the pinned translator before approval, computes the input digest (the same value as `translator_input_digest`) inside the isolated route controller, then submits both in its scoped result at `POST /internal/v1/route-bundles/{id}/preparations/{operation}/result`; the service accepts that digest from no tenant or other caller. Every JSON-structured configuration digest is SHA-256 over the RFC 8785 JCS serialization; `adapter_artifact_digests` are the native SHA-256 digest of each binary or image (OQ-GW-7). The service validates operation/input identity, controller scope and current preconditions, and atomically finalizes one immutable RouteBundleVersion containing the expected gateway digest and a server-computed complete plan digest. The mode is immutable and included in both digests: there is no automatic mode. Finalization rejects a registry_only plan unless it is deployment-equivalent to the captured deployment_version_id and has no recovery targets; the same equivalence is checked again at execution. A gateway_apply version also contains an immutable `abort_plan`: normally target_kind=restore_pair with the captured prior active registry/deployment version IDs (which may differ), the exact protected resource contents or prior absence to restore, and their expected projection; initial enrollment uses cleanup_to_closed. Recovery after failed compensation has the explicit target rules below. These artifacts are retained through the abort window; no prior deployment is a distinct initial-enrollment case, not an invented rollback target. An exact duplicate result returns the same version; a contradictory result or changed precondition requires rejection/re-preparation. Failed or pending preparation cannot be approved. M1b supplies the schema and draft/result/approval contracts; real translation and executable preparation are M3 deliverables, not an M2 prerequisite.

**Instance `security_admin` approves only a completed prepared version** through `POST /admin/v1/tenants/{tenant}/route-bundles/{id}/versions/{version}/approve`. Its expiring `AdministrativeOperation(kind=route_bundle_approval)` binds the complete plan digest, exact version, expected active generation, protected scopes, adapter/translator inputs, every affected stable parent's `security_revision`, the exact `reenable_targets`, `activation_mode` and any `abort_plan`. Gateway-apply preparation/version/approval also bind `apply_timeout_seconds` (default 120, positive and at most the instance-configurable ceiling, hard-capped at 300 seconds; OQ-LT-6). The approval separately grants exact compensation until an explicit finite `abort_until` later than its forward-execution `expires_at`, within a documented instance maximum. Both deadlines, the apply timeout and the origin-wide interruption, including incident recovery without a gateway change, are shown to the approver. Registry-only approvals grant no gateway-write or compensation authority. Recheck enabled preparer/approver authority, approval validity and all preconditions before begin and again atomically at activation. A later disable, changed input, expired/revoked approval or intervening activation invalidates forward execution; after begin, expiry or a newer disable enters the bounded abort path below rather than authorizing stale activation; a controller credential cannot substitute for either role. A person may hold both roles only by explicit assignment. Approval authorizes only that mode, exact forward plan and explicitly bounded compensation/recovery list, never arbitrary manifests or a blanket active flag. Revoking the approval or losing current controller scope also prevents compensation; forward expiry alone does not, and disabling the preparer or approver is not a revocation and does not stop it (OQ-GW-9). The mode cannot be changed by the controller or an approval retry.

**Cancellation and approval revocation are distinct administrative operations.** Tenant `client_admin` within the bundle's scope or instance `security_admin` may call `POST /admin/v1/tenants/{tenant}/route-bundles/{id}/attempts/{attempt}/cancel`. It records an audited `AdministrativeOperation(kind=route_bundle_cancel)` with reason and expected attempt revision, atomically marks that current applying attempt `abort_required`, and retains its already-approved compensation authority. It performs no gateway writes. A cancel of the same abort_required/aborting attempt is idempotent and changes neither deadline; a stale attempt ID cannot cancel a successor. Only instance `security_admin` may call `POST /admin/v1/tenants/{tenant}/route-bundles/{id}/approvals/{approval}/revoke`, recording a revision-checked `route_bundle_approval_revoke` operation and the approval's monotonic `revoked_at`/`revocation_operation_id`, never changing its immutable plan. This rejects unbegun execution and stops both forward and compensating writes of a current unfinished attempt, which becomes `recovery_required` with the gate closed. Revocation is not the graceful-cancel mechanism. Exact retries return the recorded result; activation/cancel/revoke races serialize with the attempt and approval checks. Revocation after a completed activation does not undo that deployment; incident traffic denial uses the independent security-disable operations. Neither call can clear security vetoes or grant replacement authority.

**Administrative attempt discovery.** On the private operator API, `GET /admin/v1/tenants/{tenant}/route-bundles` returns bounded bundle summaries with traffic_gate/gate_reason, apply_phase and current attempt ID/revision; `GET /admin/v1/tenants/{tenant}/route-bundles/{id}` returns a consistent runtime snapshot. Tenant client_admin within that bundle's scope or instance security_admin may read it, the same scope as cancel; neither needs controller credentials or direct database access. Detail includes runtime revision/active generation and `current_attempt={id, revision, reason, begun_at, apply_deadline, approval_id, approval_revision, approval_status, abort_until}` or explicit null when none exists. Reasons are redacted enums/safe summaries, not raw controller errors. Reads expose no write journal, manifests/xDS, private worker inputs or Secret material, and grant no write authority. List filters/cursors cannot broaden tenant/bundle scope. These reads remain independent of the application traffic gate, including unconfigured/recovery_required origins. The operator reads the attempt ID/revision before cancel or supplying supersedes_attempt_id to preparation; a racing phase/revision change must reject the stale write rather than act on a newer attempt. T14.9/T32.3/T50.4 exercise that workflow through the admin API.

Registered controller mTLS identities have explicit gateway/origin scope and no signer, WIF or human authority. Bounded, cursor-paginated private `GET /internal/v1/route-bundles` discovers only that identity's pending preparations and prepared/approved/active work; cursor/filter input cannot broaden scope. Private `GET /internal/v1/route-bundles/{id}` returns scoped preparation inputs, prepared plans and durable active/applying/deployment generations, epoch and sequence. No generated bundle ID needs to be baked into the controller deployment. Controller-only `POST .../{id}/claim` allocates a durable ownership epoch/lease; `POST .../{id}/transitions` supports service-validated begin/activate/abort/complete_abort and the registry-only operation below; `POST .../{id}/observations` records evidence under that epoch and increasing sequence. Ordinary begin requires idle; the separately approved supersession below is the only non-idle exception. Begin accepts only a gateway_apply approval and closes before any apply; activate accepts only that current forward attempt and requires a complete matching observation set. activate_registry_only accepts only a registry_only approval. Wrong-mode calls reject without changing the gate or performing writes. Begin records the exact abort source and a durable per-object write journal; ownership checks and UID/resourceVersion preconditions apply to every forward or compensating write. Reconciliation uses leader election and Kubernetes resourceVersion preconditions; uncertain/incomplete writes during handoff keep the gate closed until the new owner reconciles and re-observes. Old epochs/replayed reports cannot reopen it. Deploy at least two controller replicas with disruption/placement controls; failover never resets sequences or observation ages.

Helm, Argo CD and Flux may render/submit approved bundle inputs, but cannot directly apply managed objects while this sole-writer guard is installed. The SkyOAuth approval/controller path is therefore a deliberate deployment dependency, recorded in ADR-020. Unenrolled scopes remain independently managed. A future design that admits existing deployers' writes against approved object digests is an alternative, not an undocumented second writer.

**Immutable configuration versus live state.** Stable `ApplicationOrigin` and `ApplicationRoute` parents retain identity/ownership plus immediate `security_status` and monotonic `security_revision`. Append-only origin/route versions contain planned configuration; PATCH/import stages and never changes active pins. A completed RouteBundleVersion pins the complete origin/route version set, gateway plan, activation_mode, optional abort_plan, projection/adapter versions, expected digest, `security_preconditions` and `reenable_targets`. Runtime apply_phase is idle, applying, abort_required, aborting or recovery_required. A durable RouteBundleAttempt records its ID, version/approval, original begun_at/apply_deadline, revision, reason and per-object write journal; completed and superseded attempts remain linked audit history. Runtime points to the current attempt; restart/claim never resets its deadlines or loses unresolved writes. RouteBundleRuntime separates active registry pins from `deployment_version_id`, the approved version whose unchanged gateway configuration is backed by observations. Per-proxy RouteBundleObservation samples bind the deployment version, serving-set generation, epoch and sequence; attempt ID and target_kind additionally distinguish forward, restore_pair and cleanup_to_closed evidence. Cleanup evidence has no serving deployment version and cannot enable traffic. Polling does not revise authorization or create policy-change audit events. Activation supersedes only credentials/contexts whose actual origin/route or security dependencies changed; an unchanged route is not revoked solely because the bundle ID/version pointer advanced. Capacity records remain independent operational state.

**Incident disable and explicit recovery.** Security-disable of an origin or route is tenant `client_admin` only; instance `security_admin` does not disable a tenant's origin or route (OQ-API-6). A disable atomically sets the parent's security_status to disabled (for an origin, with security_reason `incident`), advances security_revision and invalidates forward execution of plans that captured the prior revision. If its current attempt is applying, the same transaction marks it abort_required and keeps the origin gate closed. Existing abort_required/aborting compensation retains its phase and deadlines; recovery_required cannot be cleared by disable. Other detected failures of an applying attempt's forward preconditions, including forward approval expiry, also require abort; they never clear the veto or reopen on a stale activation. Security preconditions cover the origin and all pinned or otherwise affected route parents, including a removed/replaced route; they are execution preconditions, not a continuously enforced equality that disables unrelated live routes. The 09:00 approval cannot activate after a 09:20 disable without re-preparation and fresh approval. If disable races activation, the shared transaction/CAS order either rejects stale activation or applies the later disable; it never clears the incident accidentally. A new plan may preserve a disabled parent, or name it explicitly in `reenable_targets` with its current disabled revision and recovery reason. Successful activation clears only those named parents and advances their security revisions in the same transaction as the pin change. Omitted targets keep their security state. Unpinning/replacing a security-disabled route requires explicit recovery intent for that parent rather than an overlapping new-ID bypass. Re-enablement cannot resurrect invalidated credentials or closed continuations; new evidence snapshots current security revisions. Rollback follows the same rule, not historical security-status restoration.

A route is usable only when the origin and route parents are security-enabled, the pinned ApplicationRouteVersion has `configured_status=enabled`, and the ordinary gate/policy checks pass. Configured disabling is a planned version change; security disabling is an immediate independent veto. Clearing one does not clear the other. Select the winning route before checking either status; neither disabled form permits broader fallback.

**Failure detection and apply deadline.** Begin durably sets `apply_deadline = min(begun_at + apply_timeout_seconds, approval.expires_at)`. Before that deadline the controller may retry transient apply/observation failures; a nonretryable write/programming failure, an administrative cancel, a failed forward precondition or reaching the deadline requires `abort_required` and stops forward work. In particular, a proxy that never produces the matching digest triggers abort at the apply deadline, not hours later when its approval expires. The owning controller may call `abort` directly from applying for a recorded nonretryable failure or elapsed deadline; the service records that reason and the phase change atomically. A durable service reconciler checks deadlines at least every 10 seconds, and every transition independently enforces them; activate at/after the deadline rejects even if the reconciler has not run. Ownership transfer never gives another apply interval. If no controller can compensate, the gate stays closed; no service-side timer performs Kubernetes writes.

**Abort of an unfinished apply.** A gateway_apply approval authorizes compensation only to its exact abort_plan, not arbitrary historical versions. On abort_required, or the applying failure/deadline case above, `abort` changes that attempt to aborting. Abort calls bind its approval/attempt ID, plan digest and current controller epoch; they cannot select an arbitrary source or another attempt. The controller stops forward work, quiesces/fences prior owners and outstanding writes, and restores only the approved protected resource values. It may delete an attempt-created object only with the journaled matching UID and ownership; conflicting or ambiguous writes keep the gate closed. Unrelated host resources must not be overwritten. A successor owner can resume the same bounded journal under a new fencing epoch. Current controller scope, an unrevoked approval and now < abort_until are mandatory; they are the required authority for compensation. Disabling the preparing client_admin or the approving security_admin is not a revocation and does not stop compensation; only explicit approval revocation does (OQ-GW-9). Existing abort-source holds retain their protection proof during a scope PATCH, after a verified same-ID cutover and through a protection-reconciler outage, provided coverage remains continuous as specified below. Their transfer does not require fresh adoption readiness. A newer parent disable or elapsed forward expires_at is not a reason to reject these already-approved compensating writes; expiration/revocation of the compensation authority is.

`complete_abort` is valid only for that current aborting attempt and may reopen its prior registry/deployment pair only after all writes have settled and a complete fresh observation set proves that exact restored projection for the current serving set. The service records those real samples, retains the prior registry/deployment IDs, ends the failed attempt and advances the runtime generation to fence stale plans. An exact completion retry returns the recorded result without new writes; replay after a newer attempt cannot restore older pins. It restores no security_status/revision, role, policy invalidation, session or continuation. Thus a disable after begin causes old unaffected routes to become usable after restore-and-observe while the incident route stays disabled at its newer revision; forward expiry has the same recovery path without a new preparation/approval within abort_until. Closed or expired streams require fresh admission. For initial enrollment with no prior pair, abort removes only attempt-owned staged resources and leaves the origin unconfigured/closed. A nonretryable compensation failure, missing artifacts, unresolved conflicting writes, revoked approval, lost controller scope or now >= abort_until moves the unfinished attempt to `recovery_required`; no old forward/abort call can write or reopen it. Transient compensation failures may retry only within the original abort window. Aborting is idempotent and bounded, not a general rollback API or a promise of uninterrupted service. Incident re-enable intentionally uses gateway_apply and this same interruption/compensation contract even when gateway contents are unchanged.

**Superseding a failed attempt.** recovery_required is not a dead end. The scoped client_admin requests a new preparation on the same preparations endpoint with `activation_mode=gateway_apply` and `supersedes_attempt_id`. A current scoped controller owner must first fence/quiesce the old writer and settle every outstanding request; an unaccounted in-flight write or unknown ownership blocks finalization, never licenses a forced overwrite. It captures a bounded recovery inventory and the failed attempt's revision/journal digest, last completed registry/deployment pair, all unresolved writes and cleanup obligations. These become the immutable `recovery_snapshot_digest` and approved input/plan, with current security revisions and new deadlines. The snapshot is of actual mixed resources, not a claim that they are an approved deployment. Preparation alone neither ends the old attempt nor opens the gate. Instance security_admin must explicitly approve the supersession, exact forward/cleanup scope and abort target with currently enabled preparer/controller/approver authority; a revoked old approval grants none of this new authority.

Only this newly approved recovery `begin` may replace a non-idle recovery_required attempt. Under the new ownership epoch it atomically compares the failed attempt ID/revision/journal digest, recovery inventory and active generation, records the old attempt as superseded, and installs a new attempt with all unresolved journal entries/cleanup obligations, including objects created by earlier attempts but absent from the new desired plan. Ordinary begin still requires idle; registry-only mode cannot supersede. Journal compaction may not discard unresolved provenance. Every repair/delete retains UID/resourceVersion/ownership checks; changed inventory requires re-preparation. Old owners, approvals and completion retries cannot act on the successor. The gate and old pins remain unchanged until verified completion; successful activation or compensation advances generation and never clears a newer security veto implicitly.

The recovery version's abort_plan **does not restore the captured mixed state**. It must either revalidate the retained last completed pair and its exact artifacts under current dependencies (`target_kind=restore_pair`), or, when those artifacts are unavailable/unusable, explicitly approve a complete non-serving `target_kind=cleanup_to_closed` configuration and exact owned-resource cleanup list. The latter preserves fixed SkyOAuth cleanup endpoints and unrelated hosts; it is not permission to delete foreign/conflicting objects. `complete_abort` for that target requires settled writes, verified cleanup/absence and fresh complete evidence of the approved non-serving projection. It then records the closed outcome, clears live registry/deployment pins to unconfigured, ends the attempt and advances generation **without opening the gate**; archived pins/journals remain auditable. Successful recovery activation and either abort completion require every inherited journal obligation to be reconciled, including removal of journal-owned leftovers absent from the approved target. Another failure or expired/revoked recovery approval returns to recovery_required and may be superseded by another freshly prepared/approved recovery, never by extending old authority or inventing evidence.

**Registry-only activation.** Only a version and approval explicitly marked activation_mode=registry_only can use `activate_registry_only` on the existing transitions endpoint to switch active registry pins without begin, gateway writes or gate closure only when the service verifies unchanged managed gateway resource contents, relevant dependency identities, protected scopes, adapter/bootstrap/projection versions, expected gateway digest and serving-set generation. The current gate must be eligible with complete fresh observations (within 30 seconds), all approval/security preconditions must still hold, and reenable_targets must be empty; incident recovery uses ordinary reviewed activation. Compare the approved artifacts themselves, not just equal resource names or a caller's no-op flag. Atomically advance active registry pins/generation and supersede only changed authorization dependencies, retaining deployment_version_id and the original observation samples, collection times and deadlines. No copied sample gets a new age or extra tolerance. A failed fast-path check leaves the old pair unchanged; it does not silently fall back into a disruptive apply. Freshness failure may be retried in the same mode while its approval remains valid; a disruptive retry needs a new gateway_apply preparation and approval with its interruption disclosed. Begin must reject the original registry_only approval even when its samples have become stale. Changing only one route's lease therefore need not interrupt unrelated routes, but the changed route's existing contexts still require fresh admission.

**Actual observation mechanism.** Envoy's admin interface is not assumed to provide remote authenticated read-only access; Envoy Gateway normally exposes it only on pod loopback. The supported adapter adds a **separate static management listener through EnvoyProxy bootstrap customization**, not a public HTTPRoute and not a sidecar. It requires mTLS for the enrolled controller, network access restricted to that controller, and an exact allowlist of GET requests to fixed, adapter-owned `/config_dump?resource=...&mask=...` targets forwarded to the fixed loopback admin cluster. T00.5 freezes only their shape (a fixed `resource` and `mask` per target, a maximum response size and a request timeout); the literal targets/masks and size/time bounds for each supported adapter are fixed in T32.3/T50.4 against a tested version pair (OQ-GW-1). Reject caller-supplied query variations, arbitrary paths/methods, bodies, upgrades, CONNECT, redirects and generic admin proxying; never expose secrets dumps or `/quitquitquit`, `/drain_listeners` or `/runtime_modify`. The controller receives no pods/exec or pods/portforward permission. The raw admin port stays loopback-only. Validate the listener and its isolation before admitting protected traffic; deployments unable to enforce this adapter do not silently open the full admin surface.

**Translator ownership.** The M3 route-control preparation worker, not the public auth service or tenant caller, runs the same pinned Envoy Gateway translator build through `egctl x translate --from gateway-api --to xds` before a version can be approved. Execute it as an isolated, resource/time/output-bounded helper on the validated complete input snapshot and explicit bootstrap inputs: fixed binary/arguments, no shell, tenant-selected executable or network fetch. Unspecified missing-resource synthesis is forbidden; only the supervisor's explicit Secret substitution below is permitted, and egctl's general `--add-missing-resources` stays disabled. The helper has no real auth, signing, reviewer or operator credentials. In particular it cannot access the controller's Kubernetes service-account token, mTLS private key, kubeconfig, secret mounts/environment, inherited credential file descriptors or authenticated API/proxy sockets. A credentialed supervisor performs scoped API calls; the helper receives only the bounded sanitized input and returns bounded output through dedicated pipes. Use an enforced process/container sandbox with no shared credential mounts or service-account automount, not merely a promise that the child will not read inherited secrets; test attempted access and network/API use. The public auth-serving image need not contain egctl. The service authenticates/binds the worker result to its pending operation; the scoped worker is an explicit trusted preparation component, not proof that a caller-supplied hash is correct. Do not reimplement Envoy Gateway translation or derive the expected digest from a running proxy. Pin Gateway/egctl/Envoy/bootstrap artifacts together and rerun projection fixtures plus real gateway tests on patch upgrades; this specifies a mechanism, not a tested version pair, which T32.3/T50.4 choose with its artifact digests (OQ-GW-2).

**Referenced Secrets in translation.** A complete snapshot means complete validated dependency structure, not production secret bytes in the helper. The supervisor resolves every Secret reference with scoped reads, verifies real existence, reference permissions, supported type/required keys and material validity, and records nonsecret `secret_dependencies`: kind/namespace/name, expected UID, usage and validation_mode. Exact mode additionally pins resourceVersion and approved public fingerprints; supported renewable downstream TLS listeners use the approved tls_renewal profile below, with observed resourceVersion/leaf fingerprints in operational evidence instead of immutable plan inputs. For a TLS certificate the supervisor validates the real key/certificate match, validity and required host identity itself. It substitutes an adapter-versioned deterministic **nonproduction placeholder Secret** of the same reference/type/required-key shape; its fixture certificate/key or credential is public test data and never installed. This is the only permitted substitution, not fabrication of a missing real dependency. Real private keys/passwords/tokens must not enter helper input, logs, plans, results or gateway observation dumps. Reject inline secret material or Secret usages without an explicit validated adapter profile.

The pinned adapter must prove on fixtures that the substitution preserves the projected routing/filter/TLS structure and named SDS references for each supported use. Do not assume a generic placeholder works for a policy/backend that parses credential bytes or derives configuration from them: absent that proof, reject preparation rather than omit its authorization effect. Input/plan digests bind the substitution profile and stable dependency contract, including the validation profile; exact mode also binds its material pins. Desired/observed xDS projection includes the reference and all public security semantics but excludes secret payloads; eligibility additionally requires fresh supervisor verification of those real dependencies, including a fixed-SNI per-proxy handshake/served-certificate fingerprint for supported downstream TLS listeners; other supported usages require their profile-specific safe evidence, never a raw secret dump. The comparison uses the approved validation_mode, not an implicit exact-leaf pin for tls_renewal. That verification is bound by the observation's dependency_evidence_digest, not inferred from placeholder success or a matching xDS name. Runtime secret_dependencies include only references reachable from effective protected configuration. Translation-only references proven disjoint/inert are validated for preparation but excluded from protected dependency evidence; their changes alone do not expire protected eligibility. Unknown reachability stays protected or rejects. Missing/invalid proposed dependencies reject preparation or execution without altering the old live pair merely because a staged plan failed. A known violation of a deployed dependency's approved contract closes the gate as drift; an allowed TLS renewal below is not such a violation. Forward/abort plans reference these dependencies but do not write real Secret data. No real Secret may be restored from a placeholder. T32.3/T50.4 require TLS-listener, supported policy/backend-reference, rotation/missing/invalid-secret and sandbox-leak tests for the actual adapter; this contract does not assert that an untested profile is supported.

**Routine downstream TLS renewal.** The baseline supported renewable listener enrolls validation_mode=tls_renewal. Its immutable dependency contract binds Secret reference/UID/type, protected listener/SNI, an approved validation-profile digest and enrolled renewal-writer identities. The profile pins independent trust anchors and any issuer/SPKI restrictions (not an issuer name or the Secret's supplied ca.crt alone), required hostnames/allowed SANs, serverAuth/key usages, permitted key/signature algorithms and strength, current validity/revocation checks, minimum remaining validity and renewal_overlap_seconds (default120s, positive, at most the instance-configurable ceiling hard-capped at 300s; OQ-LT-6). The profile, trust, reference or UID cannot be widened/replaced by renewal; those are newly prepared/approved configuration changes. The leaf fingerprint and resourceVersion are observations, not immutable pins in this mode. A valid same-UID renewal between preparation, approval and begin therefore does not invalidate the approved plan solely because its material changed; each execution still needs valid current dependency evidence. Other supported Secret usages retain their exact contract. A renewable downstream listener must not silently fall back to leaf pinning: an unproven renewal profile rejects enrollment before traffic is admitted.

The admission/RBAC inventory has a narrow exception for the profile's enrolled certificate renewer (for example the exact cert-manager service account) to update the profile-enumerated TLS entries (tls.crt/tls.key and optional ca.crt) and explicitly enumerated nonsecurity metadata of that exact existing Secret. Any ca.crt is validated public chain input, never authority to replace the independently approved trust roots. It cannot delete/recreate the credential target, change its reference/type/ownership, widen trust/profile, write another dependency or mutate routes/listeners. The separately constrained temporary-key lifecycle below permits no operation on that target. Do not assume CEL verifies certificate cryptography: the credentialed supervisor verifies the real pair/chain/profile before accepting material evidence. Initial Secret provisioning precedes enrollment. No route-controller gateway_apply or new approval is required for an in-profile renewal, and neither the translator nor a compensating plan writes real key material. The adapter must test this writer exception and actual SDS delivery; a cert-manager Ready condition alone is not proof of what every proxy serves.

**cert-manager temporary-key lifecycle.** An explicitly tested cert-manager adapter profile also binds temporary_key_entries within the infrastructure writer envelope: enrolled Kubernetes renewer principal, namespace UID, Certificate name/UID/controller owner reference, reserved cert-manager.io/next-private-key="true" marker (and pinned controller marker), allowed name/generateName prefix and key-only Secret shape. The pinned key manager creates these in the Certificate namespace and deletes them directly after issuance. Its guarded CREATE is permitted only for that principal/profile/class; other principals cannot set the reserved marker, malformed marker values reject, and explicit retry names must satisfy the same prefix/owner constraints. Every UPDATE that adds/removes the reserved marker or changes a temporary object's identity/owner/class is denied, including an otherwise permitted renewal update; the temporary-key profile itself grants no UPDATE. DELETE is allowed only to that enrolled principal for an object satisfying the protected temporary class. This uses actual oldObject/class checks and does not require cert-manager to become a provisioner or submit a retirement ticket/UID-delete option.

This is an issuer workspace exception, not deletion authority for credentials. Preparation, approval, every hold acquisition and metadata registration for use reject any Secret carrying the reserved marker; temporary keys can never become active, abort-source or other held dependencies. Reclassification of a held target is denied. Before initially enabling or changing the class exception, verification requires all pre-existing matching objects to have proven creator provenance or be removed through scoped zero-hold cleanup; unknown labelled objects block enabling the exception. Guarded CREATE plus immutable classification establishes provenance thereafter. The infrastructure-enrolled issuer profile may enable this scratch class before initial issuance, granting no credential-use or target-update authority before normal dependency approval. An enrolled active issuer profile permits scratch CREATE/DELETE during normal maintenance, including a draining scope. Infrastructure controls issuance_enabled versus cleanup_only on that same envelope entry through verified scope changes. Retiring an issuer profile stops new scratch CREATE but retains cleanup-only DELETE for its already-created class until empty; if the renewer is unavailable, scoped metadata registration/retirement remains available. Non-cert-manager mutable issuance workspaces stay outside the managed namespaces. T32.3/T50.4 require initial issuance and repeated renewal with temporary-key deletion and no retained key copies, plus forged labels/owners, unauthorized principals, target reclassification and reference-to-temporary negatives. This requires testing the pinned cert-manager behavior, not assuming all versions fit the profile.

**Bounded SDS propagation.** TLSRenewalRuntime is separate operational state bound to the complete stable dependency_contract_digest (including reference/UID/profile/writers), not a registry/security revision or active-generation change. The same contract retains that state across plan/pin changes, so a new bundle version cannot reset an unfinished overlap. The supervisor first validates the current real Secret, then binds per-proxy handshake evidence to its profile and validated candidate, verifying the presented chain, hostname, algorithms/strength and validity as well as the leaf fingerprint. Persist at most the current and previous validated public certificate candidates (no private keys), their resourceVersions/validity bounds, a monotonic material_sequence and the first_new_seen_at/overlap_until. When a different valid leaf is first seen, overlap_until is fixed at first_new_seen_at + renewal_overlap_seconds, capped by the old certificate's profile-validity cutoff; validity always includes the profile's minimum remaining lifetime. Before that deadline proxies may serve either candidate only while both remain independently profile-valid and fresh complete evidence accounts for every traffic-eligible proxy. Matching evidence under that rule keeps the gate eligible and unchanged stream contexts usable; it performs no begin, pin switch, forced gate closure or terminal denial. This does not promise transport continuity or extend an existing lease.

Each sample records the actually served fingerprint and observation collection time. Re-reading metadata, ownership transfer or another Secret write cannot reset overlap_until, refresh an old sample, extend the 300s observation budget or add an unbounded accepted candidate set. Same-leaf rewrites do not start a new window. Material that fails validation is recorded as a failure, never added to the two accepted candidates or counted as a third leaf. A third distinct valid current Secret while propagation is incomplete cannot enlarge that set or start another overlap; it closes admission as awaiting_evidence until the full-convergence path below proves one current target. New proxies need their own fresh evidence. If material changes during collection, discard the inconsistent sample and retry within existing deadlines, without renewing leases from uncertainty. Missing polls use the ordinary <=300s observation rule within the earlier overlap/material-validity cutoffs; they do not establish a mismatch. Ordinary in-window convergence uses the same verified single-candidate transition as recovery below: after fresh complete current-candidate proof, CAS-advance material_sequence, set propagating→stable and clear previous_candidate/first_new_seen_at/overlap_until. The old candidate is retired immediately, not authorized until the old deadline. With current Secret B unchanged, a fresh proxy regression to retired A is material_mismatch/terminal even before that deadline. An old pre-convergence report fails its material_sequence/epoch/sequence check; it cannot reauthorize A or manufacture a new mismatch from stale evidence.

**TLS renewal failure classification and recovery.** TLSRenewalRuntime records verification_state=stable, propagating, awaiting_evidence or material_mismatch, with a safe last_failure_code. At overlap_until, lack of fresh complete convergence closes new requests/admissions with 503 and gives existing contexts temporary unavailable, no renewed lease and no closed_at. This applies only to an unfinished rotation and includes a missing observation or its still-authorized, profile-valid prior leaf; it never covers a candidate already retired by convergence; the deadline is not extended to keep authorizing it. Verified withdrawal plus fresh remainder evidence may establish convergence. A confirmed invalid/revoked/expired current Secret, missing/replaced reference, freshly observed invalid served certificate or served fingerprint matching neither the actual profile-valid current Secret nor a still-authorized prior candidate is material_mismatch: close immediately with terminal rechecks and no stale allowance. An incomplete or missing sample cannot downgrade or clear that established mismatch. Conversely, expiry of a historical sample/candidate without current served-material proof is an evidence cutoff, not proof that a proxy still serves that now-invalid material. The earlier ordinary observation, certificate-validity and stream-lease cutoffs always apply.

The recheck outcomes below describe the TLS gate only. Existing lease/session/context expiry, changed authorization and independent terminal checks retain precedence; unavailable cannot keep an expired context alive.

| TLS evidence/outcome | New application requests/admissions | Existing continuation recheck | Required next step |
| --- | --- | --- | --- |
| Valid old/new during unfinished propagation within the original overlap/evidence bounds | Eligible if all other gates pass | Ordinary bounded recheck | Fresh complete current-candidate convergence |
| Unfinished propagation lacks complete convergence at the cutoff, with no established material violation | 503; awaiting_evidence | Unavailable; no renewal or terminal closure | Collect complete fresh current-target proof; do not extend the old overlap |
| Confirmed invalid, revoked, expired, foreign or otherwise unaccounted material/reference | 503; material_mismatch | Terminal deny and closed_at | Correct material under the same approved contract, or obtain approval for a changed contract |
| Complete fresh current-target proof after a TLS-only closure | Reevaluate all gates | Only still-unexpired, unclosed contexts may continue | Atomic single-candidate verification reset below; no resurrection |

The current scoped owner submits full-convergence evidence through the existing `POST /internal/v1/route-bundles/{id}/observations`; it cannot request an arbitrary gate reset. The supervisor must validate the **current actual Secret** against the unchanged approved dependency contract and obtain a coherent, complete <=30s-fresh set showing every traffic-eligible proxy serving exactly that material and the approved gateway projection. Evidence binds the current contract/deployment/serving generation, owner epoch, increasing observation sequence and expected material_sequence; a racing Secret/scope/contract change requires recollection or new approval as appropriate. The service CAS-advances material_sequence, retains only that single validated candidate, clears previous/first_new_seen_at/overlap_until and the TLS failure, and records stable. This single-candidate transition completes ordinary propagating→stable as well as recovery after awaiting_evidence **or material_mismatch**, including corrected issuance, without a new preparation/approval/gateway_apply; it is verification of already-approved material semantics, not new write authority. It may bypass the overlap admission limit only for this one fully converged target while the gate is closed, never to accept an enlarged mixed set. Original sample collection times remain unchanged. Exact recovery retries are idempotent; once stable on that candidate, later samples are ordinary evidence refresh, not another recovery transition. Plan/pin changes and partial evidence cannot reset that state. Clearing the TLS blocker reevaluates every other gate/security/attempt condition: it cannot clear another mismatch, incident disable or applying/recovery_required hold. Closed or expired contexts remain closed/expired and require new admission.

Thus a 10:00 B renewal with overlap_until=10:02 that finishes on every proxy at 10:03 may reopen on that fresh complete proof. The 10:02 closure for valid nonconvergence/missing evidence was unavailable, not a manufactured security denial; only unexpired prior leases could survive. If B failed validation, it never occupied a candidate slot: a corrected valid C with complete current-proxy proof may replace the latched failure with a single stable C. Previously terminally denied contexts do not revive. A 10:00:30–10:02:30 observation gap likewise cannot itself produce terminal mismatch; when the earlier cutoff is reached, gate admission and return unavailable until fresh proof arrives. Neither recovery grants a 300s extension or makes an old sample fresh.

Input/plan digests, approval preconditions, registry-only equivalence, recovery_snapshot_digest and restore_pair compare the stable TLS dependency contract and revalidate current allowed material, not a historical leaf/resourceVersion. Journaled gateway-resource inventory/CAS checks remain mandatory; only permitted TLS material churn is excluded from those semantic preconditions. A successful permitted renewal neither changes expected_gateway_digest nor revokes contexts, and compensation cannot write an expired certificate back. Other protected routing/filter/TLS drift, live security vetoes and current certificate-revocation results remain independent terminal conditions. T32.3/T50.4/A58 require an app.example.com renewal with mixed old/new SDS delivery and no observer-induced outage, plus invalid material, expiry, replay/churn, nonconvergence and renewal-during-approved-plan/compensation cases. These are required integration results, not a claim that the selected adapter already passes them.

**Exact-mode Secret rotation is a reference change.** A supported exact-mode policy/backend credential is a frozen, versioned object, not an in-place renewable target. An independently authorized credential provisioner creates a new unreferenced Secret S2 under narrowly configured staging RBAC/admission while S1 remains live. The staging grant is create-only in an isolated namespace/versioned-name scope and cannot update/delete any active or retained dependency; it is not a tenant label or route-controller privilege. Freeze S2 data (immutable Secret where supported) **and metadata/resourceVersion** with admission/RBAC before preparation. Automated issuance may write to a separate unreferenced source outside the dedicated guarded namespaces, then the provisioner creates a complete frozen final version inside them, or provision each new version once at CREATE; it must not attach an in-place renewal/reconciliation controller to a pinned exact-mode target. No real payload enters Git, the SkyOAuth plan, public admin output or translator input. If safe staging cannot be isolated by the adapter's guard, require a separately authorized infrastructure provisioning step; never relax pinned-object protection.

Tenant client_admin prepares a gateway_apply version changing the reference from S1 to S2; the supervisor verifies S2's real material and binds its exact reference/UID/resourceVersion/material evidence before security_admin approves. The plan explicitly lists this credential-reference rotation and its ordinary origin-wide cookie-traffic/stream apply interruption for scheduling; registry_only or tls_renewal cannot silently substitute. Reject missing/invalid S2 before begin without disturbing S1. Rotate early enough that the forward/compensating schedule fits both credentials' validity: S1 remains unchanged, unrevoked, usable and admission-protected for every outstanding abort/restore obligation. The scoped controller applies **only gateway references**, then activates after fresh complete gateway/material evidence. On failure, compensation may restore the approved S1 reference only if it is still valid; otherwise remain closed for fresh authorized recovery, never waive expiry or reinstall bytes. Only after all holds release and the sealed, guard-acknowledged retirement protocol below authorizes deletion may the independent provisioner retire S1 under its separately granted infrastructure authority. In-place automatic renewal of an exact target remains denied; a changed/expired target is known drift, not an implicit renewal exception. T32.3/T50.4/A58 require successful staged rotation/interruption, harmless failed staging, retained-source rollback/retirement and expired-source recovery outcomes.

**Credential holds are explicit service state.** A global, nonsecret CredentialDependency record keys the actual cluster/namespace/name/**Secret UID**, with monotonic hold_generation and lifecycle_state=protected, retiring or retired. Typed CredentialDependencyHold rows track active_registry, active_deployment, applying_forward, abort_source, inherited_recovery and approved_pending uses across **all** bundles. Approve acquires the future-use/abort holds before its approval can execute; begin/activate/abort/supersede atomically transfer or add holds before releasing predecessors. An expired/revoked begun attempt keeps its unresolved abort/recovery holds: abort_until alone is not a release. A supersession inherits them until its verified outcome reconciles the obligations. Unbegun approval holds may release only when the service records that approval terminal (consumed, expired, revoked, superseded or invalidated); a later reapproval must reacquire holds/protection. Historical audit/artifact retention alone is not an executable hold. Reference state comes from the service's versions/approvals/attempts/journals, never a provisioner's assertion or a scan of the currently applying manifest.

The scoped admin bundle detail adds a bounded `credential_holds` page (with a scope/revision-bound next cursor) containing dependency ID/reference/UID/observed resourceVersion, lifecycle_state, global held flag, hold_generation, protection_status/guard_generation, retirement_operation_id/status and authorized hold reasons/owner IDs. Hold owners outside the reader's bundle/tenant are opaque additional_holds, never a false globally-unheld result. This exposes no Secret payload, journal or manifest. Instance security_admin enrolls a **CredentialProvisionerIdentity** at `/admin/v1/credential-provisioners`, binding its public mTLS identity, actual Kubernetes request principal and explicit cluster/Secret/bundle read scopes. It receives only scoped `GET /internal/v1/credential-dependencies` / `/{dependency}` and the metadata-registration/retirement-request rights below, no controller/operator/configuration authority. These reads provide the same nonsecret hold/protection status while the application gate is closed; a provisioner need not borrow client_admin or controller credentials. Enrollment grants no Kubernetes rights: infrastructure administration separately grants bounded staging creation and guarded deletion. Filter/cursor/foreign-reference reads cannot widen either scope. Its metadata-registration right below adds no use/approval or guard-management privilege.

**Scope registration and verification.** Instance security_admin uses `GET / POST / PATCH /admin/v1/credential-protection-scopes` to register a CredentialProtectionScope, with optimistic revision checks and audit. Its tuple binds cluster/API identity, exact dedicated namespace names/UIDs, guard_refs (Secret-policy/binding and parameter-mutation-policy/binding refs/UIDs/adapter-template digests), parameter_ref/UID/parameter_schema_digest, infrastructure-owned writer_envelope_ref/UID/digest and the designated registered controller identity/Kubernetes principal. verification_status and verified_registration_revision are service-owned. Any infrastructure_scope_uid in the installed parameters is the installer-owned envelope UID; the server-generated scope registry ID is linked by registration, avoiding a pre-installation ID dependency. Infrastructure administration installs those Kubernetes objects and RBAC first; registration grants no Kubernetes permission. RouteControllerIdentity.credential_protection_scopes is a read-only projection of these assignments, not another writable enrollment path. Public controller identity alone confers no protect_ack/release_ack authority.

The designated controller discovers even empty/unverified scope work through private `GET /internal/v1/credential-protection-scopes` / `/{scope}` and may claim a fenced epoch while verification is pending. Through its credentialed control-plane verifier (outside the translator helper/public auth image), the service requires authenticated reads from the pinned cluster API: namespace UIDs/coverage, the actual policy/binding and its paramRef, fail-closed settings (failurePolicy=Fail, validationActions=[Deny], parameterNotFoundAction=Deny), parameter UID/schema, enforced mutation guard and designated Kubernetes writer/envelope must match the registered adapter tuple. The service validates that evidence against the pending registration/revision and configured cluster identity, not a caller-selected hash or ready flag. `verify_scope` on the scoped transitions endpoint records the verified tuple; protect_ack/release_ack additionally bind that verified registration revision, current identity/epoch/sequence/generation and live object UID/resourceVersion/digest. Missing/wrong bindings, namespace coverage, parameter UID, mutation guard or principal leave the scope not ready. Controller/principal or compatible policy-envelope changes use revision-checked PATCH **on the same scope ID**. It records an immutable credential_scope_change AdministrativeOperation/pending_change_operation_id; new adoption pauses, but the current verified registration, maintenance owner and retained guard proofs stay authoritative while the candidate is verified. GET exposes pending versus current state. The candidate may read its proposal and submit verify_scope bound to pending_change_operation_id and expected baseline revision without a current writer epoch; this grants no protect/release rights and it may not claim the current writer epoch before successful handoff; first enrollment with no baseline may still claim for verification.

Commit only after authenticated candidate installation verification and safe owner handoff. The rollout must keep namespace-wide denial in force throughout and preserve compatible exceptions for every held UID. The verifier checks the candidate against the held contracts, and the service rechecks that comparison at cutover under the same serialization as hold changes. A candidate that cannot establish continuous compatible coverage cannot commit. At cutover advance registration_revision and ownership/generation counters without resetting them. Requests using the prior owner epoch and acknowledgements for the prior registration revision reject after cutover. New adoption and grants require current-revision evidence. The cutover leaves the service-owned proofs on continuously protected holds intact. A rejected/failed candidate leaves the baseline intact; ending the pending change requires fresh baseline verification before adoption resumes. Reject a migration that removes the only functioning maintenance authority before its replacement is verified. Ordinary observations do not change the registration. Namespace ownership, parameter UID and binding identities stay fixed for the scope lifetime; a structural replacement uses drain/decommission, not a second overlapping POST or an implicit live reparenting.

**Writer envelope versus live entries.** The infrastructure-owned envelope fixes allowed reconciler principals, allowed TLS-renewer principals/Secret scopes/field sets and provisioning/deletion boundaries. The reconciler has no RBAC to change that object, policy/binding, namespace selection or parameter schema, or to delete/recreate the live parameter object. Separate live `renewal_entries` and sealed `retirement_entries` reside in the delegated parameter object. The reconciler may add/change/remove only service-authored entries within the envelope; a new renewal grant needs the approved profile and compatible holds, while sealing retirement removes that UID's live renewal entry. Thus “remove obsolete writer exceptions” edits a live entry, not the infrastructure envelope. The installed parameter-mutation guard enforces the envelope, fixed scope/parameter identity and nondecreasing owner_epoch/generation: lower counters reject even after a fresh resourceVersion read; equal counters require identical spec. Each actual spec change uses a higher service-issued generation. Workers must use their service intent's counters, not copy a newer owner's counters from rereading Kubernetes. Conflicting shared-UID exact/renewable grants reject; no live writer exception may defeat any held dependency's contract.

**Guard coverage and unreferenced staging cleanup.** The installed Secret guard denies UPDATE/DELETE for **every Secret in the exact dedicated credential namespaces**, whether or not its UID appears in CredentialDependency or a parameter list. Omission from live entries never unprotects an object. This is not a cluster-wide guard or an opt-in label/UID deny-list; unrelated namespaces stay outside it. Creation remains separately constrained by infrastructure staging RBAC/envelope. Create managed-namespace objects fully populated, with metadata and immutable-data flag finalized where applicable; mutable issuance workspaces live outside this guarded scope except the pinned temporary-key lifecycle above, and no general untracked UPDATE exception exists; namespaces that cannot be isolated for this contract are unsupported, not silently guarded by a narrower reading. Missing/invalid parameters deny. Exceptions are approved credential renewal updates, the non-referenceable temporary-key CREATE/DELETE class, and zero-hold-sealed UID/RV/principal retirement deletes; the temporary class cannot qualify as a held credential. Per-UID protect_ack confirms the actual UID is covered by this namespace-wide guard under the verified registration revision with compatible exceptions; it does not create a separate UID deny-list entry.

An unreferenced or invalid failed-stage S2 is not stranded: its enrolled scoped provisioner calls `POST /internal/v1/credential-dependencies` with reference/UID/resourceVersion and an idempotency key to register cleanup metadata. The service/verifier confirms actual object metadata and registered namespace/scope, atomically upserts the global UID record and reconciles authoritative references from all versions/approvals/attempts/journals. The caller cannot assert zero holds; an existing held/retiring/retired record is returned unchanged, never overwritten/unsealed. Unknown reference/restore state stays quarantined. A genuinely unused S2 becomes protected with zero holds and may use the ordinary retirement seal/guard acknowledgement/UID-precondition DELETE path. Metadata registration requires neither valid credential bytes nor approval to use the object, so bad staging can be cleaned without an infrastructure bypass. Raced references acquire holds through the same global row lock or reject after sealing; absent inventory alone never licenses deletion.

**Protection is projected to admission, not looked up by CEL.** One fenced M3 reconciler per verified scope updates only the delegated live parameters from service intents. The namespace-wide default denial remains even if a stale replica omits a newly held UID. Cached lower epoch/generation writes also fail the Kubernetes mutation guard; a resourceVersion reread is not authority to publish a stale snapshot. Any previously issued retirement entry can name only an irreversibly sealed UID, which cannot later acquire holds. Only the designated reconciler and trusted infrastructure administrators can write the delegated object, with the above admission constraints on the reconciler. It reads service-authored protection/retirement intents via the scoped credential-dependencies API; `POST /internal/v1/credential-protection-scopes/{scope}/transitions` allocates claim epochs and accepts current-owner protect_ack/release_ack/delete_observed results bound to increasing sequence, intended generation and observed parameter UID/resourceVersion/digest. verify_scope uses the assigned initial owner or explicitly assigned pending candidate as above; decommission_observed uses the separately defined absence proof. Claims alone cannot authorize a release. New credential adoption requires service-acquired holds **and confirmed installed protection** before an approval becomes executable or forward begin succeeds; protect_pending or unknown new-adoption protection blocks those steps. Continuously held uses may retain protection as specified below. An approval request may remain protection_pending while the reconciler installs the guard; successful protect_ack finalizes it only after rechecking authority/plan/security conditions, and terminal failure releases only that unbegun request's hold. Acknowledgement covers the guarded UID and verified policy/binding/parameter tuple. Fresh scope/projection readiness is required when a UID gains a new consumer/profile use hold, including new adoption at approval/forward begin.

**Retained guard proof.** After verified coverage, the service records retained_guard_proof on the acquired hold, binding the stable scope ID, cluster identity, namespace UID, Secret UID, consumer and dependency-contract digest to continued namespace-wide denial with compatible exceptions. The proof remains valid across registration revisions while that coverage continues. A protection_pending hold without a finalized proof cannot use this carry rule. Abort, complete_abort, already-begun activation and supersede inheritance may carry the proof while the same UID, consumer and contract stay continuously held during a pending PATCH, after any verified same-ID cutover preserving that coverage, and during a draining status or protection-reconciler outage. These transfers need no new protection-reconciler lease, registration verification or parameter-digest refresh. Hold transfer adds before releasing. A zero-hold gap, new UID/consumer or widened contract requires fresh adoption. Known guard removal or loss of compatible protection invalidates the proof; a repaired guard requires freshly verified coverage before the hold can carry again. A changed UID/namespace cannot reuse the proof. Credential material, bundle-owner/epoch, the actor/approval/security authority each step requires (for compensation, controller scope and an unrevoked approval; OQ-GW-9) and fresh completion observations remain mandatory. This narrows the protection check, not compensation authority or abort_until. Retirement or a new writer/delete grant still requires its live verified guard acknowledgement. Where protection is already confirmed it can be retained; no hold transfer temporarily unprotects its source. Guard parameters default to deny when absent/invalid and never infer release from an object label, expired approval or stale list. TLS-renewer updates retain only their previously approved exception; they cannot delete a held Secret.

**Exclusive scope ownership and drain.** Reserve (cluster_id, namespace UID) and (cluster_id, parameter UID) uniquely for each registered scope whose guard is installed or not yet proven removed, including unverified, disabled, migration-pending and decommissioning scopes. Registration/PATCH checks the reservations atomically; live policy verification also enumerates matching Secret bindings and reports guard_conflict for an additional overlapping guard, including an unregistered one. A known conflict blocks adoption, new renewal grants and delete_authorized; infrastructure removes the conflicting installation. If a conflicting binding appears after acknowledgement, a fresh denial/verification clears that readiness/authorization, records guard_conflict and keeps the UID sealed; do not churn retirement tickets against another binding's denial. Cross-plane verification does not promise atomicity with later infrastructure changes. Omission or stale state never frees a reservation. CredentialDependency.guard_scope_id is assigned from this unique namespace owner at metadata registration/first hold and stays fixed for that Secret UID. Controller migration PATCH keeps it unchanged. A source moved to a different namespace is a new UID/reference under the existing approved rotation rules, not reassignment of an existing held UID.

status=disabled means draining new credential adoption, not revoking the installed protection or maintenance identities. It denies new consumers/profiles/UID use holds and new forward adoption, but keeps claim/verify_scope, existing-profile renewal and temporary-key cleanup, existing-held protect acknowledgements, abort/completion/inherited recovery, zero-use metadata registration, retirement/release_ack and delete_observed available under the current verified maintenance registration. Recovery or a rotation moving away may carry existing source holds; any newly adopted replacement needs a separately enabled/ready scope. Fresh administrative approvals and all ordinary actor/security checks still apply; maintenance cannot add consumers or widen profiles. Re-enable by PATCH requires fresh verification for adoption. Scope disable alone does not disable a controller/provisioner identity; explicit identity or material revocation remains an independent veto. Actual outages/permission withdrawal may delay maintenance, but a status bit alone cannot strand failed staging or a zero-hold retirement.

To remove a scope, first drain all consumers, unbegun approvals/attempt obligations, outstanding retirements and temporary/staged Secrets, and quiesce issuance/staging creation. security_admin PATCHes disabled→decommissioning with expected revision; the service checks no remaining uses/obligations/inventory and authenticates that creation is quiesced in the installed envelope/RBAC, then records credential_scope_decommission, permanently blocking new adoption/re-enable while retaining reservations and maintenance discovery. Only then does infrastructure remove that scope's exact matching bindings and delegated parameter object. decommission_observed on the scoped transitions API verifies authenticated absence of those old objects and no remaining scope uses/inventory before recording retired and releasing namespace/parameter reservations. Absence/cleanup acknowledgements are valid maintenance actions against the retained scope tuple, not requests to pretend a missing guard is ready. Unknown removal/conflict keeps decommissioning, not reusable. Old scope/UID tombstones remain; a replacement scope registers/verifies fresh installation after release, and new dependencies get that new ID. A disabled scope is never treated as an unreserved namespace or a new empty scope.

**Retirement is a sealed operation.** The scoped provisioner requests `POST /internal/v1/credential-dependencies/{dependency}/retirements` with expected UID/resourceVersion, hold_generation and a reason/idempotency key. The service locks the global dependency row, verifies **no hold from any bundle** and records an audited AdministrativeOperation(kind=credential_retirement) that changes protected→retiring. A held or stale/unknown dependency rejects without changing protection. Retiring seals that UID: every new hold/approval/use rejects, even while a guard update or delete is pending. A read showing held=false is not delete permission. Only this recorded operation may cause the protection reconciler to install a DELETE exception for that **UID, resourceVersion and enrolled Kubernetes principal** in the exact guard generation; it first removes any obsolete writer exception for that UID. Before that service-authorized rule is installed, admission denies deletion. The provisioner must wait for matching release_ack/status=delete_authorized before attempting DELETE; awaiting_guard is not a usable client authorization. The rule can reach admission before its acknowledgement reaches the service, but it always follows the recorded zero-hold seal. The acknowledgement reports installed readiness rather than implying an atomic database/Kubernetes commit. There is no broad namespace unprotect or bearer authorization hidden in a status field.

The independent provisioner then performs Kubernetes DELETE with UID **and** resourceVersion preconditions under its separately granted RBAC. CEL evaluates that exact installed exception; it need not traverse the service database. A raced resourceVersion or failed/unknown delete result requires fresh metadata and service-authorized retry, never deletion by name alone. An exact idempotency retry returns the recorded operation. For an already retiring UID, a new request/key may authorize a replacement UID/RV-bound attempt at a new guard generation after rechecking zero holds and current scope; the UID stays sealed throughout. A changed payload under the old idempotency key rejects. A retired UID returns its recorded outcome, not another delete. The fenced reconciler confirms the old UID absent before recording retired and removing the exception; transport failure is not absence. Exact retries are idempotent. Once retiring is recorded the UID is never reopened for new holds, including after a worker crash or unused authorization; a new consumer must use a new staged UID. Tombstones and UID-bound exceptions prevent a late delete from harming a same-name replacement. Retiring uncertainty keeps the seal/protection rather than guessing success. After restore, reconcile hold state, retirement seals and installed guards before dependency readiness; unresolved fence history remains quarantined. Thus S1 in abort_required or recovery_required, or held by an approved unbegun recovery, cannot be retired merely because S2 appears in an applying version. T14.9/T32.3/T50.4/A58 test scope overlap/duplicate parameter rejection, pending PATCH and committed same-ID cutover with retained-source compensation and supersede inheritance, disabled maintenance/decommission, temporary-key cleanup, wrong bindings/UIDs/identities/envelopes, stale R1 writes, failed-S2 registration/cleanup, visible holds and safe final release.

**Protected-scope projection.** Compute the same versioned `P(configuration, protected_scope)` on prepared xDS and observed active configuration. Include filter chains and virtual-host selection capable of serving the protected listener/SNI/authority, including intersecting exact/wildcard/catch-all candidates and their relevant precedence. Include all routes/authentication classes on the protected host, their reachable clusters/discovery selectors/peer identities, and shared listener/HCM/TLS/normalization settings on which they depend. For HTTP filters, project the **ordered effective filter chain and resolved configuration for each protected route**, not the undifferentiated global HCM filter list. Request Cookie/CSRF removal, response Set-Cookie removal, auth exemptions and filter ordering are security-relevant. Exclude only provably disjoint virtual hosts/routes/clusters and documented nonsemantic noise; do not hash the entire shared RouteConfiguration simply because it contains the protected host. A route change solely for an unenrolled b.example.com on that listener must leave app.example.com's projection and active evidence eligibility unchanged. A wildcard overlap, protected receiver/auth change or shared listener security change must change the projection or reject preparation. Ambiguous/unsupported dependency reachability fails closed, never silently disappears from the digest. Disjoint edits do not by themselves change the protected serving-set generation or expire its observations. An Accepted condition, manifest hash or caller-selected dump is not deployed evidence.

A filter introduced for an unenrolled host may be excluded only when the pinned adapter has explicit, tested semantics proving it disabled/inert on **every** protected request path, including public, auth and fallback routes. Resolve default disabling plus all supported RouteConfiguration/virtual-host/route/backend overrides and request-dependent enablement; a default disabled flag alone is insufficient. Exclude only its exclusively unreachable configuration/clusters; retain dependencies shared with any effective protected filter. Preserve order and configuration of all effective filters. Unknown/custom filters, ambiguous overrides, global security effects or unprovable request-dependent activation must remain protected dependencies or be rejected before apply. Disabling a previously effective mandatory auth filter changes the projection and is not an irrelevant-filter exclusion.

T50.4 requires a b.example.com-only SecurityPolicy addition/removal on the shared listener, as well as a route-only edit, to leave app.example.com's digest/eligibility unchanged when the added filter is proven inert there. An override enabling it on a protected route, changed effective-filter ordering or shared security configuration must change the digest or be rejected by admission. A policy targeting an unenrolled route is not automatically outside admission scope: any dependency not provably isolated is guarded as a shared change. This avoids observer-induced denial for verified irrelevant filters; it does **not** guarantee transport continuity. A listener/HCM update can still drain Envoy connections even when the protected authorization projection is unchanged, so ordinary bounded reconnect remains necessary. The supported Envoy Gateway translation/filter combination requires real integration fixtures, not an assumption that every SecurityPolicy uses one implementation.

**Observation loss is not an observed mismatch.** Watch configuration/proxy membership and poll each traffic-eligible proxy at least every 10 seconds. Mark observations stale and alert **30 seconds** after sample collection start (OQ-LT-9), but retain a fully verified deployment for at most **300 seconds from sample collection start** while deployment_version_id and the protected serving-set generation are unchanged, the current registry version is verified deployment-equivalent, no gateway apply or known mismatch exists, and independent session/policy checks pass. Registry-only activation preserves rather than resets these deadlines. This is not a session, policy or database fail-open rule. Network delay, controller restart and failed polls never advance sample ages. New proxies have no last-known-good allowance and stay outside protected readiness until verified. One unobservable serving proxy eventually gates its affected bundles; removing it from the required set needs verified withdrawal/draining followed by verification of the remainder. A 40-second controller reschedule can preserve an unchanged deployment, but five minutes of unobservability cannot.

**During gateway apply or compensation.** Begin closes the entire affected origin bundle to new cookie-authenticated application requests and continuation admissions; return **503 `route_configuration_unavailable` with bounded Retry-After** (Connect `unavailable`) throughout applying, abort_required, aborting and recovery_required, as for an exhausted observation budget or no verified deployment. This is not 401/403 or a login redirect. An established context whose pinned origin/route versions and authorization/security dependencies are unchanged in the applying version (or in the recorded abort source while compensating) receives temporary `unavailable`, not terminal denial: no renewal and no closed_at, with retries allowed only until its existing lease deadline. A changed/removed dependency, security disable or other revocation is terminal; abort or re-enable cannot resurrect it. Only differences accounted for by the approved forward/abort plan and write journal under the closed gate are transitional, not unsolicited drift; out-of-plan mismatch remains terminal. Registry-only activation follows its separate no-write path above. A real gateway apply, incident recovery or compensating abort can therefore interrupt every cookie stream on the origin if the apply-and-observe cycle exceeds its lease, even for an unchanged route; schedule accordingly.

Transient observation/store/transport failure likewise grants no new lease and leaves the existing cutoff unchanged; auth-service transport failures map explicitly to fail-closed 503. Reopening after a real apply requires fresh complete evidence. Assertions and leases are capped by remaining observation validity and all session/policy bounds, never another stacked window. Fixed `/_skyoauth/session` and `/_skyoauth/logout` routing, native `/oauth/revoke`, verified back-channel logout and independent session-revocation/security-disable operations do not depend on the application route gate. They retain their own origin, credential, CSRF/signature and store checks; the session endpoint may supply only browser-safe metadata/CSRF needed for cleanup, never forwarding authority. `/_skyoauth/login` and `/_skyoauth/callback` are likewise not subject to the application route gate: while it is closed they are served only if the origin has an active pinned ApplicationOriginVersion and its parent is security-enabled, otherwise they deny before any redirect; their own checks still apply (OQ-API-1). The controller must preserve those fixed SkyOAuth routes, including login and callback, during an application apply. Gate bypass for cleanup is not permission to mint an application assertion or ignore infrastructure failure. No instantaneous detection or uninterrupted-availability guarantee is made.

**Known mismatch is not stale evidence.** When a current, authenticated observation records an out-of-plan digest mismatch, the service immediately closes the affected bundle gate, records/alerts the mismatch and rejects new cookie application requests/admissions with 503 route_configuration_unavailable. Do not wait for 30-second staleness or apply the 300-second last-known-good allowance. A continuation recheck returns terminal deny and closes the context, not unavailable; the backend stops on that result, while an operation already authorized before detection retains only its documented remaining bound. Late/replayed matching samples cannot reopen the gate. Recovery requires reconciled approved configuration and a complete fresh matching set under the current owner/deployment generation; closed contexts are never revived. For TLS-only material failure, the unchanged-contract full-convergence recovery above is that approved reconciliation and needs no gateway_apply; it cannot excuse routing/configuration drift, a changed dependency contract or a separate security/attempt hold. Validly journaled apply/abort transitions are the separate case above, not a way to excuse arbitrary drift. Observation alone cannot activate an unapproved version or one with wrong-mode, expired, revoked or stale approval.

T14.9 owns M1b versioned schema, pending-preparation/result/approval/list/read contracts and service-validated state transitions. T32.3 delivers M3 isolated translator preparation before approval, controller/listener enforcement, scoped observation and both activation paths; M1b must not claim a deployable translated plan without that worker. T50.4 packages/audits the actual mechanism and tests shared-listener isolation, incident recovery, preparation failures, registry-only activation and full-apply interruption. Kubernetes/Envoy administrators able to replace the data plane or remove guards are outside this guarantee. Every alternate gateway adapter, including ForwardAuth on Kubernetes, needs its own equivalent reviewed deployment/observation and all-route credential-removal contract; platform location does not imply Envoy support.

## 5. Identity and credential flows

### 5.1 Browser login, login CSRF and opaque session

1. Resolve the registered `ApplicationOrigin`, its tenant and active provider. Validate the relative return location from that registration.
2. Generate state, nonce, PKCE S256 and a server-generated browser-flow secret. Set short-lived `__Host-skyoauth_login` (Secure; HttpOnly; Path=/; SameSite=Lax; no Domain); store only its keyed hash in a `BrowserFlowBinding`. Bind the OIDC transaction to that hash, flow kind, origin, tenant, provider/epoch, exact callback and return path. The flow cookie, BrowserFlowBinding and OIDCTransaction default to 10 minutes with a 15-minute ceiling (OQ-LT-1).
3. Redirect to the fixed upstream authorization endpoint. The baseline uses a top-level GET/query callback; a provider requiring another response mode needs an explicit tested profile, not a weaker cookie fallback.
4. At `/_skyoauth/callback`, require **both** correct one-time state and the initiating browser's matching flow cookie, exact registered origin/callback, provider epoch, PKCE, the RFC 9207 authorization-response `iss` when the provider advertises it (OQ-TM-4) and verified ID-token issuer/audience/signature/nonce/time/authentication requirements. A state or transaction ID alone is not browser authentication. Wrong or missing browser binding denies without creating, replacing or linking a session.
5. Resolve the verified provider-subject link, applying §5.1.1 when none exists; never silently create a replacement for an unlinked migrated account. Create a `HumanAuthentication` record and a fresh CSPRNG opaque session ticket; persist only its keyed hash, origin/tenant/principal/authentication reference, provider/subject/optional sid, idle/absolute expiry and CSRF verifier. Atomically consume the login transaction and expire its flow binding. Starting a new flow for the same flow-cookie slot invalidates the old one; stale tabs restart rather than bypass binding.
6. Set `__Host-skyoauth_session` with Secure; HttpOnly; Path=/; SameSite=Lax, no Domain. It is not an OAuth token. `GET /_skyoauth/session` returns only safe principal/session metadata and a session-bound CSRF token with no-store.
7. Unsafe cookie calls, including Connect unary POST and logout, require exact Origin plus CSRF in `X-SkyOAuth-CSRF`. Local logout revokes the session/authentication context. Optional back-channel logout verifies signature/issuer/audience/events/time/replay and uses indexed provider/subject/sid selectors. The gateway consumes browser credentials before application forwarding as specified in §4.

A session is usable only before **both** idle (default 8 hours, ceiling 24 hours) and absolute (default 24 hours, ceiling 7 days; OQ-LT-2) deadlines, on its registered origin/tenant, with live principal/authentication/provider epoch. Throttled last-seen writes must not revive an expired session or extend absolute lifetime; document bounded early idle expiry from coalescing. Login flow, native request, authorization code and session lifetimes are instance-configurable within their ceilings (OQ-LT-1, OQ-LT-2). Verified account linking also requires an initiating-browser-bound transaction and explicit proof/approval; never email-only merging or attacker-supplied callback account reassignment. Linking to an existing principal uses a browser-bound transaction proving both identities and the OQ-TM-7 second approval; operator enrollment creates only new principals and is operator-asserted and audited. If the old IdP is unavailable during migration, an operator-asserted link to an existing principal is allowed only with the OQ-TM-7 approval and user notification (OQ-TM-6).

Login CSRF, callback injection, redirect URI confusion, OIDC mix-up, session fixation and identity-linking confusion are explicit release threats/tests. PKCE/state/nonce are not sufficient when their transaction is not bound to the initiating browser; see RFC 9700 §§2.1 and 4.7.

Default: discard upstream access/refresh tokens after login. An encrypted server-side provider-token vault is an explicit opt-in for authorized upstream operations; tokens never reach SPA JavaScript. Do not rotate the browser cookie on every ext_authz check or couple normal session lifetime to upstream token rotation.

### 5.1.1 First login and migration enrollment hold

A versioned tenant `HumanEnrollmentPolicy` has two v0.1 modes: **`preprovisioned` (default)** denies an authenticated but unlinked subject with a non-enumerating `enrollment_required` result; **`auto_create` (explicit operator opt-in)** atomically creates a fresh `usr_*` principal and verified link for the exact active provider/issuer/subject after the same full OIDC/browser checks. Concurrent first logins use a unique tenant/provider/issuer/subject constraint and converge on one principal. This policy applies to both browser and native login. It never matches by email, copies another user's membership, or creates operator authority. New principals start with **no backend resource privileges**; application onboarding/RBAC is separate. Existing disabled links/principals deny rather than triggering a replacement create. Invitation workflows are deferred; operators can preprovision through the existing verified-enrollment path, which creates only new principals (OQ-TM-6).

`TenantLoginState.enrollment_hold` overrides auto_create. A provider switch or rollback sets the hold atomically with epoch invalidation; every callback rechecks the current hold/policy/generation before creating any principal. Unmatched replacement-provider subjects are denied while the hold is set, not silently assigned new IDs. Existing verified links continue normally after reauthentication. The deliberate compromise transition (§7.3) advances auth_generation without a provider change (OQ-TM-14). Initial activation from null may explicitly enable auto_create only as an approved fresh-install choice in its plan.

After linkage reconciliation, `provider_admin` may explicitly resume enrollment through a revision-checked, audited operation bound to the current provider and login generation; neither elapsed time, import, policy edit, restart nor rollback clears the hold. The confirmation warns that resuming permits genuinely unlinked subjects to become **new** users, not to inherit old identities. Existing-user continuity must be verified before resuming; unknown equivalence cannot be inferred from claims. Changing policy/hold never changes WIF or role assignments. This avoids mandatory per-user mTLS enrollment for opted-in public apps without guessing account continuity during migration.

### 5.2 Native OAuth and issuer-origin confirmation

The Rust CLI is a public client of SkyOAuth, not Zitadel. It uses stable issuer `/oauth/authorize` and `/oauth/token`, a registered generated `client_id`, S256 PKCE and an IP-loopback redirect. Following RFC 8252 §7.3, a registered redirect rule fixes scheme `http`, the IP literal (`127.0.0.1` and/or `[::1]`) and the path; the port varies per request and is bound exactly per transaction; `localhost` is rejected (OQ-TM-5). Client ID identifies configuration/tenant but does not authenticate a local process. **Bounded rotating SkyOAuth refresh credentials are required in M4**, so normal commands renew short-lived access without repeated browser approval; they are never upstream refresh tokens or static API keys (§5.2.2).

**Issuer-origin browser flow:** `/oauth/authorize` resolves the globally unique registered client and its tenant, validates redirect/audience/scopes against registration and audience assignment, creates `OAuthAuthorizationRequest`, and sets `__Host-skyoauth_native` on the **issuer origin** with the same secure host-only attributes and a short transaction lifetime (default 10 minutes, ceiling 15 minutes; OQ-LT-1). Its keyed hash binds the native request and upstream OIDC transaction. Upstream authentication returns to the fixed **issuer `/oauth/callback`**, registered on that tenant's HumanProvider, not the app-origin callback. The issuer callback checks the RFC 9207 authorization-response `iss` when the provider advertises it; otherwise that provider uses its own per-provider callback path on the issuer (OQ-TM-4). Each such path is an exact registered issuer route with the same cookie exemption and checks as `/oauth/callback` (§4); without that exemption the gateway would strip the native flow cookie before the binding check. The server generates the path in the reserved form `/oauth/callback/{provider_id}`; it is never tenant-supplied, and the validator rejects any collision with another SkyOAuth endpoint or provider path. Adding it is a system-bundle apply that must finish before the provider is tested or used for native login. Native and app flow cookies/transaction kinds are never interchangeable.

The issuer callback checks state, the native flow cookie, expected issuer/client/callback, PKCE/nonce, epoch and ID token before storing the verified human principal/authentication on the native request. Rotate the issuer-local flow secret and bind the replacement to that request before confirmation; rotation keeps the request's original expires_at and never extends it (OQ-LT-1). `/oauth/confirm` requires this bound cookie and completed server-side authentication; a transaction ID, app cookie, URL principal or live upstream SSO alone cannot approve a request. A new native start invalidates the previous native cookie slot; stale/conflicting tabs show an explicit superseded-login error and require a deliberate restart. They must not silently approve or redirect to the replacement flow. The comparison value below lets the user distinguish concurrent requests.

**Every new loopback authorization requires explicit SkyOAuth approval.** Show the registered client name, account, audience/scopes, approved native-session duration, exact loopback destination and §5.2.1 comparison value, with approve/deny and a warning that the public client ID does not prove the local program's identity. The confirmation POST requires exact issuer Origin, CSRF, anti-framing, matching rotated flow binding, request digest, principal and unexpired provider epoch. Bind the resulting one-time code (default 60 seconds, ceiling 5 minutes; OQ-LT-1) to the exact client/redirect/PKCE/audience/scopes/authentication. Only after approval redirect that SkyOAuth code to the loopback listener. Denial/expiry creates no code; consume confirmation state and clear its cookie. Prior consent or existing SSO never auto-approves a new request (RFC 8252 §8.6).

The native client separately checks its own OAuth state and exact callback path, redeems using its PKCE verifier, and closes the loopback listener after success/cancellation/timeout. Codes are transactional and single-use across replicas. Device flow is conditional and requires user-code verification plus equivalent explicit approval/abuse controls; it cannot bypass this interaction. Do not claim native compatibility until conformance passes.

### 5.2.1 Match the browser approval to the initiating CLI

Before opening the system browser, the Rust crate exposes an immutable confirmation descriptor; the reference CLI prints its exact loopback URI/port and a grouped comparison value and instructs the user to compare **both** with the SkyOAuth page. Library consumers must display the descriptor through their own trusted UI. The page derives the value from its stored validated transaction; it does not echo a caller-supplied display-code parameter. Approval requires an explicit “matches my CLI” acknowledgement in addition to the normal CSRF-protected action. A mismatching/superseded request must be denied and restarted, not worked around by approving another tab.

State is an independent CSPRNG value with at least 128 bits of entropy. Display the first 10 digest bytes as unpadded uppercase RFC 4648 Base32, grouped 4-4-4-4. Both implementations use shared test vectors. The random PKCE verifier stays secret and is never displayed, transmitted in the authorization URL or used as the display value itself.

### 5.2.2 Required native renewal, not long-lived access JWTs

A successful approved native code exchange issues an access JWT capped at **300 seconds** and a rotating SkyOAuth refresh credential tied to one `CLIRefreshFamily`: tenant, actual OAuth client, principal, HumanAuthentication/provider epochs, one audience and the approved scope ceiling. Default family limits remain **12 hours absolute and 1 hour idle**. An audited `client_admin` HumanAccessPolicy change may opt into at most **7 days absolute and 24 hours idle**, within any stricter instance/assurance limits; require positive durations and idle <= absolute. These are proposed product limits, not OAuth-mandated durations. Snapshot both limits at explicit browser approval: increases apply only to newly approved families, never to an existing family or HumanAuthentication. A tightening transaction permanently narrows affected family limits or revokes affected families; the next refresh/live check enforces it. Elapsed or revoked state is never resurrected by a later increase. Neither rotation nor refresh resets the absolute deadline or auth_time. The native HumanAuthentication lifetime is capped by that family and any stricter authentication requirement, not by the first access JWT's 300-second expiry. There is at most one family per native authentication/client/audience tuple; live checks resolve that unique family from the signed authentication reference, actual client_id and audience, and deny if it is absent or revoked. The browser displays these limits at initial approval. Refresh continues that approved authorization and is not a new loopback transaction needing confirmation.

The form request uses standard `grant_type=refresh_token`, `refresh_token`, `client_id` and optional narrowing `scope` at the stable `/oauth/token`. Project-specific **`skyoauth_refresh_request_id` is optional** and enables only bounded retry recovery. When present it must be an independent 256-bit CSPRNG value encoded as unpadded base64url; empty, malformed or duplicate values are `invalid_request`, not silent opt-out. It is retry correlation, not client authentication or a standard OAuth parameter. Reject audience/resource/subject overrides, duplicate parameters and unknown clients. Each successful refresh atomically consumes the old credential and returns one successor plus a fresh bounded access token. Recheck current client, audience assignment, principal, HumanAccessPolicy, authentication/epochs and family deadlines/revocation; never exceed original approved scopes. Omitted scope retains the previous scope set only if still allowed; explicit narrowing can succeed, but changed authentication requirements or invalid/revoked state requires reauthentication. No refresh extends upstream identity assurance indefinitely. See RFC 6749 §6 and RFC 9700 §4.14.

**Standard-client path:** without the request ID, perform ordinary one-time rotation with no retry receipt or response envelope. Reuse of that consumed credential revokes the family, including a retry that adds an ID after the fact. A lost response can therefore require a new interactive authorization. Generic OAuth refresh clients need no private parameter to renew, but receive no idempotent-retry guarantee. Supplying an ID selects the extension for that attempt; omitting/changing it on replay cannot downgrade an extension attempt into a fresh plain rotation.

**Bounded exact retry:** when an ID is supplied, the first successful refresh atomically consumes the old credential, creates exactly one successor and stores a retry receipt on that consumed credential. The receipt binds keyed hashes of the request ID and canonical request (actual client, parent generation and requested scope, distinguishing omission from an explicit set), the issued policy revision, successor generation, and a non-sliding **30-second** deadline from commit. Store the already-issued access/refresh credential values only in a short-lived authenticated-encrypted response envelope, with associated data binding that receipt and a separate protected encryption-key reference. Keep the key outside the database and separate from signing keys; no plaintext response cache, token logs or ordinary export. Purge the envelope at expiry; retain consumed-token/replay metadata for the family's remaining lifetime. This is a narrow M4 retry record, not a general upstream-token vault.

Within that window an exact same-token/request-ID/payload retry may return the **same credential values** only while the successor is still current and unconsumed, the family/epoch/assurance and issued policy revision remain valid, and the cached access token is unexpired. Recompute expires_in from its remaining lifetime; do not re-sign, rotate again, advance idle/auth_time/absolute deadlines, or replay a response after logout/switch/revocation. Concurrent identical retries converge on the one committed result across replicas. A different request ID or payload on a known consumed token remains replay and revokes the family. An exact retry whose successor was already consumed returns invalid_grant without returning old credentials or revoking a healthy newer generation while its receipt remains recognizable. After the 30-second window ordinary consumed-token replay handling applies; the client must stop recovery and reauthenticate instead. Missing/decryption-failed receipt for an extension attempt or unavailable store fails closed, never creates a second successor or falls back to plain rotation. A stolen token **and** its matching request ID can recover that same result during the window: this explicit bounded replay trade-off is not sender constraint.

The Rust client **always sends the extension ID**, serializes refresh across processes, writes the pending token/request-ID/exact payload to secure storage (or the explicitly memory-only session) before sending, and atomically replaces it with the successor after success. It does not retry without the ID after an extension failure. A lost response permits only bounded exact retries with backoff, conservatively stopping by 30 seconds from the first client send (never later than the server receipt deadline); never generate a new nonce or blindly retry the API mutation. A crash after that window or loss of secure pending state can still require reauthentication. `/oauth/revoke` remains required, checks token/client binding and revokes the family plus associated authentication with a non-enumerating response. Offline access retains at most 300 seconds residual validity; live checks include family status.

Access tokens remain memory-only. The reference CLI persists refresh credentials only in an available supported OS credential store, with an explicitly selected memory-only session when secure persistence is unavailable; never silently write plaintext. A minimal crate can omit platform storage but still implements in-memory refresh. Ten-minute commands and later commands within the family lifetime renew without opening a browser. Refresh never automatically retries the original non-idempotent API operation. WIF and SPA JavaScript still receive **no** refresh credential.

### 5.3 GitHub WIF and proof replay

A GitHub Actions job with `permissions: id-token: write` requests the configured exchange audience, then uses the stable generated source/grant IDs at `/oauth/token`. SkyOAuth verifies that selected source, evaluates the selected grant's eligible bindings, and issues only its bounded direct or delegated credential. The Rust workload provider renews with a fresh assertion; it never logs/persists workload tokens or receives WIF refresh credentials.

Production bindings require immutable owner/repository IDs, explicit `event_name`, ref, environment and workflow identity, plus reusable-workflow identity when used. A default-branch ref/workflow does not establish a safe event. The example is **push-only**, rejecting otherwise-matching `pull_request_target`, `workflow_dispatch`, `issue_comment` and `workflow_run` assertions. GitHub's human `actor` is audit provenance, not a human SkyOAuth login.

Matcher predicates are ANDed. A configured claim absent from verified evidence is a non-match. Omitted optional predicates are unconstrained; required production predicates cannot be omitted, and deleting a predicate is explicit privilege widening. Strings are exact matches, not implicit regex/wildcards.

**Replay policy is a source capability, not a universal toggle.** Default `reusable` permits another otherwise-valid proof exchange inside its lifetime only after fresh policy evaluation/rate limits, producing a new output `jti`. `single_use` is permitted only for locally signature-verified discovery/uploaded-JWKS sources enrolled with an **on-demand assertion** profile and a client/issuer capable of obtaining a fresh signed nonempty `jti` per exchange. Consume a keyed digest of `(tenant, source_id, exact_issuer, verified_jti)` atomically across replicas/grants; exactly one attempt may issue. Missing jti/store failure/replay denies, and a crash may burn the proof. Retain consumption through exp plus skew and digest-key rotation; provider switch/rollback never resets it.

**Kubernetes projected tokens, including TokenReview sources, must use `reusable` in v0.1.** Enrollment/import rejects `single_use` for `kubernetes_token_review` or any projected-service-account assertion profile, even when keys could also be verified locally. Rereading a projected file does not promise a fresh token/JTI on demand; do not force an agent to wait for kubelet rotation after its short-lived SkyOAuth token expires. Generic JWT sources require an explicit tested renewal capability before opting into single-use. A canceled job can leave an issued bearer credential valid until expiry; critical operations use §6.1.

### 5.4 Kubernetes and generic external sources

Use rotated, audience-bound projected service-account tokens, rereading the file on renewal. A `kubernetes_token_review` source stores a stable cluster ID, configured expected issuer metadata, fixed HTTPS API endpoint, versioned CA/fingerprint, narrowly scoped reviewer-credential reference, requested audiences and timeout. Reviewer secrets are externally managed, not plaintext exports. Tenant secret references (CA bundle, reviewer credential, provider `credential_ref`) resolve only within that tenant's provisioned namespace, and discovery, JWKS and TokenReview egress destinations come from an allowlist approved by instance `security_admin`; tenants only choose from it (OQ-TM-13). Its fixed private-egress profile permits only the approved endpoint with TLS hostname/CA verification and no redirects.

The required source ID selects exactly one registered verifier. It is not proof of a tenant or cluster. Multiple clusters may share an issuer, so issuer is not a unique lookup key; do not probe clusters until one accepts, use unverified claims to select a server or accept client-supplied endpoint/CA/credentials. Shared signing authorities cannot provide independent cluster isolation.

TokenReview sends explicit `spec.audiences` and requires authenticated success, no error and compatible nonempty returned audiences. Bind returned SA identity/UID and supported bound-Pod evidence to the selected cluster/source. TokenReview returns authenticated user/audience evidence, **not a general claim set or guaranteed verified jti**. Never invent a jti from decoded input for replay enforcement. Policies requiring evidence the adapter cannot attest are rejected; parsed token fields can narrow checks but cannot supply missing positive authorization evidence. Document the supported cluster's time/object-revocation behavior rather than claiming instantaneous revocation. Tests must renew using the same still-valid projected token before rotation, then the rotated token.

Other source kinds:

- `oidc_discovery`: exact issuer, explicitly approved discovery/JWKS egress, algorithm/audience allowlists, bounded refresh/cache/staleness.
- `uploaded_jwks`: exact issuer/audiences/algorithms and a stable tenant-owned `TrustKeyset` parent with public-only versioned keysets and explicit overlap. Multiple versions may be active; conflicting live kid/key combinations deny.

Kubernetes local JWT validation is a separately enrolled mode with explicit stale-object-revocation limits, not fallback from failed TokenReview. Reject unregistered sources, token `jku`/`x5u`/embedded-key trust, `alg=none`, weak substitution, private-key uploads and arbitrary redirects. Bound input sizes, claim complexity, clocks and key refresh. None of these source configurations belongs to a human provider switch.

### 5.5 Upstream provider exchange

Zitadel is the first human adapter, not the canonical API issuer. Compatible, authorized exchange of Zitadel-issued tokens may run server-side after checking actual deployed provider capabilities and subject/actor/audience/scope restrictions. Do not assume arbitrary GitHub/K8s assertions can be exchanged into Zitadel administrator credentials.

Normalize downstream credentials to SkyOAuth's public profile. An upstream token may be retained in the explicit encrypted vault for an approved upstream operation, never passed through as the default application credential. Upstream administration uses a separately isolated, restricted service adapter; it is neither SkyOAuth operator authority nor a target of public WIF delegation.

### 5.6 Grant modes and dormant impersonation

- **Direct workload (required):** the grant's workload actor becomes `sub`; target service is null; audience/scope/resource ceilings still apply.
- **Delegation (required):** the preapproved service becomes `sub`, workload becomes RFC 8693 `act.sub`; retain source/run provenance and effective revision in audit. The single-proof request is the explicit extension in §5.7.
- **True impersonation (conditional):** high-risk mode omitting target-visible actor; not required for v0.1 and never a fallback for another mode.

An unsupported impersonation grant has a defined write path: authorized create/import accepts it **only with `status: disabled` and `activation_state: requires_reapproval`**. Reject an enabled/approved unsupported record rather than silently activating or pretending it is delegation. This permits preservation tests through normal APIs, not direct database inserts. Store its full desired constraints/provenance. A release gaining the capability leaves that record disabled and requiring approval; feature availability, import, ordinary PATCH or provider migration cannot enable it.

**v0.1 does not implement impersonation activation.** Retain only the existing grant's disabled state, desired policy/provenance and requires_reapproval marker, because preserving stored WIF policy is an explicit compatibility requirement. There is no v0.1 GrantActivationApproval table, activation endpoint, two-person ceremony implementation or active-impersonation release gate. All attempts to enable or issue this mode deny. Startup/import validation rejects active unsupported records without silently rewriting or deleting them.

A later feature-specific ADR must specify fresh revision-bound approval/activation and its tests before the mode can ship; simply upgrading capability cannot activate preserved records. This defers the active subsystem rather than removing the established no-reset guarantee. No provider migration changes dormant records.

### 5.7 Exchange selection, overlapping bindings and scope

Both form-encoded profiles require exactly one `skyoauth_trust_source`, `skyoauth_grant_id` and API `audience`, with optional `scope`. The two selectors are nonsecret SkyOAuth extensions containing **generated immutable IDs**, never tenant-local display names (§7.4).

1. Load the selected source and grant as untrusted candidate records, require the same tenant and expected grant mode; reveal no cross-tenant existence details on failure.
2. Verify the assertion only at that source. The grant determines the candidate actor/target, but an ID does not prove that actor.
3. Evaluate enabled bindings for that source **that map to the selected grant's actor and are explicitly in its `allowed_binding_ids`**. At least one must match verified evidence. Matching bindings for other actors do not make the request ambiguous or authorize this grant.
4. Bindings in v0.1 are identity predicates, not independent resource grants. If several eligible bindings match the same actor, use stable ID ordering to select one for provenance; their permissions are not unioned. Invalid cross-actor references are rejected at configuration time. The grant, target ceiling, audience assignment and requested scope/resources determine authorization.
5. Validate current tenant/principal/source/binding/grant/service status, registered audience assignment and all ceilings. Emit the selected binding and complete immutable decision dependencies in the policy revision/audit.

This permits repo-wide and deployment-specific bindings to coexist without an accidental denial or an unauthorized actor fallback. Grant selection never accepts arbitrary subject, target, tenant or mode overrides.

## 6. Explicit credential profiles and backend verification

SkyOAuth uses a **private, versioned JWT profile**, not an incomplete RFC 9068 claim. Access JWTs have protected header `typ=skyoauth-access+jwt`; internal gateway assertions use `typ=skyoauth-internal+jwt`. These are proposed private identifiers, not registered media types. Do not emit/accept `at+jwt` as a SkyOAuth profile: RFC 9068 requires, among other fields, client_id, which WIF does not invent from a source ID. Native tokens do carry their actual registered client_id for local attribution. Any future RFC 9068 support needs a separate complete conformance profile.

All credentials require a verified signature/allowed algorithm/kid, exact issuer and **one registered audience** as a JSON string (an array, even single-element, is rejected; OQ-TP-4), iat/nbf/exp with bounded TTL/skew (clock skew default 60 seconds, instance ceiling 120 seconds; OQ-TP-10), unique jti, explicit scope (issued as the canonical sorted unique string, verified as a set; OQ-TP-8), signed `skyoauth_tenant`, `skyoauth_profile`, `skyoauth_profile_version=1`, `skyoauth_policy_revision` and `skyoauth_constraints`. The protected typ, signed profile and expected ingress route jointly select validation rules. Never infer a profile from a `usr_` prefix, missing grant, presence of `act` or an untrusted request header. Reject unknown versions, contradictory claim sets and a profile not allowed by the resource-server registration. Each profile has an exact top-level claim set; any other claim, including an unknown `skyoauth_*` claim, rejects (OQ-TP-6).

### 6.1 Revocation and private live operation check

Offline short-lived access JWTs retain residual validity until expiry after a grant/policy/session change; the v0.1 access TTL ceiling is 300 seconds (policies may shorten it). Browser authentication is checked live at the gateway; an already-issued internal assertion has only its bounded residual lifetime. Do not promise cancellation of previously authorized operations or instantaneous Kubernetes object revocation.

`POST /internal/v1/policy/check` is private. Authenticate the caller against **ResourceServerChecker**, bound to the registered resource-server audience and explicit tenant set, not against the token's delegated subject/service. Direct workload credentials with no target service are fully supported. The caller sends exactly one access JWT or internal assertion plus canonical action/resource coordinates; request binding is retained for internal assertions. Input is bounded and never logged as token material or application payload.

Look up the persisted `ResourceAction` for that resource server: required scopes, supported profiles, required resource dimensions and whether live checking is mandatory. Verify the complete profile, audience/tenant assignment, current principal and immutable decision dependencies. WIF checks source, chosen binding, grant and optional target service; human checks HumanAccessPolicy, active pinned client/origin/route configuration, authentication/provider epoch and session or native refresh family as applicable. Superseded/invalidated authorization revisions deny and require renewed credentials; never reinterpret an old token under broader policy. Unknown action/resource/caller or wrong tenant/audience denies. Store/checker or transient route-observation failure returns typed unavailable without an allow; it is not an authentication failure. A resource server cannot use another audience's checker identity.

Return request-bound allow/deny/unavailable, checked revision when available and decision ID with no-store, not a new token or reusable blanket permission. The backend still applies canonical resource ownership and RBAC, with no positive caching for critical calls. Checks begun after committed revocation deny; a subsequent revocation cannot undo already-authorized work. Browser streams/downloads that outlast initial evidence use the bounded continuation below; expired assertions are never accepted as fresh evidence. **Bearer server-streaming responses (`wif` and `human_cli`) end no later than the original access JWT expiry**, hence at most its remaining 300-second lifetime, and sooner on a required live denial. v0.1 has no in-band token replacement or bearer continuation: the Rust consumer obtains a fresh credential and explicitly opens a new read-only subscription/download request. Native refresh or WIF reacquisition does not extend the old response. Resume cursors/event IDs/ranges are application-owned positions, never authorization; every new request repeats tenant/scope/resource/RBAC checks. A ten-minute log tail therefore reconnects across token lifetimes without restarting the deployment it observes. Deduplication/gaps are an application contract, not an exactly-once promise. Generalized bearer continuation is deferred under ADR-010 to avoid extending external-proof authority implicitly. M2/T26 delivers WIF support; M3 adds human-session checks and M4 human CLI checks before those profiles ship.

### 6.1.1 Established browser-stream continuation

For an action registered as stream-capable, the backend first calls `/internal/v1/policy/check` with the **unexpired** human_session assertion, canonical action/resource coordinates and a fresh backend stream-instance nonce, requesting a session continuation. Before sending protected bytes it verifies the ordinary allow and its own current RBAC. SkyOAuth atomically records a `SessionContinuation` and returns an opaque continuation ID plus `authorized_until`; this is a narrow exception to the ordinary check response, not a new bearer credential. Session/authentication references alone, or an already-expired assertion, cannot open one. An assertion jti can initialize at most one continuation; replay with different nonce/context denies. An exact retry by the same checker may recover the same ID but never extends its lease without a recheck.

Bind the continuation to the authenticated checker identity, tenant/audience, principal, session/authentication refs, origin/route and policy revision, exact action/resource coordinates, request tuple and stream nonce. It authorizes continuation of **that already-established response**, not a new request, new resource, new mutation or wider scope. It is private server-to-server state, never exposed to browser code or accepted on a public bearer path.

`POST /internal/v1/policy/recheck-session` accepts the continuation ID and bound nonce/context from the same registered mTLS checker, using stored verified references rather than an expired JWT. Check session/authentication deadlines, principal/provider/tenant epochs, pinned origin/route versions, current parent security revisions/status, assignment/policy/action dependencies and §4.2 runtime state; the backend rechecks canonical ownership/RBAC. Revocation, changed dependencies or an unauthorized caller denies and closes. During a planned gateway apply, unchanged pinned dependencies yield unavailable with no renewal or closed_at; changed/removed dependencies or security disable are terminal. Temporary store/observation/transport unavailability likewise permits retry only inside the previous lease. Staging, operational cap edits and a registry-only pointer advance with unchanged actual dependencies are not authorization mismatches. A changed version or security revision requires fresh admission; re-enabling never resurrects an invalidated context.

Each allow returns `lease_seconds` and `authorized_until`. The route's `session_lease_seconds` defaults to **15 seconds** and is bounded by the instance-administered ResourceAction `max_session_lease_seconds`. The action ceiling defaults to 15; only an explicitly classified **noncritical read-only** action may opt into a ceiling above 15, with an absolute maximum of **300 seconds**. Critical or mutating actions stay at <=15 seconds; per-operation live checks are still required where registered. Reject out-of-range or contradictory configuration rather than silently widening. The effective lease is the shortest of route/action limits, current session/authentication expiry, the applicable route-observation deadline and an immutable continuation deadline of at most **1 hour** from creation (route/action policy may shorten it). Authorization revisions bind these choices; activation of changed policy requires fresh admission, not reinterpretation of an old context.

Recheck before authorized_until; renewal after it or the absolute deadline denies even when the session remains live. Stop protected transmission immediately on terminal denial, or by the last successful deadline when the checker/store is unavailable. Neither stream traffic nor rechecks extend session idle/absolute expiry. Revocation after an allow has at most the **selected remaining lease** (default 15 seconds, explicitly opted-in noncritical maximum 300 seconds), not instantaneous cancellation. Set a monotonic local deadline no later than recheck request-start plus returned lease_seconds, subtract a safety margin and honor earlier server/session/context/observation bounds; network delay never extends it. No fail-open stream grace. A 20-second auth-checker/store outage will terminate default-lease streams whose last deadline passes; route-observer loss alone follows §4.2's separate bounded observation tolerance. Longer leases trade slower revocation for less polling and more outage tolerance, not guaranteed availability.

**Explicit release:** after completion, cancellation, disconnect, terminal denial or graceful backend draining, the backend stops local transmission and sends `POST /internal/v1/policy/close-session` with the continuation ID and its bound nonce/context. Require the same currently authorized mTLS checker; do not require an unexpired assertion, live end-user session or unexpired lease to release the checker's own context. Atomically set closed_at and release its quota occupancy exactly once, serialized with admission/recheck. A matching repeat returns success without another decrement; close wins permanently over later rechecks. Unknown IDs or mismatched checker/nonce/context receive the same non-enumerating not-found result and cannot release another stream. Do not expose the handle or release endpoint to SPA code.

Release may be retried with bounded backoff by that backend, but loss of the close request or a backend crash can leave an orphan until its last lease expires. No availability guarantee bypasses the cap in that case. Retain closed-context identity long enough for bounded idempotent retries, and an admission-jti tombstone at least through assertion expiry plus skew; closing or garbage collection never permits a second admission with the same assertion. Expired contexts cease counting without waiting for a cleanup job. Process restart or a new connection always requires fresh admission, not reuse of an orphan's handle.

The one-hour cap deliberately interrupts an unfinished download. APIs serving resumable artifacts must support range/resume against a stable object version/ETag, with If-Range or equivalent integrity checks; on version change or unsupported resume restart safely, never concatenate unrelated versions. SSE/RPC reconnection uses validated application cursors. Both client libraries provide opt-in read-only reconnect with capped exponential backoff and full jitter, honor Retry-After, and stop on cancellation or definitive authorization denial; do not reconnect all clients immediately, follow cross-origin credential redirects or replay mutations. Recovery always obtains fresh admission and backend RBAC. Payloads still flow directly through Envoy.

**Bounded load:** the recheck endpoint accepts either one item or a batch of at most **100 items / 64 KiB**, under one registered checker identity. Each item retains its continuation ID, nonce/context and correlation ID and receives an independent allow/deny/unavailable/deadline; no batch-wide allow exists. Reject duplicate IDs or malformed/oversized envelopes before writes; deny a wrong-checker/tenant item without exposing its state. Missing/late/unavailable results never extend its previous lease. Implement set-based reads/writes where safe, retaining each context's atomic no-post-expiry renewal and current-policy checks. Batching reduces network overhead, **not** the number of logical decisions or required row updates. Schedule jittered renewals before each earliest deadline, never delay to fill a batch. The close endpoint uses the same single/batch bounds and per-item identity checks, but only closes contexts and never returns an authorization lease.

Admission enforces an atomic cross-replica per-session cap using **OriginCapacityPolicy**, a separately revisioned operational record keyed by origin, default **8**, editable by that tenant's client_admin. **InstanceCapacityPolicy**, controlled by security_admin, stores the per-session ceiling (1–64) and explicit finite tenant/checker/global quotas and rate limits. The effective session cap is always the lower of the current origin setting and instance ceiling, including after the latter is lowered. Reject new origin settings above the ceiling; an existing higher value is bounded by the new ceiling until reconciled. These operational revisions are **excluded from route-bundle pins and HumanAccessPolicy/credential authorization snapshots**. Lowering limits blocks new admissions until occupancy falls below them; it does not close existing streams, change their authorization revisions or require redeployment. A session is origin-bound and occupancy counts unclosed unexpired leases across all its routes/checkers, not per API connection pool. Admission and limit updates serialize; expiry releases occupancy without waiting for cleanup.

Capacity failures have distinct safe wire reasons after authentication/authorization: **`too_many_open_streams`** is only the per-session cap (HTTP 429 / Connect `resource_exhausted`); **`stream_capacity_unavailable`** is shared tenant/checker/global exhaustion (HTTP 503 / Connect `unavailable`), without exposing other tenants' counters; request-rate limiting remains `rate_limited` (429), retried if at all only as an automatic read-only retry under the shared-capacity budget below (OQ-ERR-5). All may include a bounded Retry-After, not a guarantee that capacity will be free; `route_configuration_unavailable` must include one (OQ-ERR-10). For an opted-in resumable read-only reconnect, the TypeScript library may make **one delayed per-session-cap retry** at a valid Retry-After no greater than 300 seconds, plus jitter uniform in 0 to min(5 s, 10% of the hint), then surface the capacity error if still capped. Missing/invalid hints surface immediately. Preserve that one-retry budget across intervening transient failures; it resets only after a successfully established stream or an explicit new application/user operation, not each 429. Shared-capacity and infrastructure unavailability instead use cancellable jittered backoff with finite attempt/elapsed budgets and no login prompt: base 1 s, factor 2, cap 30 s, full jitter; at most 5 retries (6 requests) or 120 s of accumulated backoff waiting, whichever comes first, never starting a wait that would cross 120 s. A valid Retry-After of at most 300 s is honored as the earliest next attempt, excluded from the 120 s clock but counted as a retry; a missing hint falls back to backoff, while an invalid or larger hint surfaces the error (OQ-ERR-4, OQ-ERR-12). No automatic mutation replay. This permits orphan-expiry recovery after a crashed five-stream backend without creating a permanent reconnect loop. Close/expiry still preserves admission tombstones; client code never receives continuation handles. T32.14 measures actual load: ten thousand streams at 15-second intervals imply about 667 decisions/updates per second before safety margins, regardless of RPC batching.

### 6.2 Separate internal assertion signing and cost

Public access-token keys and internal assertion keys are distinct key pairs with disjoint kid namespaces and **non-interchangeable trust sets**. The v0.1 internal model is **one versioned key per deployment signer group, shared only by that group's authorized auth replicas**, not a freshly generated key per replica. Scale-out loads an already-published active key/kid from protected deployment secret storage or startup unwrapping into local protected memory; it does not enroll a new trust identity. Replicas have no public access-signing permission; neither does any other process that serves Check or holds internal keys (OQ-TM-10). Shared compromise affects the whole signer group; per-replica keys remain an alternative requiring a separate enrollment design, not an ambiguous second baseline.

Only instance `security_admin` through audited key administration enrolls/rotates/disables group keys and authorizes private-key distribution; public clients and auth replicas cannot self-register a kid/key. Backends/live checkers obtain the internal public set from authenticated private `/internal/v1/assertion-jwks`, rooted in deployment trust. It has a version/ETag and a maximum **60-second** verification-cache freshness, without stale-on-error extension. Unknown kid may trigger one bounded, rate-limited single-flight refetch of this fixed endpoint, with negative caching; it never authorizes a token-selected URL or key. Failure or still-unknown/disabled key denies. Profile/ingress selects the trust set before kid lookup, so changing typ cannot cross key purposes.

For a new group or key version, publish its public key before setting activate_after, at least the maximum verifier cache interval plus allowed clock skew later. Readiness requires the replica to load a registered key, confirm the published set/version and wait until activate_after; new verifier processes fetch the current set before readiness. Ordinary scale-out of an active group needs no new-key delay. Rotation retains the prior signer through overlap until the new key is eligible; a failed publication prevents activation, not verification bypass. Rollout/scale-out tests include cached old sets, unknown-kid floods, private key-service outage and missing/wrong group secrets.

**Emergency standby:** production commissioning and planned-rotation completion require one active version plus at least one prepublished, unexpired standby per signer group, already past activate_after. Standby public material is already verification-eligible in the private set; `signing_state=standby` is a control-plane prohibition on issuing with it, distinct from verification eligibility. Promotion therefore does not require every verifier to refresh an active-status flag. Keep the standby private key in separately access-controlled encrypted custody: ordinary auth replicas cannot mount, unwrap or read it before promotion. A standby secret already exposed to the compromised process is not a clean recovery key.

**Standby-use tripwire:** after verifying the signature, live policy checks, continuation admission and rechecks consult authoritative key state and deny evidence whose admitting key is still unpromoted/standby, with a rate-bounded compromise alert containing key/decision identifiers, never token bytes. Merely naming a standby kid in an invalid signature must not trigger a verified-compromise alert. Promotion is required before legitimate issuance. Previously promoted keys in normal retirement continue under the existing overlap/provenance rules; retirement is not standby. Offline signature verification alone cannot enforce this live-state tripwire because standby public keys are intentionally prepublished; do not claim otherwise.

On compromise, instance security_admin disables the affected version and promotes an eligible unaffected standby through an audited revision-checked key operation, then distributes it only to isolated/rebuilt or otherwise verified-clean replicas. Do not leave a compromised key enabled during propagation and do not waive activate_after for a newly enrolled key. This removes the mandatory publication wait, not the time needed for containment, key delivery or replica recovery. Promotion may operate in an alerted **degraded-redundancy** state while a new standby is enrolled and matures; lack of a replacement standby must not block use of the promoted clean signer. If no trusted eligible standby remains, fail closed until recovery rather than using compromised material. Existing offline-cache and continuation-lease revocation bounds still apply; standby promotion cannot resurrect contexts admitted under a disabled key.

Internal-key rotation/disable is independent of public JWKS and provider changes. Retain retired verification keys for the 30-second assertion lifetime plus skew, but reject compromised/disabled keys under the bounded cache/live-check rules above. Retain key status/provenance records through all dependent continuation deadlines even after public key bytes retire; retirement alone does not revoke admitted streams, whereas compromise/disable does. Continuations retain the admitting internal-key ID and deny on its compromise/disable; they do not rely on retaining an expired assertion or old key for the stream's lifetime. Key disable does not instantaneously update an offline verifier cache: its remaining freshness is at most 60 seconds; live admission/rechecks consult authoritative status, and previously granted stream leases retain only their stated bound. A compromised internal signer can forge internal evidence within its trusted boundary and is still high-impact, but cannot mint public access tokens; live checks additionally compare identity fields to the actual session/authentication records.

Expected cookie-path work is bounded metadata parsing, a live session/policy read (batched where possible), **one local asymmetric signature** and backend signature verification. There is no per-request KMS/HSM/network signing round trip in the baseline, no body processing and no cached reusable request assertion. A separately mandated remote internal signer is an explicit deployment variant whose availability/latency must be measured; failure denies. T32.14 benchmarks signing CPU, store reads/writes, p50/p95/p99 check latency and throughput, including continuation batches, per-session cap abuse and 10,000 idle open streams at several lease sizes on stated representative hardware. Set and publish the deployment's latency budget from those measurements; no unmeasured numeric performance claim or cache that weakens revocation is implied.

## 7. Persistence, ownership and administrative writes

PostgreSQL is authoritative for all stable authority and one-time state. WIF, audience, client/origin and operator records cannot cascade-delete through HumanProvider. Use immutable history, optimistic concurrency, atomic audit and conservative cache invalidation. Security events (operator writes, recovery, key operations, provider switches and the standby tripwire) are also emitted to an append-only external sink, at minimum structured logs, chosen in M1a; the database audit stays authoritative (OQ-TM-12). Store failures never expand privilege. Encrypted database backups differ from redacted configuration exports; neither ordinary YAML nor logs may expose private keys, reviewer/operator secrets, cookies, proof tokens or refresh credentials.

### 7.1 Tenant partition and instance-owned audience authority

`Tenant` is the administrative policy partition, explicitly mapped to application organization/resource ownership. Stable generated IDs are globally unique; composite tenant/object foreign keys prevent cross-tenant references. Sources/keysets/bindings/services/grants/clients/origins/human policies are tenant-owned. External issuer strings are not unique: different tenants can register GitHub, and independently keyed clusters can share one issuer. A source selector chooses only a candidate verifier; verified evidence plus the selected same-tenant grant establishes authority.

**Audience strings are not tenant-controlled free namespaces.** Instance `security_admin` creates a `ResourceServer` with one globally unique exact audience and explicitly grants tenants access through `AudienceTenantAssignment` records specifying allowed profiles/scopes and constraint schema. Tenants may not self-assign an existing audience or create a competing registration. Service ceilings, WIF grants, OAuth clients, ApplicationOrigins and HumanAccessPolicies reference registered audience IDs and are refused if no active same-tenant assignment exists. Recheck at issuance and live policy checks; a tenant admin cannot mint for another tenant's API merely by spelling its audience/project name.

The resource server separately owns checker identities and action-to-scope/resource/profile mappings, administered through instance-scoped endpoints. `ServiceIdentity` is a possible **token subject**, not the API receiver. Multiple actors or direct-mode tokens can call the same resource server without becoming its checker authority.

For a shared multi-tenant audience, every backend resource is mapped to a canonical SkyOAuth tenant. The backend must compare that owner with the signed tenant before scopes/resources/RBAC; missing mapping denies. Instance assignment is defense in depth, not permission to omit tenant verification. Audience assignments/actions/checker identities and client/origin policy are stable through a human provider switch and included in snapshots.

Check the active local credential and role on every call; a certificate alone is insufficient. OIDC roles/groups/emails, human sessions and WIF credentials never grant operator authority. Operator keys are operational trust anchors, not application API secrets.

| Tenant `auditor` | Redacted tenant configuration/audit reads; separate instance audit authority where explicitly granted. |

Bootstrap is a deployment-local command/Unix socket operation, never public enrollment. The socket is owned by the service UID with mode 0600; `pods/exec` on the SkyOAuth namespace is equivalent to channel access and is limited to already-trusted infrastructure administrators (OQ-TM-9). Atomically enroll an initial security_admin public credential and separate offline recovery public key, audit, then durably close bootstrap. Restart or an empty config cannot reopen it. The service binary retains only the deployment-local bootstrap/recovery verifier. **M1a provides a separate `skyoauth-operator` workstation binary at `operator/`, tested on Linux, macOS and Windows**, for remote private mTLS configuration and local signing of recovery challenges. It has no server/database or M4 native-OAuth dependency. Operator keys remain on the operator workstation/hardware signer, never copied into a pod to run a remote client.

Document and test the supported TLS client-key and hardware/OS signer adapters per platform; unsupported hardware/provider combinations fail explicitly, never export a key as fallback. For break-glass, the restricted local service emits a short-lived challenge (default 5 minutes, maximum 15 minutes; OQ-LT-17) including instance identity, operation/arguments digest and expected revision. The workstation verifies/displays that context and signs it with the offline recovery key; only the signed response crosses the separately authorized deployment-local channel. Offline key custody is not relaxed by the existence of a portable client. M1b adds the human configuration commands to the same operator binary before M3.

The first operator can then create a tenant, enroll/assign its scoped operators, register an API audience and tenant assignment, create/assign an application origin, register a CLI client and human policy, create workload/service principals, and configure providers/sources/bindings/grants. A single operator may hold multiple explicitly assigned roles for a small deployment, but no role implicitly inherits another. Initial human-provider activation uses the same switch operation from a null pointer. This provides a complete post-bootstrap write path with no manual database inserts.

Break-glass uses the restricted local interface plus the independent recovery key over a short-lived, single-use challenge bound to operation/arguments/expected revision. Permit bounded operator restoration or the same validated provider-switch/rollback operation only, not arbitrary WIF edits, audience reassignment or token minting. Operator restoration only enrolls a replacement `security_admin` credential and revokes operator credentials. Rotate recovery keys after use: every break-glass transaction (operator restoration or provider switch/rollback) enrolls a replacement recovery public key in the same signed transaction and retires the used key (OQ-TM-8). v0.1 has a single recovery key; a quorum is deferred. No online path replaces the recovery key; only a transaction signed by the recovery key over the local channel does (OQ-TM-15). Consume challenges durably and audit/alert. Rehearse while the human IdP is down or account linking is broken. Database/signer disaster recovery remains separate. Restore procedures preserve bootstrap-closed and consumed state or quarantine issuance (default 15 minutes, ceiling 60 minutes; OQ-LT-13) until outstanding state can no longer be replayed. Where consumed state is not preserved and the quarantine cannot cover outstanding state, such as native refresh families lasting up to 7 days, revoke the affected credentials instead (LT-100, LT-106).

### 7.3 Provider changes cannot bypass the switch transaction

`TenantLoginState.active_provider_id` is the sole active-provider pointer. HumanProvider has no independently writable active flag. All GET/export representations of active state are **read-only observations**. Ordinary provider PATCH, deletion/disable of the active provider, GitOps imports and config reloads must reject attempts to change the pointer, auth epochs or active-provider issuer/client/callback/authentication semantics. Creating/testing inactive candidates is permitted. A plan may cover such authentication-critical changes, activation from null, switch, disable or rollback; only its authorized commit transaction updates login state and advances epochs atomically. Switch, rollback and initial-activation commits (initial activation goes through the switch commit) need a distinct second approver unless single-actor instance policy applies (OQ-TM-7); a disable commit does not, because it fails safe.

**Credential-only rotation is not a provider switch.** A dedicated, audited `provider_admin` credential-rotation operation may replace the versioned secret/key reference for the **same issuer, upstream client_id, client-authentication method, callbacks and identity/authentication semantics**, including an active provider. Compare expected provider/credential revisions, validate the unchanged semantic tuple, and advance only administrative/credential revisions; provider auth_epoch and tenant auth_generation do not change. Existing sessions, native refresh families and pending transcripts retain their identity binding. Never expose secret bytes in configuration exports or logs.

Use only explicitly configured versions for bounded provider-supported overlap; no arbitrary secret/key fallback. Lack of upstream overlap may fail an in-flight code exchange and require that login to restart, but does not itself log out existing sessions. A compromised credential can separately trigger an intentional epoch-invalidating transition. This deliberate compromise transition is a revision-checked, audited, per-tenant operation that advances that tenant's existing `TenantLoginState.auth_generation` without a provider change, invalidating its sessions and authentication contexts; there is no single-origin variant, and an instance-wide response runs it for every tenant (OQ-TM-14). It is `POST /admin/v1/tenants/{tenant}/login-state/compromise-transitions`, performed by tenant `provider_admin` as a single actor with no second approver. Instance `security_admin` may only run the instance-wide response, which runs the tenant transition for every tenant; it has no per-tenant write, following the security-disable precedent (OQ-API-6). The endpoint must exist before M3, and T13.9 implements it in M1b. Requests that also alter issuer/client_id/auth method/callbacks/assurance are rejected by the credential-rotation endpoint and require the ordinary switch plan. GitOps uses an explicitly typed credential-only operation with identical validation, not a generic way to bypass active-state protection.

Rollback uses the same guarded transaction with fresh monotonic epochs. No import, including one submitted by an operator holding every role, can replace it. Auth state is never retained accidentally because a generic active flag changed.

GitOps documents are role-scoped. A combined bundle is accepted only when the actor has **every** role needed for every mutation and its plan passes the same validation; otherwise reject the whole bundle, never partially apply or ignore unauthorized sections. Active-provider observations are not writable fields and a proposed change is always rejected in an ordinary import. Separate provider, client and WIF documents are recommended; the example in §5.7 is WIF-only.

### 7.4 Generated selectors and create-then-reference workflow

All object IDs and public OAuth client IDs are server-generated opaque random identifiers. Tenant-local `name` is a human label unique only within its entity type/tenant, never an exchange selector or globally reserved name. The prefixes in examples indicate type, not authority. A client cannot choose a global ID on initial create or probe another tenant through an import collision.

Creation omits ID and supplies a tenant-scoped name; the authorized API returns the generated ID/revision. Provision in dependency order (tenant/audience assignment, principals/source/keyset, binding, grant/client policy), or use a validated importer with tenant-local manifest references that resolves to generated IDs and returns a persistent mapping. Export that mapping and place returned source/grant IDs in job/client configuration. Creating two tenants' identically named sources yields different IDs without name collision.

Updates specify the existing ID and expected revision within the authorized tenant. Redacted exports preserve IDs on same-instance reconciliation; privileged full restore preserves them only into the intended empty/restored authority after ownership/provenance validation. Ordinary tenant import cannot claim an arbitrary missing global ID or rebind it. Reapplication is tenant-local reconciliation, not recreation. Once deployed, clients retain their IDs across provider migration; the one-time create-then-reference step does not violate the zero-reconfiguration goal.

## 8. Human-provider migration runbook

1. Authenticate independently. Snapshot issuer metadata, tenant/resource-server/audience assignments/actions/checker identities, client/origin/route/bundle versions and separate capacity policies, human-policy/enrollment registrations and current hold, all verifier configurations/keysets, principals/bindings/grants/activation state, policy decision fixtures, public key metadata and replay invariants. Do not export proof/secret material; fresh route observations are runtime evidence, not restorable permission.
2. Register/test an inactive replacement provider with fixed app and issuer-native callbacks; for a provider without RFC 9207 `iss`, finish the system-bundle apply that adds its `/oauth/callback/{provider_id}` path before testing it (OQ-TM-4); prepare verified account linkage and prove operator/recovery availability independently of upstream admin accounts.
3. Create an immutable provider-switch dry-run plan against expected login/config revisions. Reject any attempted WIF/audience/client/origin/operator/gateway/signer mutation; concurrent relevant changes require replan. A generic PATCH/import is not an alternate route.
4. Commit, with the distinct second approver unless single-actor instance policy applies (OQ-TM-7), only provider login/mapping configuration and fresh human auth epochs atomically. Invalidate affected browser/native flow bindings, sessions/authentication contexts, pending requests/codes and required refresh families; set the enrollment hold (§5.1.1). Preserve WIF configuration and consumed assertions. Offline human JWTs retain only their documented short TTL; live checks reject invalidated contexts.
5. Reauthenticate humans with stable principal/RBAC mappings where explicitly verified; unmatched users remain blocked under the enrollment hold until verified linking or an explicit enrollment-resume decision. Existing client_id, origin, audience and library configuration remain unchanged.
6. Reuse prebuilt **TypeScript SPA and independent Rust CLI artifacts** (record hashes), existing GitHub job, uploaded-JWKS workload and two independently keyed shared-issuer Kubernetes clusters. No rebuild/package upgrade/YAML/CA/reviewer/source/grant/audience change. Exercise direct/delegated profiles, human profile verification and both supported replay modes; projected Kubernetes renewal stays reusable.
7. Compare pre/post allowed and denied decisions, IDs/revisions and audit. Roll back through the guarded plan with fresh epochs, never whole-DB rollback over independent policy changes or resurrection of consumed human/proof state. Unsupported impersonation stays disabled; single-use tests obtain fresh proofs, never require a consumed one to become valid.

Repeat conformance after schema/chart/protocol/SDK upgrades. Human-provider downtime can block fresh human login but not valid independent WIF or operator recovery, except where shared SkyOAuth infrastructure is unavailable.

## 9. Security and abuse model

Threats include compromised workflows/runners, issuer/key/cluster confusion, assertion theft/replay, cross-tenant audience issuance, subject-versus-resource-server confusion, profile substitution, signer/operator compromise, login CSRF and callback injection, OIDC mix-up, redirect URI confusion, identity-linking confusion, native-client impersonation, session fixation, CSRF/XSS, unprotected routes, header spoofing, SSRF, generic-provider-write bypass, credential resurrection and stale streams.

Mitigations are explicit: instance audience assignments plus canonical backend tenant/RBAC checks; typed signed profiles with distinct human/WIF schemas; grant-directed source-bound evidence; restricted verifier egress; browser-bound state/nonce/PKCE and separate issuer-native confirmation cookies; one-time codes/consumption across replicas; scoped independent operator writes and exclusive switch commits; cookie/CSRF consumption before backend forwarding; no token logging; fail-closed stores/private endpoints; short TTLs with critical live action checks and bounded streams. Every claim has positive and negative release fixtures in the task plan.

Residual limits: zero static application secrets does not mean zero privileged keys. SkyOAuth signer/operator/recovery trust and reviewer/upstream service credentials need protection. Compromised human IdPs can impersonate mapped application users, but not independently rewrite WIF/operator/audience authority. HttpOnly limits token extraction, not authenticated actions by same-origin malicious JavaScript. Root/runtime/database compromise remains separate high-impact risk. Authorization cannot retroactively undo an already accepted operation.

## 10. Required clients and repository layout

### 10.1 Two first-class libraries

| Deliverable | Package / home | Primary consumer | Gate |
| --- | --- | --- | --- |
| TypeScript SPA library | npm `@skyoauth/client`, `clients/typescript/` | Framework-neutral SPAs; React/Connect adapters | M3 |
| Rust client library | Cargo `skyoauth-client`, Rust import `skyoauth_client`, `clients/rust/` | User-owned CLIs; workload tooling | WIF M2; native M4 |
| Reference Rust CLI | `skyoauth-cli`, `cli/` | Thin consumer of the Rust library | Native M4 |
| Workstation operator client | `skyoauth-operator`, `operator/` | Private mTLS administration and offline recovery signing; Linux/macOS/Windows | M1a; human commands M1b |
| Local bootstrap/recovery verifier | Existing `skyoauth-service` subcommands | Deployment-local challenge/verification, no workstation private keys | M1a; provider transition M1b |

The similarly named npm and Cargo libraries are intentional language-specific distributions in separate registries, not competing packages or interchangeable imports. Both are required. Browser code never gets a token getter, native listener or operator key. Rust consumers do not depend on React, a JS runtime, frontend assets, service internals or PostgreSQL.

### 10.2 TypeScript: SPA-first

Evolve the existing package instead of adding a second browser core. Provide session/principal state, top-level login, CSRF-protected logout, cancellation and authenticated transport. `@skyoauth/client/react` and `/connect` are explicit entry points with optional peer dependencies excluded from the framework-neutral core. Runtime/type exports agree; the core bundles without Node built-ins/polyfills.

Authenticated targets are configured same-application-origin HTTPS routes with no URL userinfo. Validate before attaching CSRF; use Fetch same-origin mode/credentials and reject redirects for authenticated API fetches. Caller options cannot override these boundaries or add bearer authentication. Only explicit top-level login follows server-managed upstream redirects. Narrow explicit loopback development settings must not weaken production. Injected fetch is trusted integration code, not permission to bypass URL/header checks.

Keep CSRF/session metadata in bounded memory, clear on logout/account change/invalidation, and send only credential-free cross-tab invalidation signals. No access/refresh tokens in localStorage, sessionStorage or IndexedDB. Distinguish unavailable/cancelled/forbidden from unauthenticated; no automatic mutation replay on 401 or after login. Streaming/download cancellation remains end-to-end without SkyOAuth buffering bodies. Opt-in resumable read-only reconnect follows §6.1.1 backoff/jitter, range/version and fresh-authorization rules; authorization failures never become infinite reconnect loops. Expose per-session too_many_open_streams separately from retryable shared-capacity/infrastructure errors. Permit only the specified one delayed per-session recovery retry, then surface it; never turn 503 into login. The backend, not browser code, releases continuation slots on cancellation.

The bootstrap arbitrary-baseUrl `health()` helper is unauthenticated utility code, not permission to attach session capabilities to that URL. Test that an off-origin health base cannot become an authenticated target. Future TypeScript workload support is a separate nonbrowser surface and not a substitute for the SPA library. Validate packed npm artifacts in an actual browser, not only Node fetch mocks.

### 10.3 Rust: reusable CLI library

`clients/rust` is a planned Cargo member publishing `skyoauth-client`, consumed by `cli/` and an independent example. Expose typed configuration/errors, redacted credential wrappers, cancellation/timeouts and provider traits. Document feature boundaries for native OAuth, system-browser launch, loopback, required refresh protocol with optional platform-storage features, and GitHub/Kubernetes integration; test minimal/default feature sets, not just all-features.

Use an external system browser, S256 PKCE/state and §5.2 confirmation. Bind an ephemeral listener only to an IP loopback address; choose the port before authorization and match the exact chosen redirect on redemption. The registered rule fixes scheme, IP literal and path, never `localhost`; only the port varies (OQ-TM-5). Bound callback lifetime/path, reject wrong state and clean up on cancel/timeout. No embedded login webview, password or static-client-secret fallback.

Attach credentials only to configured HTTPS API origins/audiences; never log or forward them across origin redirects. Access-token cache is memory-only. Required rotating refresh uses the OS credential store for persistence; a deliberately selected in-memory session works without it, and unavailable secure storage cannot silently fall back to plaintext. Workload renewal reacquires fresh on-demand proofs or rereads reusable projected tokens and never gets WIF refresh credentials. Bearer streams use explicit fresh-token reconnect at expiry (§6.1), with application cursors/ranges and no restarted mutation; background jobs are distinct from their observation streams. Library owns protocol; CLI owns terminal UX/exit codes.

Test the native crate/consumer on Linux, macOS and Windows, including loopback/cancellation and supported keychain adapters where included. Publish MSRV, TLS/runtime/features/platform policy separately from Linux server deployment support. Package and compile an independent consumer without private workspace-path assumptions.

### 10.4 Preserve the landed bootstrap

PR #2 at `8f81df23efd4c4a0cfe522f711a9ca56f294aab1` established `service/`, the root Cargo workspace, `clients/typescript/` and CI. Retain them. Add `operator` in M1a and `clients/rust`/`cli` when implemented; start server trust/policy/issuer/etc. as modules under `service/src`, extracting `crates/` only for justified reuse/isolation. Do not duplicate a service under `crates/server` or keep stale `packages/*` paths as another authoritative layout. The M3 route-control subcommand uses the service's route_control module in a separate least-privilege deployment; it is not part of either client library.

Preserve bootstrap tests/coverage and docs-only behavior. Each implementation adding/moving a member, entry point or package updates manifests, exports, lockfiles, CI paths/jobs, packed-consumer tests and README together. Planned modules and auth handlers are not implied to exist in the scaffold. The M1a operator client and local verifier do not require M4 native auth. Versioned profile fixtures and unchanged prebuilt SPA/Rust consumers prove migration compatibility without conflating credential models.
