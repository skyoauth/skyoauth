# Proposal: a `status` operation on the local socket that changes no row, and a bound on the restore reply

Status: Reviewed; rulings applied (the lead, 2026-11-27): the design holds
(A1 `status`, B2 a count with a capped list, exact absent a tie, the
`FOR SHARE` barrier), review findings F1 to F11 and the third-round items
(a) to (h) are applied, and Q1 to Q8 are ruled (see "Rulings"). F4 widens what a local peer reads: lead scoping, user
informed. Not implemented: this text changes no code, no contract, no
fixture and no test. It answers two rulings of the user (2026-11-27,
relayed by the lead), recorded in tasks §13 under "Other rulings of the
user, 2026-11-27": "Read-only socket operation" (an operation that only
reads is added to the local socket; proposal first, then the
implementation) and "Restore reply bound" (the `restore` reply's list of
revoked IDs is bounded by a service change, a count cap with the full list
available elsewhere or paginated IDs, worked out in the same proposal).

source fixes a point, **(not verified)** where the author did not check a
claim by running anything. Line numbers refer to `main` at `662deca`.

## Problem

### 1. Nothing on the socket reads (Q18)

The local transport (`service/src/local_transport/`, design §7.2, T13.4,
T13.5) takes one JSON line, then the client's end of stream, and answers
one line (`mod.rs:200-228`). Its four operations are `bootstrap`,
`issue_challenge`, `preview` and `restore` (`wire.rs:13-18`;
`mod.rs:232-237`). Three of them write. Every write can end with an
outcome the client cannot know:

- no reply: the transaction timeout or shutdown cut the request during its
  commit (`mod.rs:352-355`), or the reply could not be written
  (`mod.rs:357-359`);
- `auth_unavailable` or `server_error` from a failed `COMMIT`
  (`mod.rs:287-292`);
- a request the client gave up on while it waited in the listen queue,
  which may still run once accepted (`mod.rs:364-373`).

The service's rule is "reconcile, then retry" (`mod.rs:291-302`;
identity-registry :406-418), and the operator client classifies these
outcomes: `CallError::Unknown` and `UnknownOutcome::UncertainCommit`
(`operator/src/local/exchange.rs:292-304`, `:469`), `Retry::ReconcileFirst`
for the three writes and `Retry::Safe` for `preview` only
(`exchange.rs:192-216`). But it cannot reconcile: "The transport has no
operation that reads state, so this crate cannot reconcile: the only
readers are the admin HTTP API and the database (open question Q18 of the
T13.10 plan ...)" (`exchange.rs:306-309`). The admin HTTP API is served
nowhere yet (tasks §13 D5), and in a break-glass recovery it is the very
path that has failed.

| Write | The client knows | Lost with the reply | What would decide it |
| ----- | ---------------- | ------------------- | -------------------- |
| `bootstrap` | `instance_id`, the mTLS key (DER), the recovery key (it sent them) | `admin_id`, `credential_id`, `binding_id` (generated by the transport, `ops.rs:274-277`) | whether the recovery state exists for this instance with this recovery key, and whether this mTLS key is enrolled |
| `issue_challenge` | the replacement's key and anchor | `operation_id` and `M` (`ops.rs:361-365`) | nothing: a lost challenge expires unused (`mod.rs:399-404`) |
| `restore` | `operation_id`, the signature | the replacement's IDs, the revoked IDs, the new epoch | whether that challenge was consumed by a restore |

A retry is today the only probe, and it misleads: a retried `bootstrap` is
`conflict` and a retried `restore` is `not_restorable` once the first one
committed, "the repeat's answer looks like a refusal and hides the first
call's success" (`operator/src/local/mod.rs:75-82`). `not_restorable` is
also every other reason a restore fails (`mod.rs:443-444`), so it cannot
tell "your restore committed" from "your challenge expired".

### 2. The restore reply has no bound

The `restore` reply carries `revoked_credential_ids`, every credential the
restore revoked (`wire.rs:117-124`; `ops.rs:518-525`). The restore revokes
every unrevoked credential in one statement and returns all their IDs
(`service/src/persistence/registry/recovery.rs:1547-1552`). Nothing bounds
the number of operator credentials, so nothing bounds the reply. The client
caps what it reads at `MAX_REPLY_BYTES`, 4 MiB, and calls a longer reply an
unknown outcome (`operator/src/local/mod.rs:111-127`); its doc leaves the
bound as "Open question for the service and the design" (:123-126). A
restore that committed and revoked enough credentials would always look
unknown to the client, by construction.

## Part A: the `status` operation

### Options

| Option | Shape | Reconciles | Trade-offs |
| ------ | ----- | ---------- | ---------- |
| **A1. `status`** (ruled) | One op; three nullable keys: `operation_id`, `credential_spki`, `revoked_after`. One fixed reply shape. | `bootstrap` (by the instance, the recovery key and the mTLS key) and `restore` (by the operation ID); pages the revoked IDs (Part B) | One more op and one reply with nullable members; the reply reveals the recovery state, a challenge's state, and whether a key is enrolled. |
| A2. `operation_outcome` | One op keyed by `operation_id` only. | `restore` only | Narrowest. Bootstrap writes no operation row (`bootstrap.rs:51`), so a lost bootstrap reply stays unreconcilable through the socket, and its generated IDs stay lost. |
| A3. Reuse an existing read | (a) `preview` answers its refusal reasons; (b) the admin HTTP API; (c) keep the retry as the probe. | (a) and (c) partly; (b) not at all | (a) breaks "a refusal is `{"error":"<code>"}` and nothing else" (`mod.rs:415-418`), tells every preview caller which check refused (`mod.rs:443-444` chose not to), and needs a signature to ask about a consumed challenge. (b) The D4 operation reads serve only the second-approver flow's kinds, `OperationKind::ALL` (`service/src/operation/read.rs:230-237`; five kinds, `operation/mod.rs:311-317`), not `operator_restoration`; and they need the admin listener (served nowhere until S6/S7, tasks §13 D5) and a working operator credential, the thing a restore replaces. (c) is today's gap. |

A1 is ruled. The rest of Part A specifies it.

### Request

```text
{"op":"status","operation_id":string|null,"credential_spki":hex|null,"revoked_after":string|null}
```

- Every member is present, in this order (the encoder's order fixes the
  golden lines, `operator/src/local/wire.rs:29-35`); a missing member is
  `invalid_request`, as for the other ops (`mod.rs:219-224`). Serde's
  derive treats a missing `Option` member as `None`, so the implementation
  needs a deserializer that requires it (serde's documented default; not
  verified).
- `operation_id`: as `preview` and `restore` take it; a NUL is
  `invalid_request` (`ops.rs:129-136`).
- `credential_spki`: lowercase hex of a DER `SubjectPublicKeyInfo`, from
  which the transport derives the public identity as bootstrap and issue
  do (`ops.rs:95-100`); never an identity string. The identity is per
  encoding (tasks §13 "Canonical public identity"), so the client sends the
  same DER bytes it enrolled.
- `revoked_after`: the last revoked credential ID the client already holds.
  Without an `operation_id` it is `invalid_request`; with an operation
  that is not `restored` it is ignored (lead ruling, F8).

### Reply

All members, always, in this order; `null` where the reply has nothing to
say. Times are whole microseconds since the Unix epoch (`mod.rs:225-227`).
The type notation is the fixture's, with `|null` for a nullable member
(lead ruling, F8).

| Member | Type | Value |
| ------ | ---- | ----- |
| `server_time` | `integer` | the transport's `now`, from the injected clock the writes use, read after the barrier (F3) |
| `instance_id` | `string\|null` | the `RecoveryState` row's, closed or not; null when there is no row |
| `recovery_key_epoch` | `integer\|null` | the row's |
| `recovery_state_revision` | `integer\|null` | the row's |
| `recovery_public_key` | `hex\|null` | the row's current recovery public key (F4; lead scoping, user informed) |
| `operation_state` | `string\|null` | null when no `operation_id` was asked; else one of the states below |
| `expires_at` | `integer\|null` | the challenge's, when found |
| `settles_at` | `integer\|null` | `expires_at` plus this transport's transaction timeout, when `expiring` (F3) |
| `restored_at` | `integer\|null` | its `consumed_at`, when `restored` |
| `admin_id`, `credential_id`, `binding_id` | `string\|null` | the replacement the restore enrolled (from the consumed plan), when `restored` only |
| `revoked_credential_count` | `integer\|null` | when `restored`: the credentials the restore revoked (Part B) |
| `revoked_credential_ids` | `string_list\|null` | when `restored`: the next page of them, in byte order, after `revoked_after` |
| `enrolled_state` | `string\|null` | null when no `credential_spki` was asked; else `not_found`, `enabled`, `disabled` or `revoked`, for the credential with that public identity |
| `enrolled_admin_id`, `enrolled_credential_id` | `string\|null` | that credential's operator and ID, when found |
| `enrolled_trust_anchor_sha256` | `hex\|null` | when found: SHA-256 of that credential's stored `trust_anchor_ref` (its UTF-8 bytes), computed at read time; the table stores the reference, not a digest (`0005_operator.sql:130-138`), and `sha2` is already a service dependency (`service/Cargo.toml:19`) (lead ruling, (b)) |

A `RecoveryState` row whose `bootstrap_closed` is false still counts as
closed (identity-registry :298-299), so `instance_id` and the other state
members report it (F10). Such a row is a dead end: a bootstrap is
refused as `AlreadyClosed`, and a restore needs a closed state
(`NoRecoveryState`, `recovery.rs:1521-1527`). Making it unrepresentable
(`CHECK (bootstrap_closed)` in a new migration) is a schema change for the
user, tracked as a follow-up that the lead takes to the user.

### Operation states

Checked before the state table: an `operation_id` asked against an
unclosed state row is `server_error` (F10). Otherwise the state is decided
in this order against the rows the read statement sees (lead ruling, F1;
state names inferred):

| State | Condition | Final? |
| ----- | --------- | ------ |
| `not_found` | no row with that ID, or a row that is not an `operator_restoration` of no tenant by `deployment_operator` with `challenge_hash` and `expires_at` set (the filter of restore step 3, `recovery.rs:166-170`) | yes (inferred: an ID the client holds came from a committed issue) |
| `restored` | consumed, outcome `restored`, whatever `revoked_at` holds | yes |
| `revoked` | unconsumed, `revoked_at` set | yes: a revoked row is never consumed afterwards (`0005_operator.sql:457-462`) |
| `retired` | unconsumed, unrevoked, but the plan's instance or epoch, or `expected_revision`, is no longer the state's | yes: the epoch never decreases (`0005_operator.sql:217-234`) and the library's one write of the row, the rotation, advances epoch and revision together (`recovery.rs:619-623`; inferred for writes by other means), so the consume (`recovery.rs:580-599`) never matches again |
| `issued` | unconsumed, unrevoked, bound, `server_time < expires_at` | no |
| `expiring` | as `issued`, but `expires_at <= server_time < settles_at` | no: a restore that took its `now` before the expiry may still be running |
| `expired` | as `issued`, but `server_time >= settles_at` | no (below) |
| any other combination (consumed with outcome `issued`, say, which only a write by other means leaves), or no state row at all | `server_error` (inferred) | |

`restored` comes before `revoked` because `0005` lets a consumed operation
be revoked later (`0005_operator.sql:323-327`, :459-460), and the restore's
own check reads "consumed" before "revoked" (`recovery.rs:170-171`).

`settles_at` waits for the transaction timeout because the restore takes
`now` after `BEGIN` (`ops.rs:500-507`), and the transaction timeout bounds
everything from `BEGIN` to the end of the commit (`mod.rs:337-340`), so a
restore of this transport that took its `now` before the expiry has ended
by then. `expired` is still not final. The contract says of a refusal for
expiry that it "writes nothing and is not final, since a later call with
an earlier `now` can still consume" (identity-registry :426-429): `expired`
stays reportable, but a later write path (a library caller with an earlier
`now`, or a transport with a longer transaction timeout) may still change
what is visible.

### What it reveals, and what it does not

It returns no `M`, no plan member other than the replacement's three IDs
(and those only once restored), no request digest, no challenge hash, no
signature, no audit event, and nothing about an operation that is not a
recovery challenge: an approval or a pending gated write by that ID is
`not_found`, the same as no row.

It reveals the recovery state with the current recovery public key, a
challenge's state, whether an mTLS key is enrolled, and the SHA-256 of
that credential's trust anchor reference (b). All of it is
public data, read by a peer that is already the service UID or root with
the database's rights (`mod.rs:448-461`; OQ-TM-9). `issue_challenge`
already reads the state to build its plan (`ops.rs:416-420`), and an issue
already answers an enrolled key with `conflict` (`mod.rs:270-275`). The
public key (F4) widens what a local peer reads: lead scoping, user
informed. The audit chain's head (IR-055) is left out: the restore's events
do not name the operation (`recovery.rs:226-229`; identity-registry
:379-381), so the sequence tells the client nothing about its request.

**Where the read lives (lead ruling, Q1).** One registry function in
`recovery.rs`, beside the restore's step-3 filter, returns the closed
enum of states and the projection above, never the row. The guarantee
"no registry getter returns the operation row" (identity-registry
:358-359; `recovery.rs:165-166`) is scoped to this projection (lead
ruling, (g)): the existing getter `get_administrative_operation`
(`service/src/persistence/registry/operation.rs:448-463`, public through
`registry/mod.rs:527`) already returns the full row of whatever kinds its
caller names, so the ruling's literal text is wider than the code. The
proposed wording is contract amendment 2 below.

### Transaction, locks and the barrier

- **The transaction.** One `READ COMMITTED` transaction, read-write, with
  the transport's timeouts, always rolled back, as `preview`
  (`ops.rs:455-486`). Never `READ ONLY` and never on a replica: the barrier
  takes a row lock, which PostgreSQL refuses in a read-only transaction
  and on a standby (the `READ ONLY` refusal of `FOR SHARE` reproduced on
  PostgreSQL 16 by the reviewer; the standby refusal not verified). It
  changes no row. It draws no ID (lead ruling, F7).
- **The mutex.** It takes the transport's mutex like every request
  (`connection.rs:160-164`; `mod.rs:304-321`), so in one process it runs
  after any earlier request has ended, a cut one included.
- **The barrier (lead ruling, F6).** In a savepoint:
  `SAVEPOINT b; SELECT … FROM recovery_state FOR SHARE; ROLLBACK TO SAVEPOINT b`.
  A restore holds that row `FOR NO KEY UPDATE` from its step 2 to its commit
  (`recovery.rs:1521-1524`), and `FOR SHARE` conflicts with it, so `status`
  waits for any restore, from any process, that has locked the state,
  including one whose client connection was discarded while PostgreSQL
  still finishes its `COMMIT` (that last case not verified). Reproduced on
  PostgreSQL 16 by the reviewer: `FOR SHARE` waits for `FOR NO KEY UPDATE`
  (`FOR KEY SHARE` would not); the rollback to the savepoint releases the
  lock and the barrier still waits first; a new `FOR SHARE` overtakes a
  restore already waiting for `FOR NO KEY UPDATE` behind another holder. The
  wait
  is bounded by `lock_timeout` (`auth_unavailable`). Held for the whole
  request instead, the shared lock of overlapping `status` calls from
  several processes could keep a restore waiting for its exclusive lock
  indefinitely (starvation; inferred). An uncommitted bootstrap's row is
  invisible and is not waited for (inferred).
- **No lock after the barrier (lead ruling, F2).** After the savepoint,
  `status` runs plain `SELECT`s only. A restore locks every unrevoked
  credential `FOR NO KEY UPDATE` at step 1 before it waits for the state at
  step 2 (`recovery.rs:1517-1524`), so a `status` that held the state and
  then locked a credential would close a cycle; the reviewer reproduced it
  as a deadlock (`40P01`).
- **One statement (F6).** The state, the challenge row, the credential by
  public identity (with its trust anchor reference, hashed after the read),
  the count and the revoked page are read in one statement, one
  snapshot. `server_time` is read from the clock after the
  barrier and before that statement (F3).

### Finality, the 100 s wait, and the reconcile procedure

`status` is one more request with the same bounds: at most 100 s from the
accept on a default server (`mod.rs:361-364`; `DEFAULT_TOTAL_WAIT`,
`exchange.rs:41-45`). It cannot see the listen queue, where a request the
client gave up on may still wait (`mod.rs:364-373`). So only `not_found`,
`restored`, `revoked` and `retired` are final, and a non-null `instance_id`
(bootstrap closes once). The procedure the operator crate documents; the
client still never retries on its own (`operator/src/local/mod.rs:75`):

- **restore, outcome unknown:** `status` with its `operation_id`.
  `restored`: it committed; the reply has the replacement's IDs, and the
  revoked IDs page by `revoked_after`. `retired`, `revoked`: it did not
  commit and never will; issue a new challenge. `issued`: repeat the same
  restore, which is single use (LT-107; identity-registry :334-346): it
  restores, or is `not_restorable` because the first one committed, which
  the next `status` shows. `expiring`: ask again after `settles_at`.
  `expired`: it did not commit through this transport; issue a new
  challenge (the old one is not final in the contract's sense, above). This
  corrects itself: if the old challenge is restored after all, it rotates
  the epoch, so the new one's restore is `not_restorable` and `status` on
  the old one shows `restored`.
  **After any retry (lead ruling, (c)):** a `conflict` from the new issue
  (a late restore has enrolled the replacement's key, `ops.rs:421-432`) or
  a `not_restorable` from the repeated or new restore means: query the
  **original** `operation_id` again and act on the state it reports. A
  late restore can commit after `expired` was seen.
- **bootstrap, outcome unknown (lead rulings, F4 and (b)):** `status` with
  the bootstrap's `credential_spki`, the same DER bytes it sent.
  - `instance_id`, `recovery_public_key`, the mTLS key (`enrolled_state`
    not `not_found`) and `enrolled_trust_anchor_sha256` all equal what was
    sent (the client hashes the `trust_anchor_ref` it sent): **the current
    state matches** the request (`enrolled_admin_id`,
    `enrolled_credential_id`; no binding ID, Q8). Which request won no
    longer matters: the effects are identical.
  - `instance_id` null: repeat the same bootstrap, which the database
    closes once (`mod.rs:313-317`).
  - anything else (another instance, another recovery key, the mTLS key
    not enrolled, another trust anchor): the current state does not match;
    do not claim the bootstrap committed, and stop. With an equal instance
    and another recovery key, the recovery key the operator holds cannot
    restore this instance. The historical outcome of the differing request
    is not reconstructible from the state.
- **issue_challenge, outcome unknown:** no reconcile possible: issue
  again. A stray challenge expires unused and any restore retires the
  others (`mod.rs:399-404`). `Op::retry` stays `Retry::ReconcileFirst` for
  it (lead ruling, Q5): it writes a row and an audit event.

### Peer check, limits and audit

- **Peer:** the service UID or root only, checked before a byte is read
  (`mod.rs:448-456`), unchanged.
- **Limits:** no new limit. `max_connections`, the mutex and the statement
  timeout bound it as they bound `preview`. A flood of `status` calls can
  delay a restore by queueing on the mutex; the peer is root-equivalent, so
  no rate limit is proposed (inferred).
- **Replay:** it carries no signature and runs no consume, so it cannot
  replay, extend or spend a challenge; the TTL, single use and the binding
  of `C` are untouched (LT-107).
- **Audit and logging (lead ruling, Q7):** no audit event; it changes no
  row, so it cannot fail on the audit append. The admin read router does
  not audit reads either (no `append_audit_event` under
  `service/src/admin_http/`, checked). Unlogged, like every local request
  today (`mod.rs:44-47`, TM-15); revisited when the transport gets logging.

### Errors

| Cause | Code |
| ----- | ---- |
| peer refused | `forbidden` |
| malformed request, a missing or mistyped member, bad hex, a DER that is not one SPKI, a NUL in an ID, `revoked_after` without `operation_id` | `invalid_request` |
| a store failure, the barrier's `lock_timeout` | `auth_unavailable` |
| an operation asked against an unclosed state row, a challenge row in no state above, an unreadable time | `server_error` |

Never `conflict` or `not_restorable`; a missing row is a state, not an
error. `status` changes no row, so every code is a plain refusal, as for
`preview`, and `status` is `Retry::Safe` (lead ruling, Q5). The operator
client must not count it as a write: `exchange.rs:469` today tests
`!matches!(op, Op::Preview)`, which would make a new op a write (mutant
M9).

### Determinism and wire versioning

- For a given database state and clock, the reply bytes are fixed:
  members in a fixed order, `null` for absent values, revoked IDs in byte
  order (`ORDER BY id COLLATE "C"`, matching Rust's byte-wise `String`
  order), each page exactly `min(page size, count - held)` IDs (absent a
  tie, Part B). With the
  fixture's fixed clock and `SequentialIds` the golden lines are
  reproducible as today's are.
- The wire has no version member; an old server answers an unknown `op`
  with `invalid_request` (`mod.rs:219-224`). The transport is served
  nowhere (`mod.rs:23-27`) and `skyoauth-operator` is `publish = false`
  (`operator/Cargo.toml:9`), so no deployed peer exists.
  `tests/conformance/fixtures/_wire/local_transport.v1.json` is edited in
  place, with a dated note in its `description` (lead ruling, Q6).

## Part B: the restore reply bound

### Options

| Option | Reply | Trade-offs |
| ------ | ----- | ---------- |
| B1. Count only | `revoked_credential_count`; no IDs | Smallest; every reply needs a `status` call to see any ID. |
| **B2. Count and capped list** (ruled) | `revoked_credential_count` (exact absent a tie, below), and `revoked_credential_ids`: the first `min(count, 1000)` in byte order | The usual reply (well under 1000 operators, inferred) stays complete in one line; the rest pages through `status`. |
| B3. Paginated restore | The restore returns a page and a cursor | A restore runs once; its later pages need a read, which is B2 with `status`. |

New `restore` reply, members in this order:

```text
{"admin_id":…,"credential_id":…,"binding_id":…,"revoked_credential_count":N,"revoked_credential_ids":[…≤1000…],"recovery_key_epoch":…,"recovery_state_revision":…}
```

The list is complete exactly when its length equals the count. The rest:
`status` with the operation ID and `revoked_after` set to the last ID held,
until the count is reached.

### The cap: 1000

The page size is the same for the restore reply and for `status`, one
constant in the service, pinned in the fixture as
`framing.max_revoked_ids_per_reply` (lead ruling, F8).

- A generated credential ID is `cred_` and 26 characters, 31 bytes (tasks
  §13 D1; `service/src/ids.rs:185`), 33 as a JSON string, 34 with its comma.
  Today's golden `restored` line is 255 bytes with one ID (fixture
  `golden_replies`, case `restored`). With 1000 generated IDs and the count
  member the line is about 34 KB (computed from the fixture line), under the
  64 KiB request limit.
- The database allows a credential ID of up to 255 bytes with any
  character (`0005_operator.sql:112-114`). `serde_json` writes a control
  character as a six-byte `\u` escape, so the worst ID is 1532 bytes as a
  JSON string; 1000 of them, with the other members at their worst, are
  about 1.54 MB, 37% of the client's 4 MiB. 2700 would be the most (about
  99%). The `status` reply adds at most a 16 KiB recovery key in hex (the
  database allows 8192 bytes, `0005_operator.sql:200-202`) and three more
  IDs (`instance_id` and the two `enrolled_` IDs): about 1,559,065 bytes at
  its worst, 37.2% (the reviewer's figure; the author's estimate is within
  a few bytes), plus about 100 bytes for `enrolled_trust_anchor_sha256`.
- 1000 is round and far above any plausible number of operator credentials
  (inferred).

The client keeps `MAX_REPLY_BYTES` at 4 MiB as a defence against a
misbehaving peer, and its doc (`operator/src/local/mod.rs:111-126`) drops
the open question: the service now bounds every reply.

### One predicate for both sources (lead ruling, F5)

The restore writes `revoked_at` and the challenge's `consumed_at` from the
same `now`: `restore_operator` computes it once (`recovery.rs:1488`) and
`restore_steps` binds it to the consume (`CONSUME_CHALLENGE`, :580-581) and
to the revocation (:1548-1549). The list is therefore the credentials whose
`revoked_at` equals the operation's `consumed_at`: **membership is by
timestamp** (lead ruling, (a)), not by a record of which restore revoked
which credential.

The registry function of Q1 computes the count and a page with that
predicate. The restore reply takes its count and first page from it too,
run inside the restore's transaction after step 6, not from the revoke
statement's list: a plain statement in the restore's transaction, inside
`within` and before `finish` (`ops.rs:500-511`), after `restore_operator`
returns. No barrier on this path. A failure of it rolls the restore back:
`auth_unavailable` (or `server_error`, by the store-failure mapping of
`mod.rs:436-441`), an `UncertainCommit` at the client, and `status` then
shows `issued` (or `expiring` or `expired` once the time has passed),
assuming no other restore commits before the client polls; if one does,
`status` shows `retired` (lead ruling, (d)). So the restore reply and
`status` agree by construction, absent a tie.

**Ties.** A tie between two restores needs a clock that repeats a
microsecond (a fixed test clock, or a clock stepped back): two restores
need two signed challenges, and the second can only be issued at the epoch
the first one's commit created (a challenge of the earlier epoch is
`retired` once the first commits), so in normal operation its `now` is
later. On a tie, `status`'s list may include the other restore's
credentials. A revocation by another writer at the identical microsecond
is listed too (`revoke_admin_credential`, `operator.rs:727-745`, has no
online caller yet; inferred). Over-inclusion only. A revocation at the
same microsecond after the restore makes `status`'s count exceed the
reply's, or change between two pages; the client restarts the walk from
`status` alone. The count is exact and the pages stable **absent a tie**.

**Per-restore membership: recorded as an option, not built** (lead ruling,
(a) and Q4). A column naming the revoking operation on `admin_credential`,
added by an in-place, pre-beta amendment of `0005`, would make membership
exact. It has the shape of the nonce ruling of the recovery proposal
("recorded as an option, not built",
`docs/proposals/recovery-verified-response.md:441-443`; the user,
2026-11-24, `docs/threat-model.md:926-929`).

### Atomicity and audit

- **Atomicity: unchanged.** The restore still revokes every unrevoked
  credential in one statement in its one transaction (`recovery.rs:190-197`,
  step 6). The cap applies to the reply only; a truncated list is a
  success, not an unknown outcome.
- **Where it lives:** the count and page query in `recovery.rs` (Q1's
  function), called by the transport (`ops.rs:518-525`) in the restore's
  transaction. The library's `Restored` keeps every ID
  (`recovery.rs:775-789`), so no registry test of the restore changes; the
  service still holds every ID in memory (`fetch_all`, `recovery.rs:1548`),
  bounded by the table, not by the wire (inferred: acceptable at operator
  scale).
- **Audit: unchanged.** Neither event lists the revoked IDs or their count
  (step 10, `recovery.rs:217-229`; the envelope has no such member, IR-056).
  The durable record is each credential's `revoked_at`, set once
  (`admin_credential_set_once`, `operator.rs:59-60`).

## Not verified

- The serde default for a missing `Option` member, and the deserializer
  that refuses it: serde's documentation, not tried.
- PostgreSQL behaviour still unverified: that a `COMMIT` received before
  the client connection is discarded keeps the row lock until it ends, and
  that a row lock is refused on a standby. Reproduced on PostgreSQL 16 by
  the reviewer, not by the author: `FOR SHARE` waits for
  `FOR NO KEY UPDATE` and `FOR KEY SHARE` does not; `ROLLBACK TO SAVEPOINT`
  releases the lock and the barrier still waits; `READ ONLY` refuses
  `FOR SHARE`; a new `FOR SHARE` overtakes a waiting `FOR NO KEY UPDATE`;
  the barrier run inside the restore's own transaction keeps the parent's
  lock, and a plain count there sees the restore's own writes without
  waiting; the deadlock of F2 (`40P01`).
- The size figures: computed from the fixture's golden line and from
  `serde_json`'s escape rules (as `operator/src/local/wire.rs:162-185`
  restates them), not by serializing 1000 IDs.
- That no online path revokes a credential yet (the tie of Part B); that
  two restores cannot share a `now` without a repeating clock rests on
  reading the code (the `retired` rule), not on a test.
- C4's scope.

## Rulings

All by the lead, 2026-11-27, on review of this proposal; the two rulings it
answers are the user's (see the status line).

- **Design:** A1 `status`, B2 (a count and a capped list, exact absent a
  tie), the `FOR SHARE` barrier. Findings F1 to F11 applied as written
  above.
- **Third round, (a) to (h):** membership by timestamp, ties only with a
  repeating clock, per-restore membership recorded as an option, not built
  (a); the trust-anchor digest and "the current state matches" (b); query
  the original `operation_id` after a `conflict` or `not_restorable` (c);
  the failed page query's outcomes assume no other restore commits first
  (d); the parser checks shape and in-page order, the iterator the rest
  (e); `Op::Status` with the fixture PR (f); the getter guarantee scoped
  to the `status` projection (g); the M13 and unconsumed-revoked tests
  (h).
- **F4 (lead scoping, user informed):** `recovery_public_key` in the reply
  and the bootstrap reconcile rule.
- **Q1:** a registry function in `recovery.rs` returning a closed enum,
  next to the restore's step-3 filter; the ruling at identity-registry
  :358-359 is amended explicitly (amendment 2).
- **Q2:** the `credential_spki` lookup stays.
- **Q3:** `expired` stays, with the transaction-timeout margin
  (`settles_at`); it is not final (identity-registry :426-429).
