# Migrations

Versioned PostgreSQL migrations for `skyoauth-service`, embedded into the
binary with `sqlx::migrate!` and applied only by `skyoauth-service migrate`.
sqlx reads only files named `<VERSION>_<DESCRIPTION>.sql`, so this README is
not a migration.

## Conventions

- **Forward-only.** A migration that has been applied anywhere is never
  edited, renamed or removed; the runner refuses a changed checksum, and the
  checksum covers comments too. Fix forward with a new file. There are no
  down migrations.
- **Contiguous versions:** `0001_…`, `0002_…`, and so on. A unit test checks
  this; it is a test-time rule, not something the runner enforces.
- **One transaction per file.** sqlx wraps each file in a transaction. Never
  use `-- no-transaction`, and never write `BEGIN`, `COMMIT`, `ROLLBACK`,
  `END` or `ABORT` at the top level; a unit test lints for them.
- **IDs** are opaque text generated by the service, never chosen by the
  caller. Their format belongs to the ID-generation work, not to SQL
  defaults.
- **Collation:** every text column that holds an ID, a key, a reference to
  one or an enumeration value is `text COLLATE "C"`, so it compares, sorts
  and indexes byte-wise whatever the database's default collation is, and a
  foreign key always pairs two `"C"` columns. Only human-readable names and
  free text keep the default collation. This holds for every later migration.
- **Tenant-scoped rows** carry `tenant_id` with a foreign key to the tenant.
  Foreign keys never use `ON DELETE CASCADE` across authority boundaries;
  records are soft-disabled through a status column instead.
- **Types:** timestamps are `timestamptz`; revisions are `bigint` and only
  increase.
- **Every function a migration creates pins its `search_path`**, with
  `pg_temp` last: `SET search_path = pg_catalog, pg_temp`, or, for a
  function that reads tables, `pg_catalog, <schema>, pg_temp` with every
  table named with its schema. A function otherwise resolves names through
  the caller's `search_path`, in which `pg_temp` comes first for tables and
  types: any role with DML grants and the default `TEMP` privilege could
  shadow a table, or a type such as `jsonb`, with a temporary table, and a
  role that can create objects in some schema could put it ahead of
  `pg_catalog` and shadow built-in functions and operators (`=`, `+`,
  `to_jsonb`), turning a guard into a no-op. Logical-replication apply and
  `pg_dump` restores, which run with an empty `search_path`, would not find
  the tables. With the pin, built-ins resolve in `pg_catalog`, and `pg_temp`,
  never searched for functions or operators, can no longer shadow a type.
  Migrations do not hard-code `public`: `0002` resolves the schema with
  `current_schema()` at migrate time and creates table-reading functions
  with `EXECUTE format(…)` in a `DO` block, passing the body as a quoted
  literal (`%L`), never inside a dollar-quoted one, since a schema name may
  contain `$$`. The one exception is `skyoauth_reject_mutation()` from the
  frozen `0001`: it resolves no names (it only raises with `TG_OP` and
  `TG_TABLE_NAME`), so it needs no pin. A catalog test checks every other
  function.
- **Append-only tables** attach `skyoauth_reject_mutation()` (from `0001`)
  and enable the triggers with `ENABLE ALWAYS`, so they also fire under
  `session_replication_role = replica`:

  ```sql
  CREATE TRIGGER <table>_append_only
      BEFORE UPDATE OR DELETE ON <table>
      FOR EACH ROW EXECUTE FUNCTION skyoauth_reject_mutation();
  ALTER TABLE <table> ENABLE ALWAYS TRIGGER <table>_append_only;
  CREATE TRIGGER <table>_no_truncate
      BEFORE TRUNCATE ON <table>
      FOR EACH STATEMENT EXECUTE FUNCTION skyoauth_reject_mutation();
  ALTER TABLE <table> ENABLE ALWAYS TRIGGER <table>_no_truncate;
  ```

  A rejected write fails with the project SQLSTATE `SK001`, which no
  PostgreSQL error uses, so callers can tell it apart from constraint
  errors such as `23001` (`restrict_violation`).

## What 0002 adds

`0002_foundation.sql` is the first slice of the M1a domain schema (T10.1):
`tenant`, `principal`, `instance_security_policy`, `egress_allowlist_entry`,
`audit_event` and `audit_chain_head`. Comments marked `(inferred)` are
choices the specifications do not dictate. Besides the append-only guard it
adds two shared guard functions, both failing with `SK001`:
`skyoauth_reject_immutable_change(column, ...)` rejects an `UPDATE` that
changes a named column (an argument naming no column is a plain `P0001`
error, so a typo fails the first update), and `skyoauth_check_revision()`
requires revision 1 on insert and exactly +1 on every update. Policy and
egress rows are never deleted.

- **Audit sink.** `audit_sink_config_digest` is `NULL` when no sink is
  configured or the sink configuration was removed (IR-053), and non-empty
  otherwise. `audit_sink_validated_at` must correspond to the current
  digest: it can only be set while a digest is, and an `UPDATE` that changes
  the digest must also change it, to `NULL` or to a later time (`SK001`).
  From `NULL`, any time is accepted. The database cannot tell which digest a
  later timestamp validated; that stays with the service.
- **Egress destinations** reject whitespace and control characters
  (`[[:space:][:cntrl:]]`: under `"C"`, `[:space:]` is ASCII whitespace
  only, and `[:cntrl:]` is the C0 and C1 controls U+0000–U+001F and
  U+007F–U+009F in every collation) and values over 2048 bytes, well below
  the btree limit of the unique index. In a UTF8 database, which the schema
  assumes (inferred), other Unicode spaces and format characters, such as
  U+00A0, U+2028 and U+200B, pass; everything else about the URL is
  validated by the service.
- **Audit chain.** It is enforced in order: an event must extend the chain
  head (`sequence` = head + 1, `prev_hash` = head hash; the first event has
  a `NULL` `prev_hash`), checked when the event is inserted; the head may
  only advance by one to an existing event; and a deferred check fails the
  commit if the head has not reached every event the transaction inserted.
  `audit_event (tenant_id, sequence)` is indexed for per-tenant reads in
  chain order.
- **Absent values in audit events.** `previous_revision` and
  `new_revision` are `NULL` when there is no such revision (a create has no
  previous revision; tenants and principals carry none yet), as are
  `prev_hash` for the first event and `tenant_id` for instance-scope events.
  There is no sentinel: revisions start at 1 and 0 is rejected. The event
  hash encoding (identity-registry IR-056; see Follow-ups) must encode an absent
  value differently from every present one (for example JSON `null` against
  a number), so that adding or dropping a value changes the hash.
- **Instance-scope events** (lead decision): the startup event that records
  the `single_actor_mode` mirror (IR-053) and the sink-change event have
  `tenant_id` `NULL`, the policy row's `instance_id` as `object_id`, and the
  row's real revisions before and after the write in `previous_revision`
  and `new_revision`. `instance_id` is a lowercase hyphenated UUIDv7,
  generated once at first bootstrap and immutable (IR-057). Events the
  service writes on its own record the reserved actor
  `{"type": "system", "id": "system"}`, never a principal or an operator
  identity (IR-058). `action` is a dotted lowercase `<resource>.<verb>` name
  (identity-registry IR-059). The decision fixes only that syntax: IR-059
  lists examples, and the action names, including those of these two
  events, are open until the audit writer (OQ-IR-15). These are lead
  decisions (2026-11-20, OQ-IR-14), provisional until the audit writer
  ships.

The database does not enforce these rules; the service must:

- generate every ID and `Tenant.secret_namespace` (T10.2), and resolve
  secret references only within the owning tenant's namespace (IR-034);
- insert the single `instance_security_policy` row at bootstrap (the schema
  allows at most one, not exactly one);
- keep `single_actor_mode` and the audit sink fields read-only online, so
  only the startup mirror of deployment configuration writes them (IR-053),
  and set `audit_sink_validated_at` only from a validation of the current
  configuration;
- require the second approver for the `widening_second_approver` toggle and
  for adding or re-enabling egress entries (IR-052, IR-054);
- check the expected revision of every write (compare and set);
- disable tenants and principals through `status` instead of deleting them
  (`0006` rejects a `DELETE` of either);
- validate `exact_destination` as an exact URL (IR-152);
- compute event and head hashes (the database only stores them);
- append audit events in this order: write the domain rows first, then lock
  the chain head (`SELECT … FOR UPDATE`), take `sequence` = head + 1 and
  `prev_hash` = head hash from that locked row, insert the event, advance the
  head and commit. The head lock comes last: a transaction that holds it
  and then waits for a domain row held by a transaction that waits for the
  head deadlocks, and one of them fails with `40P01`.

Concurrent appenders queue on the head row, which the insert trigger locks
too. A writer that took its `sequence` from a head another transaction has
since advanced waits for that transaction and then fails with `SK001` under
`READ COMMITTED` (the default), or with `40001` under `REPEATABLE READ` or
`SERIALIZABLE`. The database does not retry; a writer that locked the head
first gets the committed head and succeeds.

## What 0003 adds

`0003_resource_servers.sql` is the second slice of the M1a domain schema
(T10.1): the instance audience registry of identity-registry §7 and ADR-018,
as `resource_server`, `audience_tenant_assignment`,
`resource_server_checker` with its tenant rows in
`resource_server_checker_tenant`, and `resource_action`. It adds no
function: every table reuses `skyoauth_reject_immutable_change(…)` from
`0002`, and every table except `resource_server_checker_tenant`, which has
no revision, also `skyoauth_check_revision()`; all their triggers are
`ENABLE ALWAYS`. `status` is `enabled` or `disabled` (inferred; the sources
speak of disabling and re-enabling, and of an "active" assignment, read as
`enabled`). Every column is `NOT NULL`.

- **Keys.** `resource_server.audience` is globally unique and exact
  (IR-070) and compared byte-wise. `(resource_server_id, action_name)` is
  unique (inferred: the service looks up "the" persisted action of a
  resource server, API-072). One assignment per resource server and tenant
  (inferred from ADR-018 item 6 and the single assignment ceiling of
  IR-062). `public_mtls_identity` is unique across all checkers, disabled
  ones included, so an identity is bound to one resource server (IR-090;
  including disabled rows is inferred).
- **Free-text keys** are bounded and cleaned as `exact_destination` is in
  `0002` (lead decision, 2026-11-20): `audience`, `action_name` and
  `public_mtls_identity` are non-empty and at most 2048 bytes, so an
  over-long value fails with `23514` instead of the btree error `54000`;
  `audience` and `action_name` also reject whitespace and control characters
  (`[[:space:][:cntrl:]]`, as for egress destinations). `public_mtls_identity`
  may contain spaces, since its form is not specified and may be a subject
  DN. The audience syntax stays open (OQ-IR-9), and Unicode normalization
  (NFC or NFD) of these values is a service rule: the database compares
  bytes, so two spellings of one name are two keys.
- **ID column bounds.** Every ID column of `0003`, own IDs and reference
  columns alike, is at most 255 bytes. `resource_server.id` and `tenant.id`
  are bounded by lead decision (2026-11-20), `tenant.id` with
  `tenant_id_octet_length_check`, a forward-only constraint on the frozen
  `0002` table; every other ID column (`id` of the assignment, checker and
  action) and every reference column is bounded the same way (inferred).
  Without its bound, an over-long ID would fail with the btree error `54000`
  on its key's index. The reference columns need their own bound too: a
  `CHECK` runs before the row enters any index, but the foreign key check
  runs after it, so an over-long reference naming a missing row would
  otherwise fail with `54000` as well. With the bounds, an over-long
  ID value fails with `23514` even when it names a missing row, and every
  composite key stays below the btree limit of about 2700 bytes even for
  values that do not compress: `(resource_server_id, action_name)` at most
  255 plus 2048 bytes, the checker's `(id, resource_server_id)`, the child
  primary key `(checker_id, tenant_id)` and the assignment's
  `(tenant_id, resource_server_id)` at most 255 plus 255.
  `0003` also bounds the unique `tenant.secret_namespace` to 255 bytes with
  `tenant_secret_namespace_octet_length_check` (lead decision, 2026-11-20;
  length only, no character rule). Every primary key, unique and foreign key
  column of the five tables and of `tenant` therefore has a named
  `octet_length` bound: 255 bytes for IDs, references and the namespace, 2048
  for the free-text keys.
- **Immutable selectors** (`SK001`): the IDs (tasks §3 "IDs/names"), and
  (inferred) the audience, each row's `resource_server_id`, an assignment's
  `tenant_id` and an action's `action_name`; every column of a checker
  tenant row (lead decision, 2026-11-20). A checker's identity may be
  rotated (inferred).
- **Checker tenants** (lead decision, 2026-11-20): the model and API field
  `ResourceServerChecker.allowed_tenant_ids` is derived from the rows of
  `resource_server_checker_tenant` (`checker_id`, `resource_server_id`,
  `tenant_id`), primary key `(checker_id, tenant_id)`. Composite foreign keys
  to the checker's `(id, resource_server_id)` and to the assignment's
  `(tenant_id, resource_server_id)` hold the existence half of OQ-ADR018-1:
  a checker can only list a tenant that has an assignment to its own
  resource server (`23503` otherwise), whatever that assignment's status.
  The set is edited by inserting and deleting rows; the rows have no status
  or revision of their own (inferred: the set is part of the revisioned
  checker).
- **References.** Assignments, checkers and actions reference their
  resource server, and assignments their tenant, with no action on delete or
  update and not deferrable. Each foreign key is named, so the service can
  map a `23503` by its constraint name:

  | Constraint                                           | Columns                                            |
  | ---------------------------------------------------- | -------------------------------------------------- |
  | `audience_tenant_assignment_resource_server_id_fkey` | `resource_server_id` → `resource_server`           |
  | `audience_tenant_assignment_tenant_id_fkey`          | `tenant_id` → `tenant`                             |
  | `resource_server_checker_resource_server_id_fkey`    | `resource_server_id` → `resource_server`           |
  | `resource_server_checker_tenant_checker_fkey`        | `(checker_id, resource_server_id)` → the checker   |
  | `resource_server_checker_tenant_assignment_fkey`     | `(tenant_id, resource_server_id)` → the assignment |
  | `resource_action_resource_server_id_fkey`            | `resource_server_id` → `resource_server`           |

  The unique
  `(tenant_id, resource_server_id)` of the assignment is the target for
  composite foreign keys from later tenant-owned records that name an
  audience (grants, services, clients, origins, human policies; IR-080), so
  they cannot name an audience assigned only to another tenant.

- **Named checks.** The bounds and character rules are named too, so the
  service can map a `23514` by its constraint name. Two names abbreviate
  `resource_server_id` to `server_id`, because the full name would exceed
  the 63-byte identifier limit:

  | Constraint                                                        | Rule                                        |
  | ----------------------------------------------------------------- | ------------------------------------------- |
  | `tenant_id_octet_length_check`                                    | `tenant.id` at most 255 bytes               |
  | `tenant_secret_namespace_octet_length_check`                      | `tenant.secret_namespace` at most 255 bytes |
  | `resource_server_id_octet_length_check`                           | `id` at most 255 bytes                      |
  | `resource_server_audience_no_space_check`                         | `audience` has no whitespace or controls    |
  | `resource_server_audience_octet_length_check`                     | `audience` at most 2048 bytes               |
  | `audience_tenant_assignment_id_octet_length_check`                | `id` at most 255 bytes                      |
  | `audience_tenant_assignment_server_id_octet_length_check`         | `resource_server_id` at most 255 bytes      |
  | `audience_tenant_assignment_tenant_id_octet_length_check`         | `tenant_id` at most 255 bytes               |
  | `resource_server_checker_id_octet_length_check`                   | `id` at most 255 bytes                      |
  | `resource_server_checker_resource_server_id_octet_length_check`   | `resource_server_id` at most 255 bytes      |
  | `resource_server_checker_public_mtls_identity_octet_length_check` | `public_mtls_identity` at most 2048 bytes   |
  | `resource_server_checker_tenant_checker_id_octet_length_check`    | `checker_id` at most 255 bytes              |
  | `resource_server_checker_tenant_server_id_octet_length_check`     | `resource_server_id` at most 255 bytes      |
  | `resource_server_checker_tenant_tenant_id_octet_length_check`     | `tenant_id` at most 255 bytes               |
  | `resource_action_id_octet_length_check`                           | `id` at most 255 bytes                      |
  | `resource_action_resource_server_id_octet_length_check`           | `resource_server_id` at most 255 bytes      |
  | `resource_action_action_name_no_space_check`                      | `action_name` has no whitespace or controls |
  | `resource_action_action_name_octet_length_check`                  | `action_name` at most 2048 bytes            |

  The other checks on the five tables keep the names PostgreSQL generates
  (the list domains carry their own checks, which are not table
  constraints):
  - `resource_server`: `resource_server_id_check`,
    `resource_server_audience_check`, `resource_server_name_check`,
    `resource_server_constraint_versions_check`,
    `resource_server_status_check`, `resource_server_revision_check`;
  - `audience_tenant_assignment`: `audience_tenant_assignment_id_check`,
    `audience_tenant_assignment_constraint_versions_check`,
    `audience_tenant_assignment_status_check`,
    `audience_tenant_assignment_revision_check`;
  - `resource_server_checker`: `resource_server_checker_id_check`,
    `resource_server_checker_public_mtls_identity_check`,
    `resource_server_checker_status_check`,
    `resource_server_checker_revision_check`;
  - `resource_action`: `resource_action_id_check`,
    `resource_action_action_name_check`, `resource_action_status_check`,
    `resource_action_revision_check`;
  - `resource_server_checker_tenant`: none.

- **Lists** are `jsonb` arrays checked through three domains, so each rule
  is written once (a domain `CHECK` is stored as an expression tree and
  resolves no names at run time): `skyoauth_scope_list` holds RFC 6749
  scope tokens (IR-066), `skyoauth_profile_list` `wif`, `human_cli` and
  `human_session` (token-profiles §3), and `skyoauth_string_list` non-empty
  strings (`required_resource_dimensions`; inferred). The scope domain
  checks the IR-066 grammar, not only non-empty strings (lead decision,
  2026-11-20).
  `constraint_versions` only has to be an array: the type of a version and
  its relation to the constraints `version` member are open (OQ-TP-7). Empty
  arrays and duplicate elements are accepted (inferred: no source forbids
  them). An empty requirement (`required_scopes`,
  `required_resource_dimensions`) requires nothing; an empty ceiling
  (`scopes`, `allowed_profiles`, `allowed_scopes`, `accepted_profiles`)
  allows nothing, so it fails closed.
- **M1a fields only.** `resource_action` has no stream fields
  (`stream_capable`, `max_stream_duration_seconds`, `stream_class`,
  `max_session_lease_seconds`); T14.4 adds them in M1b.
  `live_check_required` has no default (inferred): the service states it.

The database does not enforce these rules; the service must:

- validate the audience syntax (OQ-IR-9), normalize the Unicode form of
  audiences and action names, canonicalize `public_mtls_identity` before it
  is stored, and parse, pin and match the checker's mTLS certificate;
- check scope vocabulary: that assignment and action scopes lie within the
  resource server's scopes, and that profiles and constraint versions do
  too, where a source requires it (IR-062, IR-110, IR-141);
- give `constraint_versions` its meaning and check that each listed
  version exists;
- leave out of a checker's effective tenant set every tenant whose
  assignment is disabled, without editing its rows, so that re-enabling the
  assignment restores it (the other half of OQ-ADR018-1), and advance the
  checker's revision when its tenant rows change;
- refuse references outside an enabled same-tenant assignment at write and
  at issuance (IR-080, IR-081); a composite key proves only that the
  assignment exists;
- let only instance `security_admin` write these tables (API-147); who may
  assign an audience is authorization, not schema;
- reject out-of-range or contradictory action rules (IR-103);
- disable instead of deleting (`0006` rejects a `DELETE` of the four
  revisioned tables; checker tenant rows stay deletable), check the expected
  revision of every write and write the audit event in the same
  transaction.

## What 0004 adds

`0004_trust_binding_grant.sql` is the third slice of the M1a domain schema
(T10.1): `trust_keyset`, `trust_keyset_version`, `trust_source`,
`principal_binding`, `service_identity` and `service_grant`, with the list
tables `service_identity_resource_server`, `service_grant_binding` and
`service_grant_resource_server`. All of them are tenant-owned, and every
reference between them is a composite foreign key to a unique key of the
target that starts with `(tenant_id, id)`, so no reference crosses tenants
(IR-031). It reuses `skyoauth_reject_immutable_change(…)` and
`skyoauth_check_revision()` from `0002` and the list domains of `0003`, and
adds one function, `skyoauth_service_grant_has_binding()`. Every trigger is
`ENABLE ALWAYS`. `status` is `enabled` or `disabled` (inferred, as in
`0003`), and every table but the keyset versions and the list tables carries
a `revision`. The single-use replay table (T10.9) and the policy revision are
not part of it.

- **Keys and bounds** follow `0003`. Every ID column, own ID or reference,
  is at most 255 bytes; every name, a unique free-text key per table and
  tenant (IR-021; disabled rows included, inferred), is non-empty, at most
  2048 bytes and free of whitespace and control characters
  (`[[:space:][:cntrl:]]`; inferred from the `0003` rule for names, lead
  decision 2026-11-20). So an over-long value fails with `23514` from its
  named check, also when it names a missing row, never with the btree error
  `54000`, and every composite key stays below the btree limit even for
  values that do not compress: three IDs at most 765 bytes, a tenant ID and
  a name at most 2303 bytes. Names keep the database collation; IDs and the
  exact strings below are `COLLATE "C"`. IDs reject only an empty value, as
  in `0003`.
- **The character rule does not follow the collation.** Each
  `<table>_<column>_no_space_check` is
  `CHECK ((<column> COLLATE "C") !~ '[[:space:][:cntrl:]]')`, so it judges a
  name by the same classes on every instance: `[:space:]` is ASCII
  whitespace and `[:cntrl:]` U+0000–U+001F and U+007F–U+009F. U+0085 is
  rejected and U+3000 accepted everywhere. Without the `COLLATE "C"`, a
  name column, which has the database collation, would reject U+3000,
  U+1680, U+2000 and U+2028/U+2029 under `en_US.utf8` and accept them under
  `C`, so a dump of a `C` database could fail to restore into an
  `en_US.utf8` one.
- **Exact strings.** `exact_issuer`, `discovery_url`, `token_review_endpoint`,
  `ca_bundle_ref`, `ca_fingerprint`, `reviewer_credential_ref` and the
  version `fingerprint` are compared or resolved exactly. They get the
  egress destination rules of `0002`: non-empty, no whitespace or control
  character, at most 2048 bytes (inferred; none of them is indexed).
  `cluster_id` is an opaque server-generated ID owned by its source
  (OQ-ADR011-1), so it is bounded as an ID and unique across sources
  (inferred).
- **Unicode normalization is a service rule.** The database compares bytes:
  it neither normalizes nor rejects unnormalized names, issuers or claim
  values, so two spellings of the same text are two values.
- **`principal`.** `0004` adds `principal_tenant_id_id_kind_key`
  (`UNIQUE (tenant_id, id, kind)`) to the frozen `0002` table, and, because
  that is a new key, the forward-only bounds `principal_id_octet_length_check`
  and `principal_tenant_id_octet_length_check` (255 bytes). A binding and a
  grant actor reference `(tenant_id, id, kind)` with a constant `'workload'`
  column, and a service identity with a constant `'service'` column, so the
  database pins the principal kind as well as the tenant (inferred
  mechanism). The 255-byte bound is a lead decision (2026-11-20),
  consistent with tenant IDs in `0003`: IDs are server-generated, and no M1a database is deployed.
  Up to `0003` the database accepts longer principal IDs, and `0004`
  validates the new checks against existing rows. Upgrade precondition:
  before `0004` is applied to a populated database,
  `select count(*) from principal where octet_length(id) > 255 or octet_length(tenant_id) > 255`
  must return 0.
- **Trust sources** (ADR-005 item 1). `kind` fixes which fields are set:
  `discovery_url` exactly for `oidc_discovery`, `jwks_keyset_id` exactly for
  `uploaded_jwks`, and `cluster_id`, `token_review_endpoint`,
  `ca_bundle_ref`, `ca_fingerprint`, `reviewer_credential_ref` and
  `review_timeout_ms` all for `kubernetes_token_review` and none otherwise;
  `algorithms` is set for every kind but TokenReview, which also requires
  `projected_service_account` (each inferred).
  `stale_revocation_acknowledged` is `true` exactly for
  `projected_service_account` on `oidc_discovery` or `uploaded_jwks`, and
  `NULL` elsewhere (IR-151; `false` is rejected, inferred). `single_use`
  replay needs `on_demand_jwt` on `oidc_discovery` or `uploaded_jwks`
  (OQ-ADR005-2). `discovery_url` and `token_review_endpoint` are not foreign
  keys to egress entries: a write that leaves them unchanged must not fail
  for a missing or disabled entry (IR-152).
- **Keysets and versions.** A version holds a JWK Set whose `keys` is a
  nonempty array of objects (nonempty inferred), none with a private or
  symmetric member (`d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`, `k`), so a
  private-key upload is rejected here too (ADR-005 items 2 and 8). Versions
  are immutable (tasks §3 "Ownership"); that `status` alone may change is
  inferred. `expires_at`, when set, is after `effective_at` (inferred);
  versions may overlap.
- **Bindings.** `profile` is `github_production`, `kubernetes_production`
  or `generic_production` (the examples of ADR-016 item 4, taken as the
  whole set, inferred); `claim_match_policy` is a nonempty object of string
  values (string values only, inferred).
- **Grants.** A direct grant has no `target_service_id`; delegation and
  impersonation name a same-tenant service identity (IR-045,
  OQ-ADR006-1). An impersonation grant is stored only `disabled` with
  `activation_state = 'requires_reapproval'` (design §5.6), and the other
  modes carry `not_required` (inferred). `default_scopes`, when set, is
  nonempty and within the grant's `scopes` (IR-063). `max_ttl` is in
  seconds, 1 to 300 (unit inferred from the export name, OQ-IR-6).
- **Immutable selectors** (`SK001`): the IDs (tasks §3 "IDs/names"), every
  column of a keyset version but `status` (versions are immutable, tasks §3
  "Ownership"), and (inferred) the owning tenant everywhere, a source's
  `kind`, `cluster_id` and `jwks_keyset_id`, a binding's source and
  principal, a grant's actor, target and mode, and every column of a list
  row.
- **List tables.** `ServiceIdentity.resource_server_ids`,
  `ServiceGrant.resource_server_ids` and `ServiceGrant.allowed_binding_ids`
  are rows, as checker tenants are in `0003`; they have no status or
  revision of their own (inferred), and a row is added or deleted, never
  updated. An audience row references
  `audience_tenant_assignment (tenant_id, resource_server_id)`, so it names
  an audience assigned to the owner's own tenant (the existence half of
  IR-080). A binding row carries the grant's actor in both references, so
  it names only a same-tenant binding of that actor (ADR-022 item 13). A
  deferred, `ENABLE ALWAYS` constraint trigger
  (`skyoauth_service_grant_has_binding()`, pinned `search_path`, tables
  named with the schema) fails the commit with `SK001` when a grant created
  in the transaction has no binding row, or the last binding row of a grant
  that still exists was deleted (identity-registry §10). It locks the grant
  row with `FOR NO KEY UPDATE`, and under `REPEATABLE READ` and
  `SERIALIZABLE` also the grant's remaining binding rows with
  `FOR KEY SHARE`; see "Concurrent binding removals" below.
- **Empty arrays.** Nonempty: `trust_source.audiences`, `algorithms` when
  set, `default_scopes` when set, the JWK Set `keys`, `claim_match_policy`
  and a grant's binding rows. May be empty: `service_grant.scopes`,
  `service_identity.max_scopes` and the audience rows of a service or
  grant. An empty ceiling or audience set allows nothing, so it fails
  closed; it never means "unconstrained" (inferred). A `NULL`
  `default_scopes` means the grant has no defaults, so a request without
  scopes fails (IR-063).
- **Empty objects.** The database accepts `'{}'` for `proof_bounds`,
  `service_identity.max_resource_constraints` and
  `service_grant.resource_constraints`; it checks only that each is an
  object. For the two constraint ceilings IR-121 and IR-140 already make the
  service fail closed. For `proof_bounds` the service applies its defaults:
  an empty object never means unbounded.
- **Not NULL.** Every column is `NOT NULL` except the fields the model marks
  optional (`trust_keyset_version.expires_at`,
  `service_grant.target_service_id`, `default_scopes` and `valid_until`)
  and the kind-specific trust source fields above. No column of a composite
  foreign key is nullable except `jwks_keyset_id` and `target_service_id`,
  which `CHECK`s tie to `kind` and `mode`; a `NULL` elsewhere would make
  `MATCH SIMPLE` skip the check.
- **References.** Every foreign key takes no action on delete or update, is

The database does not enforce these rules; the service must:

- refuse an audience outside an enabled same-tenant assignment at write and
  at issuance (IR-080, IR-081): the composite key proves only that the
  assignment exists, whatever its status; and keep a delegation grant's
  audience within its target service's audiences (IR-083);
- check `discovery_url` and `token_review_endpoint` against an enabled
  egress entry of the matching purpose when they are written (IR-152), and
  validate them as URLs;
- resolve `ca_bundle_ref` and `reviewer_credential_ref` only within the
  tenant's secret namespace (IR-034);
- check that a binding's template fits its source, require the predicates
  each template demands (ADR-016 item 4), and never match a disabled
  binding;
- check JWK algorithms, key sizes, `kid` conflicts and fingerprints of an
  upload (T11.3);
- keep `default_scopes` and `scopes` within every other ceiling (service,
  assignment, resource server; IR-063) and check resource constraints
  against their schemas (IR-123, IR-141);
- keep an impersonation grant dormant when it is edited or reapproved
  (design §5.6; T10.11): the `CHECK`s fix only its stored state;
- create a service principal and its service identity in one transaction
  (identity-registry §5.1);
- generate every ID, `cluster_id` included, and normalize the Unicode form
  of names, issuers and claim values where a source requires it;
- advance the parent's revision when its list rows change, check the
  expected revision of every write and write the audit event in the same
  transaction;
- hard-delete a binding or grant only under ADR-008 item 3, deleting a
  grant's list rows first; disable the other records instead. `0006`
  checks that the row is disabled, and the foreign keys reject it while a
  grant row references it; that no approval or audit-required record
  references a binding stays with the service.

Concurrent binding removals: of two transactions that each delete a
different one of a grant's last two binding rows, at most one commits, at
every isolation level. Under `READ COMMITTED` (the default) the check sees
committed rows: the grant lock makes the later transaction wait for the
earlier one, see its delete and fail with `SK001`. Under `REPEATABLE READ`
and `SERIALIZABLE` the check reads the transaction's snapshot, which still
shows the other transaction's deleted row, so it also locks the grant's
remaining binding rows with `FOR KEY SHARE`: the later transaction fails
with `40001`, or `40P01` when the two wait for each other. That lock is
taken only under `REPEATABLE READ` and `SERIALIZABLE`: under
`READ COMMITTED`, and `READ UNCOMMITTED`, which PostgreSQL runs as
`READ COMMITTED`, it would turn the `SK001` into a deadlock. The database does not retry. Because the check runs with the
caller's privileges, a role that creates grants or deletes binding rows
needs `UPDATE` and `SELECT` on `service_grant` and `SELECT` on
`service_grant_binding`, and under `REPEATABLE READ` or `SERIALIZABLE` also
`UPDATE` on `service_grant_binding` (see Follow-ups). The service's revision
compare-and-set on the grant, done for every list change, remains the
first line.

## What 0005 adds

`0005_operator.sql` is the fourth slice of the M1a domain schema (T10.1):
`admin_identity`, `admin_credential`, `admin_role_binding`,
`recovery_state`, `administrative_operation` and `consumed_assertion`, named
as in the logical model (tasks §3). It also adds the single-use replay table
that "Not done in `0004`" lists (T10.9). It reuses
`skyoauth_reject_immutable_change(…)`, `skyoauth_check_revision()` and
`skyoauth_reject_mutation()` and adds three guard functions,
`skyoauth_reject_change_once_set(…)`,
`skyoauth_check_recovery_key_rotation()` and
`skyoauth_reject_consume_after_revoke()`. None reads a table, so each pins
`search_path` to `pg_catalog, pg_temp`. Every trigger is `ENABLE ALWAYS`
and raises `SK001` for a row it rejects.

- **Authority.** Operators, their credentials and the recovery state are
  instance authority: instance security_admin enrolls operators and scoped
  roles and manages recovery policy (design §7.2), and operators are not
  principals (identity-registry §5.2). These tables have no tenant owner. A
  role binding and an administrative operation may name one tenant
  (`tenant_id`, `NULL` for the instance). They reference `tenant` with a
  plain foreign key, as an audience assignment does in `0003`; `tenant` has a
  single-column key, so the "composite" key of the brief is that plain key
  (inferred). `consumed_assertion` is tenant-owned: its composite
  `(tenant_id, trust_source_id)` key keeps a proof on a source of its own
  tenant (IR-031).
- **Keys and bounds** follow `0003` and `0004`. Every ID and reference column
  is at most 255 bytes, and the exact strings `public_identity`,
  `trust_anchor_ref` and `kind` are at most 2048 bytes. Each bound is a named
  check, so an over-long value fails with `23514`, never with `54000`, also
  when it names a missing row. `trust_anchor_ref` and `kind` also reject
  whitespace and control characters (the `COLLATE "C"` form of `0004`).
  `public_identity` is not checked for them: it is the canonical public-key
  identity of the credential, for example the SHA-256 digest of its
  SubjectPublicKeyInfo, in an encoding the service fixes; subject DNs are
  not stored. The digests
  `request_digest`, `challenge_hash` and `replay_key_digest` are `bytea` of
  32 to 64 bytes, and the recovery public key is 1 to 8192 bytes. Every ID,
  key, reference and enumeration is `COLLATE "C"`; only `outcome` keeps the
  database collation, as `audit_event.outcome` does.
- **`0002` key bounds.** `0005` makes `audit_event` and
  `instance_security_policy` foreign-key targets, and every key column of
  the schema is bounded (lead decision, 2026-11-20), so `0005` adds the
  forward-only 255-byte bounds `audit_event_id_octet_length_check`,
  `audit_event_tenant_id_octet_length_check`,
  `instance_security_policy_instance_id_octet_length_check` and
  `egress_allowlist_entry_id_octet_length_check` to the frozen `0002`
  tables, as `0004` did for `principal`. An over-long value fails with
  `23514`. The test `every_key_column_of_the_schema_has_a_named_bound`
  checks every unique and foreign-key column of every table. Up to `0004`
  the database accepts longer values, and `0005` validates the new checks
  against existing rows. Upgrade precondition: before `0005` is applied to a
  populated database,
  `select (select count(*) from audit_event where octet_length(id) > 255 or octet_length(tenant_id) > 255) + (select count(*) from instance_security_policy where octet_length(instance_id) > 255) + (select count(*) from egress_allowlist_entry where octet_length(id) > 255)`
  must return 0.
- **Locks on existing tables.** `0005` runs in one transaction, so it holds
  its locks until it commits. Adding the bound checks takes
  `ACCESS EXCLUSIVE` on `audit_event`, `instance_security_policy` and
  `egress_allowlist_entry` and scans each of them to validate the existing
  rows. The new foreign keys take `SHARE ROW EXCLUSIVE` on the tables they
  reference: `tenant`, `trust_source`, `audit_event` and
  `instance_security_policy`. Checked with `pg_locks` in a transaction that
  applies `0005` to a `0004` database (PostgreSQL 16); an over-long existing
  `egress_allowlist_entry.id` there makes the migration fail with `23514`.
  On a populated database, every read and write of the three
  `ACCESS EXCLUSIVE` tables, and every write of `tenant` and
  `trust_source`, waits until the migration commits, a brief stall that
  grows with the size of the three scanned tables. Run the upgrade in a
  maintenance window.
- **Roles** (identity-registry §5.2; public-api API-120; ADR-013
  OQ-ADR013-3). `role` is `security_admin`, `trust_admin`, `client_admin`,
  `provider_admin` or `auditor`. `tenant_id` is `NULL` for `security_admin`,
  the instance role, and set for the three tenant roles `trust_admin`,
  `client_admin` and `provider_admin`. `auditor` is either: with a tenant it
  reads that tenant, and with a `NULL` tenant it is the instance auditor,
  the only grant of instance audit reads. No role implies another; each is
  one row. `UNIQUE NULLS NOT DISTINCT (admin_id, role, tenant_id)` allows one
  binding per operator, role and scope, disabled rows included, and makes
  this hold for `security_admin` too. `NULLS NOT DISTINCT` needs
  PostgreSQL 15.
- **Recovery state.** The table holds one row
  (`recovery_state_single_row ON ((true))`), so a concurrent second
  bootstrap fails with `23505` (T13.6). Its `instance_id` references the
  `instance_security_policy` row. `bootstrap_closed` goes from `false` to
  `true` only (T13.4). `recovery_key_epoch` never decreases, and it
  increases exactly when `recovery_public_key` changes (OQ-TM-8). The step
  size is free.
- **Administrative operations** (tasks §3; ADR-008 item 12; IR-054;
  public-api OQ-API-13). The request digest, plan, kind and actor are
  immutable, as are the ID, tenant, expected revision, challenge, expiry,
  approved operation and audit event. `outcome`, `revision` and the one-way
  fields change. `consumed_at` is set once and never changed or cleared.
  `revoked_at` and `revocation_operation_id` are recorded together, once.
  An operation may be both consumed and revoked: security_admin may revoke a
  `route_bundle_approval` after beginning an attempt consumed it (tasks §3
  "Route preparation, approval and recovery"), and the set-once guard keeps
  each field one-way. The other order is refused for an `UPDATE` only: an
  `UPDATE`, `ON CONFLICT … DO UPDATE` included, that sets `consumed_at` on
  a row already revoked and not consumed fails with `SK001` (lead decision,
  2026-11-21). An `INSERT` is not checked, and the database never compares
  the two timestamps (see the service rules below). An operation of kind `approve` names the operation it
  approves; other kinds may name one too, for example a
  `route_bundle_approval` naming its preparation. No operation approves or
  revokes itself. A
  recovery challenge has an expiry, and nothing is consumed at or after its
  expiry (LT-107). `actor_id` is not a foreign key, because bootstrap and
  break-glass recovery act for actors that are not operator identities.
  `audit_id` references the audit event that records the operation, so that
  event is inserted first (see the ordering note below).
- **Consumed assertions** (T10.9; ADR-016 items 6 and 7). The primary key
  `(tenant_id, trust_source_id, replay_key_digest)` makes consumption atomic
  across replicas. A replay fails with `23505` on `consumed_assertion_pkey`,
  or inserts nothing under `ON CONFLICT DO NOTHING`. A consumed proof has a
  row under the current digest-key version and, while a retiring version
  drains, one under that version too (see the service rules below). Rows
  are insert-only: an `UPDATE`, including an `ON CONFLICT … DO UPDATE`,
  fails with `SK001`. `retain_until` is after `consumed_at`. The only
  removal is a `DELETE` after `retain_until`, which `0006` checks (see
  "What 0006 adds").
- **Not NULL.** Every column is `NOT NULL` except the fields the model marks
  optional: `admin_credential.revoked_at`, `admin_role_binding.tenant_id`,
  and `administrative_operation`'s `tenant_id`, `challenge_hash`,
  `expires_at`, `consumed_at`, `revoked_at`, `revocation_operation_id` and
  `approves_operation_id`. The `CHECK`s above tie
  `admin_credential.revoked_at` to `status`, `admin_role_binding.tenant_id`
  to the role, `revoked_at` and `revocation_operation_id` to each other,
  `challenge_hash` to `expires_at`, and `consumed_at` to `expires_at` when
  both are set; `approves_operation_id` is required only for kind
  `approve`. `administrative_operation.tenant_id` is tied to nothing: the
  service sets it to the `tenant_id` of its audit event (see the service
  rules below). Only `admin_identity.created_at` (`now()`)
  and `revision` (1) have defaults.

- **Privileges.** The guards read no table, so they need no grant. Foreign
  key checks run as the table owner. Consuming a proof therefore needs only
  `INSERT` on `consumed_assertion`, with a plain `INSERT` or
  `ON CONFLICT DO NOTHING` without a conflict target. Naming the target
  (`ON CONFLICT (tenant_id, trust_source_id, replay_key_digest)`) needs
  `SELECT` too and otherwise fails with `42501`. Pruning needs `DELETE`.
  The test `proof_consumption_needs_only_insert` checks each case.

Choices marked "(inferred)" in `0005`, which no source dictates:

- `status` is `enabled` or `disabled` on the three operator tables;
- revocation of a credential means permanent `disabled`;
  `public_identity` is unique across all credentials, revoked ones
  included, and is not checked for whitespace; `trust_anchor_ref` is an
  exact reference;
- one role binding per operator, role and scope, `NULL` tenant included,
  so an operator has at most one instance `auditor` binding;
- `recovery_state.instance_id` references the policy row;
  `bootstrap_closed` has no default and may be inserted `true`; the recovery
  key is 1 to 8192 bytes, the epoch is at least 1, and the epoch changes exactly
  when the key does, by any increase;
- digests are 32 to 64 bytes;
- `kind` is an open, bounded name; `expected_revision` is 0 for a create;
  `immutable_plan` is a JSON object (`'{}'` accepted); `outcome` is
  non-empty free text;
- `actor_id` is not a foreign key; `audit_id` names the creating event and
  is not unique;
- an `approve` must name an approved operation and other kinds may; no
  operation approves or revokes itself; an operation may be both consumed
  and revoked;
- the immutable columns beyond the plan, digest, kind, actor and IDs listed
  above;
- `digest_key_version` is an opaque ID; `retain_until` is after
  `consumed_at`; `consumed_assertion` has no separate tenant foreign key,
  since the source key implies the tenant (as for the `0004` list tables).

The database does not enforce these rules; the service must:

- require a second, different security_admin for gated writes and refuse
  self-approval (IR-054); check that an approval names a pending,
  unexpired, unrevoked operation of an approvable kind and that the
  echoed digest matches; the foreign keys prove only that the approved and
  revoking operations exist, in any tenant or none. That an approver is not
  the actor, and that an approval or revocation of a tenant operation stays
  in its tenant, stay service rules (accepted in review of `0005`);
- give an operation the `tenant_id` of the audit event that records it; the
  database checks neither against the other;
- give every pending gated write, `route_bundle_approval` and recovery
  challenge an `expires_at`; the database requires one only with a `challenge_hash`;
- keep secrets out of `immutable_plan`: it is kept for the life of the row
  and read back by auditors, and secrets never appear in configuration
  exports or logs (design §7);
- insert the first `recovery_state` row with `recovery_key_epoch` 1; the
  database checks only that the epoch is at least 1;
- never record an operation as consumed after it was revoked, by an
  `INSERT` that carries both `consumed_at` and `revoked_at` or by one
  `UPDATE` that sets both on a row that has neither: the consume-after-revoke
  guard checks only an `UPDATE` of a row already revoked, and the database
  does not compare the two timestamps;
- authorize each write by an enabled binding of an enabled operator with an
  enabled, unrevoked credential; the database does not join the statuses;
- cap the challenge lifetime at 15 minutes (LT-107): the table has no
  creation time to measure it from;
- refuse a retired recovery key; the table keeps only the current one;
- record a consumed proof only for a `single_use` source, and set
  `retain_until` to at least the proof's `exp` plus skew (lifetimes §9);
- prune `consumed_assertion` with a job that runs the `DELETE` after
  `retain_until`; `0006` rejects an earlier one (see "What 0006 adds");
- generate every ID and the `replay_key_digest` (a keyed digest; ADR-016
  item 6);
- keep replay detection across digest-key rotation with a drain deadline
  (lead decision, 2026-11-21; tasks §3 "One-time state"; ADR-016 items 6
  and 7; T21.8). This protocol must land before any T21.8 code. The primary
  key compares digests, and the same proof has a different digest under
  each key version, so a row written under one version does not conflict
  with a replay digested under another. The protocol:
  - at the cutover (`cutover_at`) a new version becomes current, and each
    retiring version gets a fixed drain deadline
    `drain_until = cutover_at + max_proof_ttl + skew`;
  - a consumption writes, in one transaction, a row under the current
    version with the proof's full `retain_until`, and, only while
    `consumed_at < drain_until`, a row under each retiring version with
    `retain_until = least(proof_retain_until, drain_until)`. A conflict on
    any of them is a replay and rolls back all of them. The capped
    `retain_until` is still after `consumed_at`, since both
    `proof_retain_until` and `drain_until` are, so
    `consumed_assertion_retention_check` holds;
  - after `drain_until` nothing is written under a retiring version.

  Invariant: every proof is replay-protected for its whole validity under
  at least one retained key. A proof consumed before the cutover has its
  row under the old version, written with its full `retain_until`, for its
  whole retention; a replay during the drain conflicts with that row, and
  the proof expires by `drain_until`, since it was issued before
  `cutover_at`. A proof consumed during the drain also has a row under the
  new version with its full `retain_until`, so capping its old-version row
  at `drain_until` loses nothing: from `drain_until` on, a proof is checked
  and consumed under the new version alone. The default is this write-side
  drain with capped rows. The follow-up, once every replica writes the new
  version, switches a retired version to `SELECT` checks: the service looks
  for an existing row under it and no longer writes there. That needs
  `SELECT` on `consumed_assertion` for the runtime role, which consumption
  otherwise does not need (see "Privileges" above);

- order the locks of a write that creates an operation, so that it cannot
  deadlock with another such write:
  1. first lock every existing row that the new operation references or
     that the write updates, with `FOR NO KEY UPDATE`, never `FOR UPDATE`.
     The foreign-key checks of the operation insert take `FOR KEY SHARE` on
     the referenced rows, which conflicts with `FOR UPDATE` and not with
     `FOR NO KEY UPDATE`. Lock the rows in one fixed order: the tables of
     `0005` in the order of this section (`admin_identity`,
     `admin_credential`, `admin_role_binding`, `recovery_state`,
     `administrative_operation`, `consumed_assertion`), then the `0002` to
     `0004` tables by name, ascending bytewise, leaving out
     `audit_chain_head`, which step 2 locks; within a table, by primary
     key, ascending bytewise. Where possible, lock a table's rows with one
     statement,
     `SELECT … FROM <table> WHERE … ORDER BY <primary key> COLLATE "C" FOR NO KEY UPDATE`
     (a `bytea` key column takes no `COLLATE`; it already compares
     bytewise);
  2. then lock the audit head, insert the audit event and insert the
     operation;
  3. then do the remaining updates. A revocation's `UPDATE` of the revoked
     row comes here, after the head lock, because it names the revoking
     operation, which exists only after step 2. It does not wait here: the
     revoker already waited in step 1 for the locks of the rows it needs,
     before it took the audit head.

  PostgreSQL locks the rows of such a statement as they are returned. The
  test `writers_locking_rows_in_key_order_wait_instead_of_deadlocking`
  asserts that the plan of its statement has `LockRows` on top, with a
  `Sort` or an index scan of the primary key directly below it, so the rows
  are locked in key order. Caveats: only the locking statement's own
  `ORDER BY` orders its locks, not one in an outer query around a locking
  subquery; and under `READ COMMITTED` a row whose sort key changed while
  the statement waited for its lock keeps its old place in the lock order
  and is returned out of order (PostgreSQL documentation, "The Locking
  Clause" of `SELECT`), which the immutable IDs rule out here. Rows locked
  by separate statements are locked in the order of those statements. A
  waiting writer proceeds only under `READ COMMITTED`: under
  `REPEATABLE READ` or `SERIALIZABLE`, once the first writer commits an
  update of a row the second one waits for, the second fails with `40001`
  (`serialization_failure`; checked by hand on PostgreSQL 16 at both
  levels), and its whole transaction must be rerun. The registry reports
  `40001` as a retry-the-whole-transaction error, never as a stale
  revision.

  The two-connection tests
  `for_update_on_a_referenced_row_deadlocks_with_the_audit_head` and
  `a_row_updated_after_the_audit_head_must_be_locked_first` reproduce the
  `40P01` deadlock that each step 1 rule avoids. In the prescribed order the
  first test's insert does not wait at all, and in the second the revoker
  waits in step 1 for the revoked row's lock, before it takes the head, and
  then finishes.
  `writers_locking_rows_in_key_order_wait_instead_of_deadlocking` shows
  two writers that update the same two role bindings in opposite orders
  deadlock when each locks a row as it updates it, and that with the
  ordered statement the second writer waits for the first while holding
  neither row and then proceeds, with no `40P01`. Against the "domain rows
  first" order of `0002`, a write that creates an operation still locks its
  domain rows first, but makes its writes after the head lock: the event,
  the operation and the remaining updates of step 3. `audit_id` stays an
  immediate, not deferrable foreign key, so the event is inserted first.
  Writes that create no operation (consume, outcome) update their rows
  before the head, in the `0002` order.

- `0005` makes two `0002` tables foreign-key targets, so a bare `TRUNCATE`
  of them now fails with `0A000` (a table referenced in a foreign key) before
  the `0002` truncate guard can raise `SK001`:
  `TRUNCATE audit_event` needs `administrative_operation` in the same
  statement, and `TRUNCATE instance_security_policy` needs `recovery_state`.
  The `0002` guard tests list those tables and check that the `SK001`
  message names `audit_event` or `instance_security_policy`, and
  `bare_truncate_of_a_referenced_foundation_table_fails_before_its_guard`
  checks the `0A000`; the guard itself is unchanged.

## What 0006 adds

`0006_registry_guards.sql` adds the delete and truncate guards that the
follow-ups of `0002` to `0005` left open, for every registry table at once
(lead decision, 2026-11-20), and the pruning index of `consumed_assertion`.
It changes no column, constraint or existing trigger. Every new trigger is
`ENABLE ALWAYS` and raises `SK001`. The guards do not reuse
`skyoauth_reject_mutation()` from `0001`: its message calls the table
"append-only", which is false here: their rows are updated (status,
revision) or, for the list tables and `consumed_assertion`, deleted (lead
decision, 2026-11-21). The unconditional guards call two new
functions, `skyoauth_reject_delete()` ("DELETE is not allowed on
`<table>`") and `skyoauth_reject_truncate()` ("TRUNCATE is not allowed on
`<table>`"). The three conditional ones are
`skyoauth_reject_delete_unless_disabled()` ("only a disabled row of
`<table>` may be deleted"), its `service_grant` variant
`skyoauth_reject_delete_grant_unless_disabled()` (the same message, and "an
impersonation grant of `<table>` is never deleted") and
`skyoauth_reject_delete_before_retention()` ("a row of `<table>` cannot be
deleted before its retain_until"). None of the five reads a table, so each pins `search_path` to
`pg_catalog, pg_temp`.

- **Why.** A row deleted and created again with the same ID starts again at
  revision 1, so an old `(id, revision)` snapshot could match the new row.
  Deleting one-time state undoes it: a new `recovery_state` row could
  reopen bootstrap with a lower key epoch, a deleted operation forgets its
  consumption and revocation, a consumed proof deleted before
  `retain_until` lets a replay through, and a deleted credential erases
  its revocation record and frees its `public_identity`, so the key could
  be registered again.
- **`DELETE`** is checked per row by a `BEFORE DELETE … FOR EACH ROW`
  trigger, so a `DELETE` that matches no row passes and a rejected one
  deletes nothing:
  - never: `tenant` and `principal`; the four revisioned `0003` tables;
    `trust_keyset`, `trust_keyset_version`, `trust_source` and
    `service_identity`; `admin_identity`, `admin_credential`,
    `admin_role_binding`, `recovery_state` and `administrative_operation`.
    With the guards of `0001` and `0002`, no record of the tables above is deleted. For `tenant`, `principal`, `resource_server`,
    `audience_tenant_assignment`, `resource_server_checker`,
    `resource_action`, `trust_keyset`, `trust_keyset_version`,
    `trust_source` and `service_identity`, no source defines a hard delete
    (ADR-008 item 3 allows one only of bindings and grants): offboarding is
    disable-only, and if a specification ever defines a hard delete, a
    later forward migration can relax the guard (lead decision,
    2026-11-21). An `admin_credential` is never deleted, revoked or not,
    like an `admin_identity`: a credential leaves service by revocation
    (T13.6), and deleting its row would erase the revocation record and
    let its key be registered again (lead decision, 2026-11-21);
  - only when `disabled`: `principal_binding` and `service_grant` (ADR-008
    item 3), except that an impersonation grant (`mode = 'impersonation'`) is
    never deleted, disabled or not (lead decision, 2026-11-21, provisional):
    deleting and recreating a dormant impersonation grant under
    caller-supplied IDs is the only way to revive it, and an ADR-008 errata
    line records the exception. The foreign keys still reject a referenced row with `23503`
    after the guard, so a binding goes only when no grant row names it, and
    a grant only after its list rows. The `0004` binding-set check passes
    for a grant deleted in the same transaction as its binding rows;
  - `consumed_assertion`: only a row whose `retain_until < now()`, where
    `now()` is the start of the deleting transaction; a row whose
    `retain_until` equals it is kept (inferred);
  - always: the list tables `resource_server_checker_tenant`,
    `service_identity_resource_server`, `service_grant_binding` and
    `service_grant_resource_server`. Deleting a row is how such a set
    shrinks, and the owner's revision records it; `DELETE` still cannot
    empty a grant's binding set (`0004`).
- **`TRUNCATE`** is rejected by a `BEFORE TRUNCATE … FOR EACH STATEMENT`
  trigger on each of the 22 tables of `0002` to `0005` that had none, the
  list tables included (required for `service_grant_binding`; inferred for
  the other three, where a `TRUNCATE` would empty every owner's set without
  advancing a revision). With the guards of `0001` and `0002`, every table
  of the migrations has one. `TRUNCATE … CASCADE` fires the `BEFORE TRUNCATE`
  triggers of every table it reaches, so the reached table's guard rejects
  a cascade from another table: `TRUNCATE principal_binding CASCADE` and
  `TRUNCATE service_grant_binding` no longer leave a grant without a
  binding, nor does `TRUNCATE admin_identity CASCADE` empty the operator
  tables. A bare `TRUNCATE` of a table that a foreign key references still
  fails earlier, with `0A000`.
- **Pruning.** No pruning job exists: nothing deletes expired
  `consumed_assertion` rows yet, and the guard only permits a deletion
  after `retain_until`; it performs none. The job is a service follow-up,
  not part of this migration (see Follow-ups), that is to run
  `DELETE FROM consumed_assertion WHERE retain_until < now()`.
  `consumed_assertion_retain_until_idx` indexes
  `consumed_assertion (retain_until)` and serves that predicate, and the
  guard rejects the whole statement if a differently written one would
  delete a row still retained.
- **Concurrency.** A guard judges the row version its `DELETE` locks:
  under `READ COMMITTED`, a delete that waited for a concurrent status
  change sees the committed status, so it fails after a re-enable and
  succeeds after a disable. Nothing is deferred.
- **Triggers:**

  | Trigger                                     | Fires on                   | Function                                         |
  | ------------------------------------------- | -------------------------- | ------------------------------------------------ |
  | `<table>_no_delete` (the 15 tables above)   | `DELETE`, each row         | `skyoauth_reject_delete()`                       |
  | `principal_binding_delete_disabled_only`    | `DELETE`, each row         | `skyoauth_reject_delete_unless_disabled()`       |
  | `service_grant_delete_disabled_only`        | `DELETE`, each row         | `skyoauth_reject_delete_grant_unless_disabled()` |
  | `consumed_assertion_delete_after_retention` | `DELETE`, each row         | `skyoauth_reject_delete_before_retention()`      |
  | `<table>_no_truncate` (the 22 tables)       | `TRUNCATE`, each statement | `skyoauth_reject_truncate()`                     |

  The catalog test in `service/tests/schema_registry_guards.rs` pins every
  trigger of the schema that fires on `DELETE` or `TRUNCATE`, and fails for
  a later table without a truncate guard.

- **Locks on existing tables.** `0006` runs in one transaction, so it
  holds its locks until it commits. `CREATE TRIGGER` and
  `ALTER TABLE … ENABLE ALWAYS TRIGGER` take `SHARE ROW EXCLUSIVE` on each
  of the 22 tables, and `CREATE INDEX` takes `SHARE` on
  `consumed_assertion` and scans it. Checked with `pg_locks` in a
  transaction that applies `0006` to a `0005` database (PostgreSQL 17.12).
  Neither mode conflicts with the `ACCESS SHARE` lock of a plain read;
  both conflict with the `ROW EXCLUSIVE` lock of a write (PostgreSQL
  documentation, "Table-Level Locks"). So on a populated database, writes
  of these tables wait until the migration commits, and the migration
  waits for open transactions that wrote them. The write stall lasts as
  long as the longest open write transaction on any of the 22 tables: the
  migration queues behind it, later writes queue behind the migration, and
  the migration can fail with `40P01` or `55P03` (a retry is safe, since the
  migration is transactional). The index build adds a stall that grows with
  the size of `consumed_assertion`. No `CHECK` is added and no
  existing row is
  validated, so the migration cannot fail on existing data and has no
  upgrade precondition. Run the upgrade in a maintenance window.
- **Frozen comments.** The comments of `0003` (lines 14–16), `0004` (lines
  18–24) and `0005` (lines 30–36, 124–126 and 365–367) that say these
  guards come later are fulfilled by `0006`; the files stay unchanged.

The database does not enforce these rules; the service must:

- hard-delete a binding only by an audited admin write, and only when no
  approval or audit-required record references it (ADR-008 item 3); the
  database checks only the status and the foreign keys of the schema;
- retire a credential by revoking it (T13.6); the database rejects every
  `DELETE` of one;
- build and run the pruning job, which does not exist yet;
- advance the owner's revision when it deletes a list row (`0003`,
  `0004`).

Under `session_replication_role = replica` foreign keys do not fire (see
"Limits"), so there a disabled binding or grant that a list row still
references can be deleted; the guards check only the status.

## What 0007 adds

  the key has it, become `<x>_principal`. The indexes are not partial
  (inferred: the tables are small, so a partial index would save little).
  Five foreign keys get none (inferred): the leading column of their
  table's primary key is one of their columns and identifies the referenced
  row on its own, so the primary-key index already narrows the check to
  that row's few referencing rows. They are
  `resource_server_checker_tenant_checker_fkey` (`checker_id`),
  `service_identity_resource_server_service_id_fkey` (`service_id`),
  `service_grant_binding_grant_id_fkey` and
  `service_grant_resource_server_grant_id_fkey` (`grant_id`), and
  `service_identity_id_fkey` (`id`, the primary key itself). A catalog test
  fails for a later foreign key that has neither. The indexes serve
  parent-scoped lookups and the foreign-key check of a `DELETE` or key
  `UPDATE` of the referenced row. Since `0006` most referenced rows are
  never deleted and their keys are immutable, so that check now runs for a
  deleted binding or grant, and when the table owner repairs rows with the
  guards disabled.

- **Collation.** `0007` changes no column's collation, so the `no_space`
  follow-up of `0002` and `0003` stays as it is (see "Follow-ups").
- **Locks on existing tables.** Checked with `pg_locks` in a transaction
  that applies `0007` to a `0006` database, on PostgreSQL 16 and 17.12
  (the 17.12 run, from the lead's review, gave the same results). The
  `ALTER TABLE` statements (`ADD COLUMN`, `ADD CONSTRAINT … CHECK`) take
  `ACCESS EXCLUSIVE` on the 11 tables with a `timestamptz` column
  (`schema_info`, `tenant`, `principal`, `instance_security_policy`,
  `audit_event`, `trust_keyset_version`, `service_grant`, `admin_identity`,
  `admin_credential`, `administrative_operation` and `consumed_assertion`)
  and scan each once to validate its checks; the new column has a constant
  default, so no table is rewritten (its `relfilenode` stays the same).
  `CREATE TRIGGER` and `ENABLE ALWAYS` take `SHARE ROW EXCLUSIVE` on
  `tenant`, `principal` and `trust_keyset_version`. Each `CREATE INDEX`
  takes `SHARE` on its table, reads the whole table, and holds
  `ACCESS EXCLUSIVE` on the new index; 13 tables get one or more.
  `ACCESS EXCLUSIVE` conflicts with every other lock, plain reads included,
  and `SHARE` with every write (PostgreSQL documentation, "Table-Level
  Locks"). `0007` runs in one transaction, so it holds all of them until it
  commits: from the first `ALTER TABLE` until the commit nothing reads the
  11 tables, and nothing writes the 13 indexed ones. Stop the service and
  run the upgrade in a maintenance window; its length grows with the size
  of `audit_event`, `consumed_assertion` and the indexed tables. No index is
  built `CONCURRENTLY`, which cannot run in a transaction (inferred: the
  registry tables are small).

  The predicate is the negation of the check, so it counts exactly the rows
  the check rejects; a `NULL` is not counted. The registry never writes
  such a row (see "The `0004` tables"); a restored or hand-written one can
  exist. `service/tests/schema_registry_shape.rs` runs this query from this
  file.

  A counted `audit_event` row is an integrity incident, not a row to
  repair: never edit it in place, but restore a verified backup or follow a
  separate recovery procedure (this README defines none). The event's
  `timestamp` is part of its hash: identity-registry IR-056 hashes the
  canonical JSON of the event envelope without only its `hash` and
  `prev_hash` fields, and OQ-IR-15 lists how `timestamp` is serialized in
  that envelope among the details still open. An edited timestamp gives
  another hash than the one the next event's `prev_hash`, or
  `audit_chain_head.head_hash` for the last event, records (see the audit
  writer under "Follow-ups", "Not done in `0002`").

  A counted row of any other table can be repaired in place. Most of these
  columns are immutable and the tables reject a `DELETE` (`0006`), so the
  table owner repairs the rows in one transaction, with the user triggers
  of each repaired table off only for its repair:
  1. List the table's user triggers:
     `SELECT tgname FROM pg_trigger WHERE tgrelid = '<table>'::regclass AND NOT tgisinternal;`
  2. Run `ALTER TABLE <table> DISABLE TRIGGER USER;`. This turns off every
     listed trigger, not only the guards: also the revision trigger, the
     `*_set_once` triggers, `administrative_operation_no_consume_after_revoke`,
     `instance_security_policy_sink_validation` and the deferred constraint
     trigger `service_grant_has_binding`. A constraint trigger that is
     disabled when a row changes queues no check for that change, even once
     it is enabled again before the commit (checked on PostgreSQL 16), so
     nothing checks the repaired rows against those rules: the repair
     changes only the counted column and, where the table has one, the
     revision.
  3. `UPDATE` each counted row to a time inside the range. On a table with
     a `revision` column (of these tables before `0007`:
     `instance_security_policy`, `service_grant` and
     `administrative_operation`), also set
     `revision = revision + 1` (inferred: a compare-and-set writer that
     read the row before the repair then fails instead of overwriting it).
     While enabled, the revision trigger accepts nothing else; while
     disabled it checks nothing, so the repair advances the revision
     itself. `tenant`, `principal` and `trust_keyset_version` have no
     revision before `0007`, which gives every row revision 1.
  4. Run `ALTER TABLE <table> ENABLE ALWAYS TRIGGER <name>;` for every
     trigger listed in step 1.

  Before the `COMMIT`, this query must return 0:

  ```sql
  SELECT count(*) FROM pg_trigger WHERE NOT tgisinternal AND tgenabled <> 'A';
  ```

  Every user trigger of `0001` to `0007`, the constraint triggers included,
  is `ENABLE ALWAYS` (`A`), so any other state is one the repair left
  behind. (inferred: in a database that also holds other triggers, for
  example of another schema or an extension, restrict the query to the
  registry's tables.) Then commit, and record the repair in the audit
  trail. `service/tests/schema_registry_shape.rs` runs these steps and this
  query.

- **Frozen comments.** The comments of `0002` (lines 269–271: tenants and
  principals carry no revision) and `0004` (lines 91–94: versions have no
  revision) describe the schema before `0007`; the files stay unchanged.

The registry's `KNOWN_CONSTRAINTS` lists the new checks of the tables it
writes (`tenant_revision_check`, `principal_revision_check`,
`trust_keyset_version_revision_check` and the range checks of `tenant`,
`principal`, `trust_keyset_version` and `service_grant`). The registry reads
the new revisions and updates tenants, principals and versions as
compare-and-sets on them (see "Rust registry surface").

## Limits

- The guard triggers are a tripwire against application DML, not a
  security boundary. The table owner or a superuser can disable or drop
  them, or rewrite rows with `ALTER TABLE … ALTER COLUMN … TYPE … USING`.
  The real control is a runtime role that does not own the tables, together
  with the pinned `search_path` of the guard functions: a non-owner role
  alone is not enough, because without the pin a temporary table shadows the
  chain head for it. Today one `SKYOAUTH_DATABASE_URL`
  serves both `migrate` and the server, and separating the roles is a
  follow-up.
- Under `session_replication_role = replica` (logical-replication apply,
  some restores), foreign keys are not enforced: their internal triggers
  fire only in origin mode. The `ENABLE ALWAYS` guards and the `CHECK`,
  `NOT NULL` and unique constraints still are.
- An initial logical-replication table sync or a data-only reload of
  `audit_event` cannot pass the chain triggers: each copied event is checked
  against a head the copy does not advance, and the migration has already
  inserted the head row. Nor can a reload of a revisioned row past revision
  1 (a policy or egress entry at revision 2 fails with "rows start at
  revision 1"). A data-only reload is therefore owner-level surgery: the
  table owner disables the user triggers for it
  (`ALTER TABLE … DISABLE TRIGGER USER`; the `pg_restore --disable-triggers`
  option needs a superuser), reconciles the head row, and then re-enables
  every guard with
  `ALTER TABLE <table> ENABLE ALWAYS TRIGGER <name>`. `ENABLE TRIGGER USER`
  or `ALL`, which `pg_restore` uses, sets them to origin mode only, so they
  would no longer fire under `replica`. This query lists the user triggers
  that are not `ALWAYS`:

  ```sql
  SELECT tgrelid::regclass, tgname, tgenabled FROM pg_trigger
  WHERE NOT tgisinternal AND tgenabled <> 'A';
  ```

- Streaming apply of committed transactions carries each event insert and
  head update together, but the deferred chain check cannot run in the
  security-restricted operation in which the apply worker runs as a table
  owner other than the subscription owner: the first `audit_event` insert
  fails with "cannot fire deferred trigger within security-restricted
  operation". The subscription owner must own the tables, or the
  subscription must use `run_as_owner = true`. The deferred trigger stays
  `ENABLE ALWAYS` (lead decision): logical replication of the audit chain is
  not a v0.1 requirement.
- The deferred binding-set check of `0004` works under logical replication
  when the subscription owner owns the tables. Its limits:
  - When the table owner differs from the subscription owner, a replicated
    `INSERT` into `service_grant` or `DELETE` from `service_grant_binding`
    fails with "cannot fire deferred trigger within security-restricted
    operation", and the apply worker retries it forever.
  - The initial table sync copies each table in its own transaction, so the
    sync of `service_grant` fails with `SK001` if it runs before that of
    `service_grant_binding`. A retry after the binding rows are in recovers;
    with `disable_on_error` the subscription is disabled instead.
  - A data-only `pg_dump` replayed in autocommit fails at the
    `service_grant` `COPY` for the same reason; replaying it with
    `--single-transaction` works (T10.6).
- The database must use the `UTF8` encoding (inferred; the migrations do not
  check it). The egress destination rules above hold only there: under
  `SQL_ASCII` a multibyte character is matched byte by byte, so U+2028 and
  U+200B (bytes `E2 80 A8` and `E2 80 8B`, each with the C1 byte `80`) are
  rejected as controls.
- The migration role must own the database, or at least have `CREATE` on
  the `public` schema (PostgreSQL 15 and later no longer grant that to
  every role).
- Runners serialize on a session-level `pg_advisory_lock`. It needs a direct
  connection: through a transaction-pooling proxy such as PgBouncer in
  transaction mode the lock and the migration can land on different server
  sessions. The lock wait has no timeout; adding one is a follow-up.

## Follow-ups

Open for all registry tables:

- Delete and truncate guards: done in `0006` for every instance- and
  tenant-level registry table, decided together (lead decision,
  2026-11-20); "What 0006 adds" has the rules per table and what they
  leave to the service. They were a prerequisite before any code snapshots
  an `(id, revision)` pair (tasks §3 "Policy revisions") or relies on
  revisions only increasing, and before any code of T13.4 (bootstrap),
  T13.5 (recovery) or T21.6 (single-use consumption) lands. For `0005`,
  `admin_credential` is never deleted, revoked or not (lead decision,
  2026-11-21, replacing the earlier rule that only a revoked row is kept):
  a credential leaves service by revocation (T13.6).
- The `consumed_assertion` pruning job. No pruning job exists: `0006`
  only permits a `DELETE` after `retain_until` and adds the index on
  `retain_until` that a job needs. The job, a service job that runs
  `DELETE FROM consumed_assertion WHERE retain_until < now()`, is not
  built.
- A `revision` column on `tenant`, `principal` and
  `trust_keyset_version`: done in `0007` (lead decision, 2026-11-21; see
  "What 0007 adds"), with the registry's compare-and-set updates of them,
  `update_tenant`, `update_principal` and `update_trust_keyset_version`
  (see "Rust registry surface").
- Indexes on the referencing side of the foreign keys: done in `0007` for
  every foreign key whose columns led no index, with five exceptions that
  the primary key already serves ("What 0007 adds").
- Timestamp ranges: done in `0007`, a named check on every `timestamptz`
  column of `0001` to `0005`, with the upgrade precondition query ("What
  0007 adds").
- Open spec question: name uniqueness (IR-021). IR-021 says a `name` is
  unique within its entity type and tenant, but the schema has no unique
  constraint on `tenant.name` or `principal.name`. The open question is a
  unique `(tenant_id, name)` for principals and a rule for tenant names.
  The lead decides the spec text; no migration is added until then. The
  registry test `tenant_and_principal_names_need_not_be_unique` pins the
  current schema and fails once such a constraint exists.
- Runtime-role privileges (the T10.1 runtime-role follow-up). The deferred
  binding-set check runs with the caller's privileges: creating a grant
  needs, besides `INSERT`, `UPDATE` and `SELECT` on `service_grant` (the
  grant lock) and `SELECT` on `service_grant_binding`; with only `INSERT`
  and `SELECT` on `service_grant` the commit fails with `42501`. Under
  `REPEATABLE READ` or `SERIALIZABLE`, creating a grant and deleting a
  binding row also need `UPDATE` on `service_grant_binding` (the row locks),
  or the commit fails with `42501`. The test
  `grant_binding_check_needs_the_callers_privileges` checks each case.
- The `no_space` checks of `0002` (`exact_destination`) and `0003`
  (`audience`, `action_name`) do not name a collation in the expression;
  they rely on their columns being `COLLATE "C"`, so they hold the same
  values on every instance today. If such a column ever gets another
  collation, a later forward-only migration replaces the check with the
  `0004` form, `CHECK ((<column> COLLATE "C") !~ '[[:space:][:cntrl:]]')`;
  the frozen files stay unchanged.

Not done in `0002`:

- An `audit_event` detail column, for example the affected source IDs that
  the audit event of an egress entry write lists (IR-152, OQ-IR-12).
- A `revision` on `tenant` and `principal`: updates require
  ID, tenant and revision (tasks §3 "IDs/names"). Done in `0007`.
- The audit writer. The service computes the event hash (lead decision,
  2026-11-20, OQ-IR-14; identity-registry IR-056; provisional until the
  writer ships). The hash is SHA-256 over the concatenation of:
  1. the ASCII bytes `skyoauth.audit.v1` followed by one zero byte;
  2. `prev_hash` as 32 raw bytes, or zero bytes for the first event, whose
     `prev_hash` column is `NULL`;
  3. the RFC 8785 (JCS) canonical JSON of the event envelope without the
     `hash` and `prev_hash` fields.

  `prev_hash` and `head_hash` store the raw 32-byte digest as `bytea`;
  lowercase hex is only the JSONL and API output form. `audit_event` has no
  column for an event's own hash, so verification recomputes it and compares
  it with the next event's `prev_hash` or the head's `head_hash`. Still open
  before the writer ships (identity-registry OQ-IR-15): the text
  serialization of an object `actor`, the envelope's member names, the
  timestamp format, the encoding of absent values, and the action names
  (IR-059 fixes only the `<resource>.<verb>` syntax), including those of the
  startup-mirror and sink-change events.
  Tests assert chain linkage and verification outcomes, never hash values.

- Errata for comments and checks in `0002`, which is frozen (its checksum
  covers comments), so they are corrected here and not in the file:
  - Lines 116–118, on `instance_security_policy.instance_id`: "No format or

  - `audit_chain_head.head_hash` and `audit_event.prev_hash` check

## Rust registry surface

`skyoauth_service::persistence::registry` is the typed Rust entry point to
the registry tables of `0002` and `0003`: create, get, list and
revision-checked update for `tenant`, `principal`, `resource_server`,
`audience_tenant_assignment`, `resource_server_checker` (with its tenant
rows) and `resource_action`; and reads of `instance_security_policy` and
`egress_allowlist_entry`. The revisions of `tenant` and `principal` are the
ones `0007` adds. Their updates, `update_tenant` and `update_principal`,
take a patch (`TenantPatch`, `PrincipalPatch`) and change only the columns
set in it, `name` and `status` (lead ruling, 2026-11-21); the other updates
replace every mutable column. An empty patch is an encode error (`Other`)
before any statement runs, so it neither reaches the database nor advances
the revision. Names need not be unique: `0002` has no unique constraint on
`tenant.name` or `principal.name`. `update_principal` is kind-agnostic; the
rule that only workload and service principals change through it belongs
to the service handler. Disabling and re-enabling are plain status changes;
any approval or widening rule for re-enabling belongs to the service layer
(provisional lead pick, 2026-11-21).
Every function runs one statement on any executor (pool, connection or
caller transaction). Writes take caller-supplied IDs (T10.2 generates
them). An update is a compare-and-set: it sets `revision = revision + 1`
where `revision = expected`, as `skyoauth_check_revision()` requires, and
touches only the columns these migrations leave mutable. The expected
revision is only compared, so even `i64::MAX` gives `StaleRevision` or
`NotFound`, not an overflow; only a row already at revision `i64::MAX`
gives `Other` with `22003` from `revision + 1`, which is unreachable in
practice since revisions start at 1 and advance by 1. Adding or removing a checker tenant row
advances the checker's revision in the same statement. A principal is read
by tenant and ID; lists are ordered by ID byte-wise and paged after an ID
cursor.

Of two concurrent updates from one revision exactly one succeeds. Under
`READ COMMITTED` the second waits for the first's row lock and then gives
`StaleRevision`. In a caller transaction at `REPEATABLE READ` or
`SERIALIZABLE` it fails instead with `40001` (`serialization_failure`),
which maps to `Retry`: it means "retry the whole transaction", so it is
never mapped to `StaleRevision`. A deadlock (`40P01`,
`deadlock_detected`) is `Retry` too. `Retry`, like `Other`, keeps the raw
`sqlx::Error` as its `source()`; the registry does not retry.

Errors map by SQLSTATE and, for constraint errors, by the constraint names
in the tables above (the module's `KNOWN_CONSTRAINTS`, checked against the
catalog by a test). The `Display` and `Debug` text of an error carries
constraint, table and column names and SQLSTATEs only, never a value. The `source()` of
`Retry` and `Other` is the raw `sqlx::Error`, which may quote values, so
logging must not walk the source chain.

| SQLSTATE | Rust error                                      |
| -------- | ----------------------------------------------- |
| —        | `NotFound`, `StaleRevision` (no row matched)    |
| `23505`  | `AlreadyExists { constraint }`                  |
| `23503`  | `Invariant { kind: ForeignKey, constraint }`    |
| `23514`  | `Invariant { kind: Check, constraint }`         |
| `23502`  | `Invariant { kind: NotNull, constraint: None }` |
| `SK001`  | `Guard`                                         |
| —        | `UnreadableTimestamp { table, column, id }`     |
| `40001`  | `Retry` (retry the whole transaction)           |
| `40P01`  | `Retry` (retry the whole transaction)           |
| other    | `Other`, also for a constraint not listed       |

PostgreSQL text and `jsonb` cannot hold U+0000: a NUL character in any
string argument (IDs, names, the page cursor, list elements, strings inside
`jsonb` values) gives `Other` with `22021` (`text`) or `22P05` (`jsonb`).
The request layer (T14.1) must reject it.

The registry does not authorize writes (API-147; T14.1, T14.2), write
audit events (T13.x), check the rules listed under "The database does not
enforce these rules" above, generate IDs or run migrations.

Consumed assertions (T10.9; ADR-016 items 6 and 7): `consume_assertion`
inserts one row with `ON CONFLICT … DO NOTHING` and returns `Consumed`, or
`Replay` when the key exists, leaving that row unchanged.
`consume_assertion_set` writes the rows of one proof under several
digest-key versions all or none: a plain multi-row `INSERT`, whose `23505`
on `consumed_assertion_pkey` is `Replay` with nothing written; inside a
caller transaction that error aborts the transaction, which the caller
rolls back. It inserts its rows sorted by the primary key, bytewise, so
two sets that share keys lock them in the same order and do not deadlock.
An empty set, or one of more than `MAX_ASSERTION_SET` (8, inferred) rows,
is rejected before the statement. A replay is not an error; every error, a store failure included,
is a deny. The digest, `retain_until` with its drain cap, `consumed_at`,
and the `single_use` and enabled checks of the source stay with the service
(see the service rules above). The claim that exactly one attempt consumes
holds under `READ COMMITTED`; under `REPEATABLE READ` or `SERIALIZABLE` a
loser may get `Retry`.

Follow-ups for the registry surface:

- Parent-scoped lookups and lists, needed by the admin API (T14.1, T14.2)
  and landing with its handlers: by `resource_server_id` for the
  assignment, checker and action lists; by `(tenant_id, resource_server_id)`
  for an assignment (IR-080, IR-081); and by
  `(resource_server_id, action_name)` for an action.
- `list_principals` for an unknown tenant returns an empty list, not
  `NotFound`; the handler decides whether an unknown tenant is a 404.
- `create_principal` with an ID another tenant already uses gives
  `AlreadyExists { constraint: "principal_pkey" }`, which tells the caller
  the ID exists elsewhere. That is harmless while IDs are server-generated
  (T10.2); import paths (T14.8) must not surface it for client-chosen IDs.
- Replacing a checker's whole tenant set with `k` adds and removes advances
  its revision by `k`. T14.3 may want a single replace operation that
  advances it by one.

### The `0004` tables

The same module covers the nine `0004` tables, with the same conventions:
create, get, list and revision-checked update for `trust_keyset`,
`trust_source`, `principal_binding`, `service_identity` and
`service_grant`; create, get, a per-keyset list and
`update_trust_keyset_version` for `trust_keyset_version`. That update sets
the version's `status`, its one mutable column, as a compare-and-set on the
version's own revision (added by `0007`), with no tie to the keyset's
revision (lead decision, 2026-11-21). Every one is tenant-owned: reads,
updates and list-set changes take the tenant and ID, so another tenant's ID
is `NotFound`, and lists hold one tenant's rows. A trust source is stored
flat, and the database's `trust_source_*_kind_check`s decide which fields a
kind takes. Timestamps are written as whole microseconds, truncated toward
the past (inferred).

The list tables change one row at a time, each a compare-and-set on the
owner's revision, as checker tenants do: a service identity's audiences, a
grant's bindings and a grant's audiences. A service identity and a grant
are created with their initial sets in one statement. That keeps the
deferred binding-set check whole. The check is two constraint triggers on
one function: `service_grant_has_binding` (a grant created with no binding)
and `service_grant_binding_keeps_one` (the removal of a binding), both
calling `skyoauth_service_grant_has_binding()`. A grant created with a
binding passes on any executor; a grant created without one, or the removal
of its last binding, fails with `Guard` at once on a pool, and at the
caller's commit inside a transaction unless a binding is added first (`RegistryError::from` maps the commit's error). Of two
removals from one grant revision, the later is `StaleRevision` under
`READ COMMITTED`; under `REPEATABLE READ` and `SERIALIZABLE` PostgreSQL
fails it with `40001`, which maps to `Retry`. The `0004` constraint names
are in `KNOWN_CONSTRAINTS`, and `service/tests/registry_trust.rs` tests the
surface.

Timestamps: the registry reads a timestamp as
`(extract(epoch FROM <column>) * 1000000)::bigint`, microseconds from the
Unix epoch in a signed 64-bit integer. `since_epoch` writes only a part of
that range: from PostgreSQL's earliest `timestamptz` (4713 BC,
`-210_866_803_200_000_000` microseconds) to `i64::MAX - 1` microseconds
(`294247-01-10 04:00:54.775806+00`), both inclusive, rejecting any other
time with `Other` (an encode error, "timestamp out of range") before any
statement runs.
`i64::MAX` itself is excluded because PostgreSQL 16's
`extract(epoch ...)` rounds exactly that time to
`9_223_372_036_854_775_800`. Since `0007` the tables hold the same range:
each `timestamptz` column has a named `<table>_<column>_range_check` that
rejects `'infinity'`, `'-infinity'` and every finite time past the upper
bound with `23514` (see "What 0007 adds"). Such a row can still exist if
it was written while a check was dropped (or left in place by a
`NOT VALID` re-add), or be read from a schema not yet migrated to `0007`;
the upgrade precondition finds them. The plain projection would fail the whole
statement on it, with `0A000` (`feature_not_supported`) for an infinity or
`22003` (`numeric_value_out_of_range`) past the bound. So the registry
selects a time outside the checked range as `i64::MAX`, one past the
latest readable microsecond (inferred), and a get, a list or an update's
returned row maps it to `UnreadableTimestamp { table, column, id }`, a
variant of its own, not an `Invariant` kind (lead ruling, 2026-11-21). A
list stops at the first such row in its order. `Display` and `Debug` name
the table and column but leave out the row ID (inferred: the ID is a row
value). The marker cannot collide with a stored time, since the range
checks cap stored values at `i64::MAX - 1` microseconds; a test reads rows
at both bounds back exactly. An update that leaves such a column
untouched (`update_tenant`, `update_principal`,
`update_trust_keyset_version`) fails with `23514` naming the range check
when a range check is in force but `NOT VALID`, since PostgreSQL checks
the whole new row; with the check dropped, the update applies its write
and then returns `UnreadableTimestamp`, so outside a caller transaction
the write is committed. `update_service_grant` replaces `valid_until`, so
with the check in force (even `NOT VALID`) a revision-checked update that
sets a finite `valid_until` (or none) succeeds and repairs the row. A
grant list-set change writes only the revision, so with the check in force
it still fails with `23514`; with the check dropped it applies and returns
only the new revision, since it does not read the timestamp column. The range checks of the tables the registry writes are in
`KNOWN_CONSTRAINTS`.
