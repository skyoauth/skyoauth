# Migrations

Versioned PostgreSQL migrations for `skyoauth-service`, embedded into the
binary with `sqlx::migrate!` and applied only by `skyoauth-service migrate`.
sqlx reads only files named `<VERSION>_<DESCRIPTION>.sql`, so this README is
not a migration.

## Conventions

- **Forward-only.** A migration that has been applied anywhere is never
  edited, renamed or removed; the runner refuses a changed checksum, and the
  checksum covers comments too. Fix forward with a new file. There are no
  down migrations.
- **Contiguous versions:** `0001_…`, `0002_…`, and so on. A unit test checks
  this; it is a test-time rule, not something the runner enforces.
- **One transaction per file.** sqlx wraps each file in a transaction. Never
  use `-- no-transaction`, and never write `BEGIN`, `COMMIT`, `ROLLBACK`,
  `END` or `ABORT` at the top level; a unit test lints for them.
- **IDs** are opaque text generated by the service, never chosen by the
  caller. Their format belongs to the ID-generation work, not to SQL
  defaults.
- **Collation:** every text column that holds an ID, a key, a reference to
  one or an enumeration value is `text COLLATE "C"`, so it compares, sorts
  and indexes byte-wise whatever the database's default collation is, and a
  foreign key always pairs two `"C"` columns. Only human-readable names and
  free text keep the default collation. This holds for every later migration.
- **Tenant-scoped rows** carry `tenant_id` with a foreign key to the tenant.
  Foreign keys never use `ON DELETE CASCADE` across authority boundaries;
  records are soft-disabled through a status column instead.
- **Types:** timestamps are `timestamptz`; revisions are `bigint` and only
  increase.
- **Functions that read tables** name each table with its schema and pin
  `SET search_path = pg_catalog, <schema>, pg_temp` (`pg_temp` last). A
  trigger function otherwise resolves names through the caller's
  `search_path`, in which `pg_temp` comes first: any role with DML grants and
  the default `TEMP` privilege could shadow a table with a temporary one, and
  logical-replication apply and `pg_dump` restores, which run with an empty
  `search_path`, would not find the table. Migrations do not hard-code
  `public`: `0002` resolves the schema with `current_schema()` at migrate
  time and creates such functions with `EXECUTE` in a `DO` block. Functions
  that only use `NEW`, `OLD` and built-ins need neither.
- **Append-only tables** attach `skyoauth_reject_mutation()` (from `0001`)
  and enable the triggers with `ENABLE ALWAYS`, so they also fire under
  `session_replication_role = replica`:

  ```sql
  CREATE TRIGGER <table>_append_only
      BEFORE UPDATE OR DELETE ON <table>
      FOR EACH ROW EXECUTE FUNCTION skyoauth_reject_mutation();
  ALTER TABLE <table> ENABLE ALWAYS TRIGGER <table>_append_only;
  CREATE TRIGGER <table>_no_truncate
      BEFORE TRUNCATE ON <table>
      FOR EACH STATEMENT EXECUTE FUNCTION skyoauth_reject_mutation();
  ALTER TABLE <table> ENABLE ALWAYS TRIGGER <table>_no_truncate;
  ```

  A rejected write fails with the project SQLSTATE `SK001`, which no
  PostgreSQL error uses, so callers can tell it apart from constraint
  errors such as `23001` (`restrict_violation`).

## What 0002 adds

`0002_foundation.sql` is the first slice of the M1a domain schema (T10.1):
`tenant`, `principal`, `instance_security_policy`, `egress_allowlist_entry`,
`audit_event` and `audit_chain_head`. Comments marked `(inferred)` are
choices the specifications do not dictate. Besides the append-only guard it
adds two shared guard functions, both failing with `SK001`:
`skyoauth_reject_immutable_change(column, ...)` rejects an `UPDATE` that
changes a named column (an argument naming no column is a plain `P0001`
error, so a typo fails the first update), and `skyoauth_check_revision()`
requires revision 1 on insert and exactly +1 on every update. Policy and
egress rows are never deleted.

- **Audit sink.** `audit_sink_config_digest` is `NULL` when no sink is
  configured or the sink configuration was removed (IR-053), and non-empty
  otherwise. `audit_sink_validated_at` must correspond to the current
  digest: it can only be set while a digest is, and an `UPDATE` that changes
  the digest must also change it, to `NULL` or to a later time (`SK001`).
  From `NULL`, any time is accepted. The database cannot tell which digest a
  later timestamp validated; that stays with the service.
- **Egress destinations** reject whitespace and control characters
  (`[[:space:][:cntrl:]]`; under `"C"` these classes cover ASCII only) and
  values over 2048 bytes, well below the btree limit of the unique index.
  Everything else about the URL is validated by the service.
- **Audit chain.** It is enforced in order: an event must extend the chain
  head (`sequence` = head + 1, `prev_hash` = head hash; the first event has
  a `NULL` `prev_hash`), checked when the event is inserted; the head may
  only advance by one to an existing event; and a deferred check fails the
  commit if the head has not reached every event the transaction inserted.
  `audit_event (tenant_id, sequence)` is indexed for per-tenant reads in
  chain order.
- **Absent values in audit events.** `previous_revision` and
  `new_revision` are `NULL` when there is no such revision (a create has no
  previous revision; tenants and principals carry none yet), as are
  `prev_hash` for the first event and `tenant_id` for instance-scope events.
  There is no sentinel: revisions start at 1 and 0 is rejected. The event
  hash encoding, not yet specified, must encode an absent value differently
  from every present one (for example JSON `null` against a number), so
  that adding or dropping a value changes the hash.
- **Instance-scope events** (lead decision): the startup event that records
  the `single_actor_mode` mirror (IR-053) and the sink-change event have
  `tenant_id` `NULL`, the policy row's `instance_id` as `object_id`, and the
  row's real revisions before and after the write in `previous_revision`
  and `new_revision`. The source and format of `instance_id`, the reserved
  actor for events the service writes on its own, and the `action` names
  (which must name the entity, since `object_id` alone does not) are open:
  identity-registry OQ-IR-14.

The database does not enforce these rules; the service must:

- generate every ID and `Tenant.secret_namespace` (T10.2), and resolve
  secret references only within the owning tenant's namespace (IR-034);
- insert the single `instance_security_policy` row at bootstrap (the schema
  allows at most one, not exactly one);
- keep `single_actor_mode` and the audit sink fields read-only online, so
  only the startup mirror of deployment configuration writes them (IR-053),
  and set `audit_sink_validated_at` only from a validation of the current
  configuration;
- require the second approver for the `widening_second_approver` toggle and
  for adding or re-enabling egress entries (IR-052, IR-054);
- check the expected revision of every write (compare and set);
- disable tenants and principals through `status` instead of deleting them
  (only foreign keys hold back a delete);
- validate `exact_destination` as an exact URL (IR-152);
- compute event and head hashes (the database only stores them);
- append audit events in this order: write the domain rows first, then lock
  the chain head (`SELECT … FOR UPDATE`), take `sequence` = head + 1 and
  `prev_hash` = head hash from that locked row, insert the event, advance the
  head and commit. The head lock comes last: a transaction that holds it
  and then waits for a domain row held by a transaction that waits for the
  head deadlocks, and one of them fails with `40P01`.

Concurrent appenders queue on the head row, which the insert trigger locks
too. A writer that took its `sequence` from a head another transaction has
since advanced waits for that transaction and then fails with `SK001` under
`READ COMMITTED` (the default), or with `40001` under `REPEATABLE READ` or
`SERIALIZABLE`. The database does not retry; a writer that locked the head
first gets the committed head and succeeds.

## Limits

- The guard triggers are a tripwire against application DML, not a
  security boundary. The table owner or a superuser can disable or drop
  them, or rewrite rows with `ALTER TABLE … ALTER COLUMN … TYPE … USING`.
  The real control is a runtime role that does not own the tables, together
  with the pinned `search_path` of the functions that read tables: a
  non-owner role alone is not enough, because without the pin a temporary
  table shadows the chain head for it. Today one `SKYOAUTH_DATABASE_URL`
  serves both `migrate` and the server, and separating the roles is a
  follow-up.
- Under `session_replication_role = replica` (logical-replication apply,
  some restores), foreign keys are not enforced: their internal triggers
  fire only in origin mode. The `ENABLE ALWAYS` guards and the `CHECK`,
  `NOT NULL` and unique constraints still are.
- An initial logical-replication table sync or a data-only reload of
  `audit_event` cannot pass the chain triggers: each copied event is checked
  against a head the copy does not advance, and the migration has already
  inserted the head row. Such a load needs the table owner to disable the
  user triggers for it (`ALTER TABLE … DISABLE TRIGGER USER`; the
  `pg_restore --disable-triggers` option needs a superuser) and to
  reconcile the head row.
  Streaming apply of committed transactions works, since each carries its
  event insert and head update together.
- The migration role must own the database, or at least have `CREATE` on
  the `public` schema (PostgreSQL 15 and later no longer grant that to
  every role).
- Runners serialize on a session-level `pg_advisory_lock`. It needs a direct
  connection: through a transaction-pooling proxy such as PgBouncer in
  transaction mode the lock and the migration can land on different server
  sessions. The lock wait has no timeout; adding one is a follow-up.

## Follow-ups

Not done in `0002`:

- Delete guards for `tenant` and `principal`, including
  `TRUNCATE principal`, which nothing references yet. ADR-008 item 3 settles hard
  delete for bindings and grants only; for tenants and principals it is
  open, and today only foreign keys hold back a delete.
- An `audit_event` detail column, for example the affected source IDs that
  the audit event of an egress entry write lists (IR-152, OQ-IR-12).
- A `revision` on `tenant` and `principal`: updates require
  ID, tenant and revision (tasks §3 "IDs/names").
- Who computes the audit event hash, with which algorithm and over which
  input (including the encoding of absent values above). This needs a spec
  decision before the first code that writes events.
